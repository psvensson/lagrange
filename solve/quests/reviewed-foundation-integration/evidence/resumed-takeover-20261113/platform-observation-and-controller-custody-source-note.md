## Error-driven platform fallback

History: commit265e187eadc2efd8ed919b0a415f1db48c85e25f (14September2026, dev: probe home lab node platform over ssh) introduced probeRemoteNode's catch-all POSIX failure→PowerShell branch. The behavior survived43e217c extraction unchanged. Current scripts/lab/probe.js78–86 catches any POSIX capture error, or an unknown successful OS result, and tries Windows. It does not discriminate missing uname from authentication/connectivity/command/metadata failure. This is systematic observer-selection/first-cause loss, not evidence of a current Linux placement failure.

Reachability: lagrange-lab.js commandNodeProbe invokes it without the registered OS; resolveNodePlatform invokes it for missing OS OR missing architecture, likewise without passing available declared OS. It can therefore select a Windows observer after a failure even when the existing node was explicitly Linux. Successful returned metadata is assigned/saved by commandNodeProbe; add saves only after resolution. Canonical corpus discovery instead calls probeTestCapability through fleet-discovery; it does not consume probeRemoteNode. A POSIX failure cannot establish Windows identity.

Existing project design precedent: observeLocalCorpusProcess selects Linux/Darwin observer before probing and returns UNAVAILABLE after read failure without switching; fleet settleProbe retains null capability plus original error. These are appropriate semantics to reuse within inventory owner, not a new cross-project authority.

Bounded proposed correction: pass the existing explicitly declared node/platform into the single platform observer; select POSIX for declared Linux/macOS and PowerShell for declared Windows before any remote call. A declaration selects protocol; it is not successful observation evidence. Preserve actual observed OS/arch and refuse explicit mismatch rather than retaining the declaration as verified. Unknown/unsupported platform must produce named unavailable/selection-required outcome without trying two protocols. Existing node-add documentation currently permits omitted OS; revise that interaction explicitly (require --os for a newly unknown target unless the owner chooses a separately evidenced single discovery protocol). Do not retain an auto/fallback compatibility path. Preserve original error/cause, no inventory mutation on unavailable, no assumed architecture, no replacing failed facts with old cache. Known-platform dispatch is legitimate; switching on an error is the prohibited fallback. Linux delivery scope does not authorize deleting Windows/macOS contracts.

Witness proposal in existing home-lab CLI test owner: temporary inventory plus finite executable transport witness records exact calls and returns controlled first POSIX failure while a forbidden PowerShell response would falsely report success. Invoke real public node probe on a declared Linux target; original must reveal second-protocol execution, candidate must retain first failure and byte-identical inventory. Add independent successful Linux observation, declared Windows direct selection (simulated transport only), architecture-only missing input, unknown platform refusal before transport, and observed/declaration mismatch. Count actual calls, distinguish SSH255 from remote nonzero/malformed output, preserve first failure and deterministic fixture closure. This proves dispatch/custody on Linux; not actual Windows/macOS remote execution. No such witness has run.

External design inspiration (primary sources): OpenSSH documents return of remote command status or255 for an SSH error: https://man.openbsd.org/ssh.1#EXIT_STATUS . Therefore unsuccessful SSH capture is not platform detection. Ansible network playbooks explicitly supply ansible_network_os and connection/module before gathering facts: https://docs.ansible.com/projects/ansible/latest/network/getting_started/first_playbook.html . This is an analogous configured dispatch boundary, not proof that Lagrange must copy its API.

## Controller machine reservation

Current runLabTest/startLabShare sends controller files directly to runClassifiedChild. That child sets placement=local; neither its path nor the classified/file runner acquires the machine-wide lock. splitHeadroom checks exact commit and thermal/load; controllerMachine consumes cores/memory but not controller machineLock. Remote shards separately take the machine lock and holder record in placement shell. Discovery deduplicates identical boot identities.

Consequently direct unreserved --split cannot be described as internally locking every assigned physical host. Conversely a genuine outer controller reservation need not self-deadlock: the controller path does not reacquire its lock. Current approved outer-reserved route satisfies this bounded proof condition when reservation spans the actual controller work/closure; remote shards retain independent locks. Do not infer a generic job necessarily excludes the controller or that idle discovery itself reserves it.

Future owned correction/witness: make controller reservation authority explicit through the existing placement/hold owner before any controller workload, with clear reuse of an already acquired reservation instead of guessing from an environment flag or holder JSON. A competing real flock holder must prevent controller child admission; verified self-owned reservation must permit one child without reacquisition deadlock; admission race after discovery must refuse; closure retains first nonzero result and releases only the run's reservation. Use real finite children, real machine-lock fixture paths and independent teardown. This is an unimplemented source finding, not a demonstrated concurrent collision and not a reason to discard already valid externally reserved evidence. No new lock service or alternative scheduler is proposed.
