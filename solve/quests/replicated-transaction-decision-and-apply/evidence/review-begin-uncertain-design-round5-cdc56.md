## Findings — one category-complete round

### R5-1 — HIGH — descriptor-to-handoff conversion can deadlock at the aggregate byte limit

D:839-861 places operation, descriptor and result-handoff retained bytes in one aggregate pool. D:902-907 requires reserving the handoff count and bytes **before** releasing descriptor capacity. If reserve fails, D:929-931 retains the descriptor and defers resolution. A legal single descriptor may consume the entire byte limit under accepted P1, and several legal descriptors may collectively fill it. Once their rows resolve, none can reserve even a smaller handoff while its descriptor charge remains held. No unrelated release is guaranteed: all owners can be in the same resolved-but-handoff-starved state, so the existing sweep only repeats the refusal.

This is a check-act/resource-transfer deadlock, not a request to overcommit or raise the limit. The resource owner needs an atomic exact-token reclassification: compute the post-transition aggregate, synchronously drop the descriptor-only row/key/closure references at the same owner turn, and exchange that exact charge for the handoff charge without an unowned interval. Alternatively, descriptor admission must reserve explicit handoff headroom up front and charge it throughout. The low-cap witness must include a descriptor whose legal charge fills the pool and a cohort that fills it collectively, then resolve them and prove delivery/recovery and exact reclamation progress without external capacity release.

### R5-2 — HIGH — the result-delivery CAS has neither the normal uncertain-answer transition nor an actual pgwire acceptance edge

The first BEGIN intentionally returns typed uncertainty immediately (D:120-126 and D:983-984). B4-1 releases an attachment “on answer” (D:863-869). B4-2 defines only `WAITING(invocationId) -> DELIVERED` when that original invocation accepts **success**, or `WAITING -> HANDOFF_PENDING` when detach wins (D:924-929). A normal, successfully delivered `TRANSACTION_CREATION_UNCERTAIN` answer is neither transition: the caller stopped waiting and its attachment is released, but it did not detach and did not accept success. The later sweep therefore has no specified CAS state from which it may own `ACTIVE_READY`.

The other end is also undefined at the actual protocol owner. Today the engine promise resolves first; the handler writes CommandComplete, then mutates its `PgWireSession` to T, then writes ReadyForQuery using that state (`pgwire-protocol-handler.js:619-669,691-697`, `:597-601`). No typed interaction reports this acceptance to the coordinator. “Pgwire then enters transaction state normally” (D:936-939) and “delivered/consumed” (D:974-976) do not choose a linearization or a failure disposition. Marking DELIVERED when the engine returns is too early; marking it after the local state change needs a named token-bound callback whose stale/refused result cannot leave pgwire at T or duplicate a handoff. Socket `write()` itself is not durable client acknowledgement, so the contract should name the intended server-side protocol linearization rather than claim remote receipt.

Define a complete state machine for at least: WAITING → UNCERTAIN_ANSWERED (live-session delivery entitlement retained without the old waiter), WAITING → DIRECT_SUCCESS_CLAIMED, UNCERTAIN_ANSWERED → HANDOFF_PENDING, and one exact handoff-consumption token → ENTERED_ACTIVE at the handler/coordinator boundary. State which owner writes CommandComplete, applies the coordinator CAS, mutates `PgWireSession`, and writes ReadyForQuery, including callback throw/stale/close races. Application-database direct promise completion must use its own declared non-pgwire consumption edge without pretending it has a wire block. Required evidence must latch after engine success, before CommandComplete, between CommandComplete and local T, and before ReadyForQuery, then show one owner of the result and the correct I/T state.

### R5-3 — HIGH — close-before-handoff-install can retain an unreachable session result

D:947-953 says session close removes the handoff and releases its capacity. D:902-905 also says resolution after a caller detached installs a handoff. If `closeSession` detaches/removes while no handoff exists and the in-flight/sweep classifier later resolves, the late path can install `creationResultBySession` after the only session cleanup already ran. An exact session string is not a current-session lifecycle witness. The result is unreachable by the closed socket and unreclaimable until process shutdown; repeated close/late-resolution schedules can consume the bounded handoff pool and block live sessions. Current close is synchronous and deletes the adapter session after optionally launching rollback (`postgres-wire-adapter.js:276-305`), while handler destroy calls it before dropping its local session (`pgwire-protocol-handler.js:165-181`).

Bind attachments and handoffs to an exact live protocol-session incarnation/token, capture it before awaits, and recheck it atomically at install and consumption. If close wins, late resolution must publish only server workflow/recovery state and must not install client-delivery state; it must still perform the exact descriptor-to-server-state resource conversion. If install wins, close must remove that exact token and a later callback must be inert. The witness must exercise close at I and legacy/racing E both immediately before and after result installation, then prove zero handoffs for the retired session, preserved workflow/durable identity, and later sweep progress.

## Required bounded correction

Preserve B4-1 and B4-3. Amend B4-2 only enough to:

1. atomically exchange an exact descriptor charge for its result-handoff/server-state charge, or reserve the necessary headroom at descriptor admission, with full-pool progress witnesses;
2. name the normal uncertain-answer delivery-entitlement transition and the exact handler/coordinator consumption token and server-side protocol linearization for CommandComplete, local T and ReadyForQuery; and
3. bind client handoffs to an exact live protocol-session incarnation so close-before-install installs no unreachable result and install-before-close is reclaimed once.

Then implement and verify the coupled owners. This review does not reopen the six-field identity, producer/reader domains, fixed encoding, restart ceiling, transaction binding, activation, C17 or broader transaction design.
