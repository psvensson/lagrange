## Findings — one complete round

### B4-1 — HIGH — the waiter bound can release before its retained FIFO work disappears

D:623–627 claims an independent count bounds foreground request closures. For a **first BEGIN**, however, D:629–645 reserves the waiter only **inside the session FIFO**, after enqueue has already retained the operation. Only retries of an existing descriptor reserve before enqueue (D:679–682). Concurrent first calls that observed no binding can accumulate before the first insertion creates one; unrelated sessions can also enqueue before the new resource gate runs. A later capacity refusal does not bound the already-retained waiter population.

For a retry, D:679–680 and :782–787 releases its waiter token on caller deadline/detach, while D:752–754 explicitly allows its coordinator turn to continue. The existing FIFO is a promise chain, `previous.catch(...).then(operation)`, with no unlink/cancel operation (`src/query/distributed/distributed-transaction-statement.js:22–33`). Releasing the caller-facing token does not remove that operation closure, promise reaction or any captured descriptor/strings from the chain. Repeated short-wait retries behind a slow head can therefore reuse the same small waiter capacity while retaining many unresolved operations. A timeout check only when each operation eventually runs does not fix this retention gap.

P1 correctly requires one encoded row, streaming key hashing, and dropping descriptor references before releasing descriptor capacity (D:631–677). The remaining budget must also account for variable strings retained by queued callbacks or descriptor/map keys: a captured session string remains retained after request/socket lifetime ends, even if it was originally allocated by the request. D:649's “temporary” input exclusion cannot justify excluding a still-retained closure/reference. This does not require an exact JS heap estimator: a documented conservative count/byte bound and copy/lifetime model is sufficient, including any multiplicity relative to canonical encoded bytes.

**Required bounded correction:** reserve the foreground/FIFO resource before enqueue for every BEGIN branch, including the first request and calls racing the first descriptor install. Distinguish completion of the client wait from release of the queued/running server operation. Either remove/neutralize and drop captured references before releasing that retained-work token, or keep the token charged until the bounded operation settles; separate caller attachment accounting if necessary. Define how all waiters for a closing session are detached (the new method currently refers to a singular current waiter), while the exact descriptor remains server-owned. Retain one FIFO and the existing sweep; no new retry scheduler is needed.

**Required witness:** low count/byte settings; withhold a real first INSERT/FIFO head; issue both racing initial BEGINs and repeated short-deadline retries; expire/detach callers without releasing the head. Assert actual retained operations/closures/strings remain bounded and no further delivery occurs at capacity. Release the head, prove exact once-only reclamation and reuse, and then prove disconnected descriptor recovery under the original identity.

### B4-2 — HIGH — background resolution can strand the ordinary same-session BEGIN retry

The promised normal-client path at D:775–798 assumes the retry encounters an uncertain descriptor. N1 only defines reentry for `INSERT_OUTCOME_UNCERTAIN` (D:414–421). P1 separately allows an exact initial readback to change that descriptor to ACTIVE and release its attempt bytes in a no-await turn (D:659–660), including when a foreground waiter is detached or when the sweep performs reconciliation.

Schedule: first plain BEGIN returns uncertainty and `ReadyForQuery(I)`; retain the same live socket. Before the next BEGIN arrives, the existing sweep or a late bounded server turn reads the original initial row and changes the descriptor to ACTIVE. The client still has no wire transaction ID. The actual coordinator's ordinary ACTIVE branch answers `TRANSACTION_ACTIVE`, not successful BEGIN with that original ID (`src/query/distributed/distributed-transaction-coordinator.js:230–246`). The wire enters a transaction only on a successful executed BEGIN (`src/runtime/pgwire-protocol-handler.js:641–668,691–695`); an error from IDLE keeps it IDLE (`src/runtime/pgwire-transaction-outcome.js:155–170`). Thus same-ID durability is preserved, but the proposed ordinary client recovery promise is not fulfilled. No design rule currently handles this resolved-but-not-delivered interval.

**Required correction:** define the existing coordinator/adapter handoff for a retained creation that resolves after its caller has stopped waiting but before the same live session retries. Preserve enough exact owner state to return or reconcile the original BEGIN result without treating it as a second ordinary BEGIN, minting a replacement, silently running user statements outside the intended protocol block, or resurrecting an expired/advanced transaction. If resolution has already advanced/ended, return that exact typed disposition and permit the appropriate subsequent protocol action. Keep reconnect a new session domain; no hidden client token or cross-session inference is needed.

**Required paired schedules:** (1) plain retry wins the FIFO before background reconciliation, and (2) background/late reconciliation becomes initial ACTIVE before the plain retry. Both must use one ID and give the wire the correct current transaction state; add the advanced/expired outcome so a stale successful BEGIN cannot reopen settled work.

### B4-3 — HIGH — ROLLBACK while creation is uncertain changes the protocol state the detach design assumes

B2 deliberately makes `hasActiveTransaction` report occupied for an uncertain descriptor and returns typed uncertainty for ROLLBACK without performing rollback (D:251–258). The actual statement owner stamps failed transaction-end answers using precisely `hasActiveTransaction` (`src/query/sql-query-engine-statement-execution.js:534–542`; `src/query/sql-query-engine-statement-admission.js:138–145`). Pgwire's existing failed-ROLLBACK rule converts an occupied result into FAILED even when the prior wire state was IDLE (`src/runtime/pgwire-transaction-outcome.js:179–201`).

Concrete ordinary-client sequence: BEGIN uncertainty → error + I; client sends ROLLBACK to clear it → uncertainty + **E**; client then sends plain BEGIN → protocol admission refuses it before the coordinator (`src/runtime/pgwire-session.js:265–281`). Destroy now passes `transactionOpen:true`, contrary to D:767–769's unconditional uncertain-BEGIN IDLE assertion (`pgwire-protocol-handler.js:165–179`); `PostgresWireAdapter.closeSession` consequently takes its rollback cleanup branch (:276–305). The proposed coordinator gate prevents an unsafe rollback, but neither the advertised always-IDLE cleanup rationale nor subsequent plain-BEGIN reentry is correct for this reachable sequence.

**Required correction:** specify the typed protocol distinction between a retained creation obligation and an entered transaction block at the actual engine-state stamp/pgwire outcome owner. Choose and document the ROLLBACK/error/ReadyForQuery behavior while creation remains uncertain, including whether/how a same-session plain BEGIN can reenter afterward. Do not fake `NO_TRANSACTION`, discard the descriptor, issue rollback merely on uncertainty, or globally make occupied state false and enable autocommit. Detach must preserve the server obligation for both actual I and E close paths. A positive ROLLBACK after a fully established transaction remains ordinary existing behavior.

**Independent minimal diagnostic:** imported the actual `resolveFailedStatementOutcome`, canonical AST constants and `PG_TRANSACTION_STATE`; with `stateBefore=IDLE`, `TRANSACTION_CREATION_UNCERTAIN`, and `engineHoldsTransaction=()=>true`, BEGIN returned `{kind:"engine_error",state:73}` (**I**), ROLLBACK returned `{kind:"engine_error",state:69}` (**E**). This directly checks the existing outcome owner, not a full wire/startup witness. An initial mistyped import path failed before execution and is excluded from semantic evidence. No repository file was created for the diagnostic.
