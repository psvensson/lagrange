## 10. Round 2 amendments from the closed-admission startup census (2026-10-12)

Source: `evidence/activation-reduction-2026-10-12/startup-admission-census.md` (sections C, D, E, G). Each amendment names the census fact, the rule, and the change to sections 2-6.

### 10.1 Restart revalidates incarnations under the same cycle (D.2)
Fact: the FRESH_SEED authorization id hashes a per-boot random `invocationId` (`participant-release-authorization-owner.js:34-38`, `seed-startup-session-store.js:226-233`) and the retained targets embed `lifecycleIncarnation/runtimeGeneration/connectionGeneration/admissionGeneration/ownerIncarnation`, so `continueDurableRelease` never matches after a restart and the full cycle, RETIRE first, runs for every partition on every seed restart.
Rule: owner 18:32 — the persisted decision survives restart; incarnation observations are revalidated.
Change: (a) the cycle's population is bound by replica identity (`replicaIdentity`, `peerId`) in RESERVE/FINALIZE; the per-incarnation fields live only in RECEIPTs (one CURRENT receipt per replica identity, revisioned). (b) Observe compares the decision: release identity, cycle `(dependent, gen)` CONFIRMED at the control, population by replica identity; it never compares the root authorization id or any incarnation field. (c) A restarted member whose CURRENT receipt names an old incarnation records a retirement obligation for that receipt, the recovery owner carries `RETIRE(dependent, gen, target)` to the control leader, and the member re-RESUMEs under the same cycle with a new receipt (revision+1); the old-incarnation refusal holds because the local predicate (`resumeParticipantCutoverAdmission`) still requires the receipt's target to equal the current generation. No PAUSE, no RESERVE, no new cycle on restart. (d) The root authorization is consumed only where a cycle STARTS (the fresh-storage authority check when the origin is null, `participant-cutover.js:577-584`); a request without a root (recovery loop, `existing:<releaseId>`) may continue or observe a cycle but never start one on null origin (existing OPERATOR_REQUIRED).

### 10.2 One attempt per partition across drivers (D.2, G.6)
Fact: the seed loop (trigger FRESH_SEED, 100 ms retry) and the recovery loop (trigger EXISTING_ORIGIN, 30 s attempt, 1 s re-enqueue) share `RUNS` and refuse each other with `different_release_request_in_flight` because the request identity includes trigger, deadline and authorization id (`participant-cutover.js:770-783`).
Rule: R11 one execution path; concurrency-serialization template item 3 (single winner, other drivers are nudges).
Change: the single-flight key is `(partitionId, releaseId)`; a second request for the same key joins the running promise (its own deadline only bounds how long it waits for that promise; the attempt's deadline is the longest of the joined requests' or the recovery bound). A request for a different `releaseId` is refused typed `release_identity_in_flight`. Trigger and root authorization are attributes of the first starter, not of the key.

### 10.3 A membership change — OWNER DECISION requested (C.2, D.1)
Fact: every conf change closes admission on every member because the OPEN proof embeds `configurationKey` and `membershipGenerationIndex` (`transaction-pause.js:54-60`), and the release identity embeds them too (`release-identity.js:149-157`); a joiner's fresh-create therefore runs a full cycle on the LEADER, pausing the whole partition (all writes on it, including other nodes' registration rows and heartbeats, are `CUTOVER_PAUSED` until RESUME), and any STALE member answer in `resumeCohort` restarts the attempt. During formation (many ADDs across system partitions) this is a repeated write-unavailability window of one cycle each, i.e. the spent-wait class that certification forbids.
Question for the owner: must a population change pause writes at all? Recommendation: no. The participant protocol's correctness rests on Raft commit; a new member joins the current cycle by its own RECEIPT (its RESUME binds the cycle and its incarnation) once it has applied the log; existing members keep OPEN. The cycle identity then changes only on a build change, an explicit operator release, or the legacy cutover; `configurationKey`/`membershipGenerationIndex` leave the release identity and the OPEN proof (the committed configuration is still bound at FINALIZE apply through `committed.committedConfiguration`, and a member not in the current committed configuration cannot commit anything). Trade-off: the "complete fixed population bound at finalization" clause of the predecessor design is dropped in favour of "population = the committed configuration at each commit"; a stale member is fenced by Raft, not by the population list.
Interim (this increment, until the owner decides): keep the conf-change invalidation and the cycle, made cheap by 10.1/10.2 and section 2 (no retire storm, no nested control cutover, observe-first), and MEASURE the window per membership change in W-H. The owner decision is recorded on the quest log when given.

### 10.4 Snapshot install does not wait for the retirement route (E.1, D.4, G.3)
Fact: `beforeServiceReplacement` retires the old projection and a `RETIREMENT_FAILED` aborts the install (`snapshot-catchup.js:369-376`); the RETIRE route needs a local control leader or the engine's topology owner, whose SERVICES rows exist only after release.
Rule: owner 20:32 — the successor cannot publish CURRENT, consume authorization or report OPENED before the ordered retirement; nothing says the data install must wait.
Change: the install proceeds; the replacement starts CLOSED (existing); the old receipt's retirement is an obligation carried by the recovery owner; the successor's RESUME (its receipt) is refused typed `predecessor_retirement_pending` until the obligation has a committed result. Ordering preserved, liveness restored.

### 10.5 Typed dependencies that stay outside the release owner (E.3, G.1, E.2)
- Query settlement on a restart with HELD `sql_transactions` rows needs engine routing that may not exist before cache hydration (G.1 unsettled): typed `query_settlement_unavailable` with `retryAfterMs`; the recovery owner re-drives after hydration. Observe (10.1) needs no settlement, so a restart with a valid record never waits on it.
- A conf-changed learner not yet in its node's `localServices` answers `hosted_replica` UNAVAILABLE (existing, typed); the attempt waits inside its bound.
- `topologyTransitionOf` UNAVAILABLE before a joiner's cache hydration (`topology-fence.js:80-81`) stays `release_topology_pending` (existing, typed).
