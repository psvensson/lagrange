# WASM writer slots v1: selected contract

Base: cdcb9c95f4bdb90e709ed4d20058b51cb193625f. Source review required before implementation. This specifies the user's selected new protocol, not existing behavior. The evidence-only Quest and original WASM/F1/W07 inputs remain unchanged. A separate v1 companion is authorized. No runtime-owner edit, generic proposal wait or main merge.

## Ownership and interfaces

WasmServiceLifecycle is the trusted local administrative ingress. Add an explicit `administerWriter(serviceId, intent)` method addressing its current hosted replica. It is a NEW interface owned by this existing lifecycle; it is not accepted by raw replica `handleMessage`, never enabled by an `authorized:true` payload, and has no independent permit store. The trusted local administrative caller retains exact intent before calling. Nonleaders return redirect without proposing. The existing private-network/trusted-process threat model applies; identity is not a claim of authentication against arbitrary trusted-host code.

WasmServiceReplica owns write request admission, bounded local completion interest and generation-fenced publication. A new WASM-specific request-state module is the application result implementation, borrowing the existing database. Codec/admission own canonical v1 bytes. The Raft application transaction supplies atomicity, applied position and `effects.afterCommit/afterRollback`; it is unchanged. Runtime remains free while callers await application.

Provide a caller-facing writer client/builder in the WASM subsystem: caller-supplied retained writer token, immutable pending command, terminal receipt, and an explicit persistence adapter. Persist pending before first send, terminal response before advancing; re-drive sends the same canonical command. A helper without durable storage promises only its supplied storage's lifetime. No implicit fresh identity after UNKNOWN. Transport redirect/lost response leaves pending bytes intact; no automatic effect retry under a new token. One logical write at a time per client/slot. The helper synchronously claims the slot before its first await. Its storage adapter must provide atomic compare-and-replace against a revision, including across helper instances/processes; plain get/set is insufficient. Persist failure before delivery sends nothing and preserves prior state. Persist failure after a response preserves pending identity and blocks sequence advancement; restart retries/queries that exact pending request. Terminal receipt and removal of pending form one atomic storage update. Concurrent submit cannot overwrite pending, and stale CAS completion cannot erase a successor state. The helper reports storage uncertainty rather than claiming restart safety from a volatile adapter. Caller storage and delivery are injected existing integration boundaries, not a global request service.

## Common profile and encodings

One compiled profile `wasm-writer-v1/1`, persisted by INIT and validated on restart:
- W=64 slots, created once; slot integer0..63.
- serviceId UTF-8 <=128 bytes; incarnation and admin intent nonce exactly64 lowercase hex chars (32 random bytes created by trusted caller before delivery).
- generation and sequence safe nonnegative integers <=Number.MAX_SAFE_INTEGER; no rollover. First allocated generation1, first write sequence1. Generation exhaustion permanently refuses recycle for that slot; never wraps. These are protocol-domain bounds, not full64-bit support.
- sessionId/key UTF-8 <=256 bytes each; value bytes <=32768, encoded canonical base64. JSON encoded canonical full command <=49152 bytes. Validate before proposal AND inside application; never truncate. Fixed field order and rejected unknown fields prevent aliases. Canonical encoding covers identity, action, session/key/value, preceding receipt acknowledgment. Transport route/attempt is excluded.
- Strong-write common KV limits: 65536 value bytes per session and 1048576 per service, evaluated from replicated KV rows at application. Pass this compiled/persisted profile explicitly to the existing SessionKVStore limit evaluator; do not consult mutable local setLimits for v1 strong decisions. ASYNC/TIMER keep their existing separate call semantics. These value-byte limits do not bound key counts or total SQLite storage. A strong request can deterministically refuse because prior strong/ASYNC state fills this profile.
- terminal receipt serialized <=2048 bytes; admin retained intent/result pair <=4096 bytes; scalar bookkeeping <=512 encoded bytes/slot; metadata <=4096 bytes. Bounds are enforced, not inferred from count. Worst-case JSON escaping is included: 128 UTF-8 bytes may encode as 768 ASCII bytes and 256 as 1536; 32768 value bytes encode as 43692 base64 bytes. The exact codec must enumerate maximal legal command/admin/receipt/metadata shapes and verify each final serialized budget, including escaping and maximum safe counters, before the source checkpoint. INIT must validate the full profile and all supported maximal admin encodings; it cannot initialize a service that cannot enroll at its legal identifier boundary.
- application request/outcome payload bound: 4096 +64*(49152+2048+4096+512)=3,575,808 bytes. This deliberately overcounts each record's fields and is an encoded logical-state bound only. SQLite pages, WAL, retained Raft log/occurrences, copies, KV values and snapshots are excluded and retain storage/runtime ownership.
- pending local unique intents <=64, duplicate waiters <=4/intent, global waiters <=128. Own at most one canonical command buffer/intent. Request wait uses the caller's finite deadline with maximum5000ms local interest; a timeout is UNKNOWN after possible proposal. This is a new bounded wait, not an increase to transport/test deadlines. Pending bytes <=64*49152=3,145,728 plus bounded waiter metadata. Removing interest cannot release runtime custody or durable result/fence.

Canonical command fields will be exact named objects in the codec; strong `write` accepts only the v1 shape. Required identity `(serviceId,incarnation,slot,generation,sequence)` is distinct from KV sessionId and messageId. Request content includes the preceding-ack token and canonical payload. Receipt is the exact stored object `{version,identity,commandDigest,outcome,index,term}` plus deterministic refusal code where applicable; its acknowledgment token is SHA256 of the canonical receipt. Matching this token is a caller's explicit acknowledgment of that receipt, not cryptographic proof of having physically received a network reply. Invalid/gapped/forged ack requests receive protocol refusal and never advance writer state.

Positions come from the existing application callback; require Number.isSafeInteger(index/term), positive index, nonnegative term, otherwise fail application closed. Never stringify a rounded number as exact. This does not upgrade the existing operation port to full64-bit support.

## Persistent format and INIT

`_wasm_writer_meta`: singleton format/profile/serviceId/incarnation/initIntent and INIT receipt. `_wasm_writer_slots`: fixed slot PK, generation, completed sequence, retained command bytes and receipt, last successful admin intent/result. These are proposed names under the existing WASM application owner, not an independent service. Results and bookkeeping are bounded by the profile; no additional row per request.

Before creating SessionKVStore/normal serving, inspect format. A genuinely empty application database may create the v1 schema with explicit UNINITIALIZED metadata. A retained database with application/consensus tables but no v1 marker is incompatible and is refused without mutating/deleting tables. A malformed/missing expected row in an established v1 format fails closed; absence never means fresh. Existing alpha policy permits explicit new service creation, not in-place guessed migration.

INIT is a trusted lifecycle-admin command containing fresh incarnation, exact compiled profile and caller-retained nonce; it only transitions UNINITIALIZED once. It creates64 generation0 empty slots inside application. Exact INIT replay returns its retained receipt; different INIT against initialized state returns conflict, never replaces incarnation. A newly recreated service chooses a new incarnation before INIT; no per-replica lifecycle UUID substitutes for the service's replicated incarnation. Noninitialized STRONG refuses; v1 marker alone does not grant writer admission. ASYNC/TIMER remain their distinct old command semantics; their application is not newly assigned exact-write identities.

## Admin enrollment/recycle

No autonomous slot allocation loop. Caller selects a slot and retains `(service,incarnation,slot,expectedGeneration,expectedCompletedSequence,expectedReceiptDigest,newGeneration=expectedGeneration+1,nonce)` before submission. ENROLL requires generation0/sequence0/no result. RECYCLE explicitly abandons the selected generation and checks the exact expected generation, completed sequence and current receipt digest at actual application. It may retire unavailable historical answers but does not undo effects or retag uncertain writes.

On match: atomically increment generation, reset completed sequence0 and clear previous write detail, store exact admin intent and token/result. Fixed slot row remains. Exact admin replay returns stored result, even if writes subsequently advanced within that same generation. A later successful recycle replaces this admin cell; older admin retries return fenced/unavailable, never allocate again. Same expected generation with competing nonce has one winner; loser is fenced because generation advanced. Expected-state refusal does not change state. A future expected generation or sequence is refused at ingress, not put into consensus as a deferred authorization. Saturation means all slots are allocated; it requires explicit owner reclaim, never a new row or TTL/LRU.

A write ordered before recycle may commit and causes exact-state recycle refusal if its expected sequence changed; admin must deliberately observe/authorize a new recycle intent. Recycle ordered first fences delayed old-generation writes. Neither ordering rolls back the other.

## Write transition table

All new proposals are leader-local semantic admission checked against the existing durable application state through one WASM result owner; replicated application repeats the deterministic classification at its actual prefix. There is no follower-local quota predicate in application.

| State/request | Disposition/effect |
| --- | --- |
| Missing identity, wrong service/incarnation, invalid codec/profile/domain | Typed pre-proposal refusal; no strong anonymous fallback |
| Old generation | FENCED; no state mutation |
| Future/unknown generation, sequence gap | OUT_OF_SEQUENCE; no speculative reservation or future authorization |
| sequence < completed | HISTORY_RETIRED; never reexecute |
| sequence == completed, exact retained canonical bytes | Original stored receipt, no KV effect or result allocation |
| sequence == completed, different canonical bytes | CONFLICT, preserve original record |
| sequence == completed+1, completed0 and ack null | New intent admissible |
| sequence == completed+1, completed>0 and ack matches exact retained receipt | New intent admissible; previous detail remains until successful application transaction |
| missing/wrong ack | ACK_MISMATCH; no advance or retirement |

The leader must not propose future/gapped requests. A protocol refusal is not a retained terminal application result for an admitted logical write and cannot consume its sequence. Classification of an unexpected invalid committed command still cannot mutate KV/writer state; this path is diagnosed distinctly. Duplicate physical log occurrences repeat no effect: they find the retained receipt or monotonic retired/generation fence. A permitted later request can retire the older detailed answer; it cannot change that older request's terminal fact into a new failure or success. HISTORY_RETIRED is explicitly unavailable detail, not a rewritten outcome.

For new admissible intent: within the existing application transaction, applySet returns its actual accepted/refused result, write canonical contents/terminal receipt, advance completed sequence, atomically replace prior acknowledged detail, and advance applied state. Deterministic size refusal consumes the sequence with a refusal receipt; actual environment/transaction failure rolls all of it back. Post-commit hook publishes receipt only to matching instance/intent interests. Apply-time protocol refusals (including recycle-before-delayed-write, conflict and retired history) also publish their actual typed disposition to that exact committed command digest afterCommit, even though no additional durable refusal row is allocated. A receipt for another command never resolves this interest. On replay, the monotonic slot fence classifies unavailable history separately from the immutable retained outcome; a protocol refusal at an invalid prefix is not a terminal write receipt or evidence of permanent noncommitment. New ingress must rerun semantic admission, and no accepted future/gapped intent may be queued as a deferred grant. Local applied-index publication also waits for afterCommit. Same-key writes from other slots are legal; A's retained replay after B returns A's original result without touching B.

## Live completion/lifecycle

Enroll interest synchronously before proposing; same exact pending key joins within duplicate bounds; conflicting contents refuse without another proposal. Only one canonical buffer per intent. Proposal acceptance is not completion; v1 strong path awaits separate completion promise. Generic proposeEntry remains acceptance-only for ASYNC/TIMER callers.

On success afterCommit: resolve exact matching interest, dispose timer/buffer/waiters. On environment rollback: resolve typed UNKNOWN/environment reason, no success. If proposal is demonstrably refused before any possible effect, return a pre-proposal refusal; otherwise error/role loss/shutdown/deadline is UNKNOWN with original identity. A recorded result wins when available. Instance/intent object identity fences stale callbacks; shutdown settles owned interests before database release. Cleanup never deletes durable slots/results or claims cancellation. Client retries retained bytes through the same request path; no separate driver/polling KV value.

## Exact v1 boundary shapes

The write delivery remains `operation:'write'` and adds `requestId:{serviceId,incarnation,slot,generation,sequence}` and `ack:null|64hex`. `sessionId`, `key` and `value` remain the KV payload; deadline belongs to local delivery interest, not immutable command contents. The codec constructs `{type:'WASM_WRITER_V1',profile:'wasm-writer-v1/1',action:'WRITE',identity:requestId,ack,sessionId,key,value:<canonical base64>,valueEncoding:'base64'}` in that field order. Reject unknown public write fields, except documented delivery-only deadline; never retain a caller-mutable object after admission.

Admin command shape is `{type:'WASM_WRITER_V1',profile:'wasm-writer-v1/1',action:'INIT',serviceId,incarnation,nonce}` or `{type,profile,action:'ENROLL'|'RECYCLE',serviceId,incarnation,slot,expectedGeneration,expectedCompletedSequence,expectedReceiptDigest:null|64hex,newGeneration,nonce}`. All fields are required and no extras are permitted. The trusted lifecycle method receives this canonical command and never routes it through raw write messages. INIT's profile identifier selects the entire immutable compiled profile, not independently mutable limits.

Write receipt shape is `{version:1,identity,commandDigest,outcome:{accepted:boolean,error:null|string},index,term}`. Admin receipt is `{version:1,commandDigest,outcome:{accepted:true,token},index,term}` with INIT token `{serviceId,incarnation}` and enrollment/recycle token `{serviceId,incarnation,slot,generation}`. Its retained exact command binds the admin identity; it need not repeat that identity twice inside its receipt. The public terminal write reply is `{status:'RECORDED',accepted:<actual outcome>,async:false,receipt}`. Protocol refusals are `{status:'REFUSED',reason,identity}`; uncertainty is `{status:'UNKNOWN',reason,identity}`. A reply without a receipt never permits caller acknowledgment/sequence advancement.

The caller adapter has `load()` and atomic `compareAndSwap(expectedRevision,nextState)` returning the persisted revision/state or an explicit conflict. Its record retains writer token, last receipt and optional exact pending command. A helper holds a synchronous busy claim across all storage/delivery awaits, validates loaded state and response identity/content digest, and uses CAS for every transition. A process losing a CAS never sends its newly constructed mutation. Only persisted terminal state permits constructing the next sequence with its receipt digest. Retrying an existing pending command does not create another logical identity.
