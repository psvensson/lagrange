DECISION SUMMARY

1. Existing ProposalQueue bounds live waiters, not outstanding commands or
   future application results. Its 1000 entries cannot establish finite Q.
2. A runtime-owned projection of command custody can use the existing log and
   result authorities. It needs new, explicit admission/transfer/reconstruction
   seams; no current API supplies them. It must cover forwarded MsgPropose as
   well as local propose, and separate unique requests from physical copies.
3. The result owner is the existing committed-statement-outcome owner, with a
   narrow typed release-result extension, not a second generic outcome ledger.
   Application plus result plus applied-position already have one SQLite
   commit point. That is the correct exchange boundary for result reservations.
4. A single replaceable retirement cell per partition+origin is a plausible
   result-owner extension. One new retained cell PER GENERATION is unbounded.
   A fixed cell can avoid consuming its own normal result slot, but it cannot
   by itself guarantee proposal, persistence, application or recovery progress.
5. The prior 5,388,288-byte arithmetic is only a proposed logical release
   encoding envelope. It does not bound native/JS/transport copies, old log
   history, SQLite pages/WAL, snapshot staging, or transaction settlement.

ALL FINDINGS AND MINIMAL ADVERSARIAL TRACES

F1. Waiter Q is not command Q. [Native-source reachability, not executed]
  Keep a leader active using heartbeat responses; delay/drop append responses
  so proposed entries remain unresolved. Admit up to the local waiter limit;
  persist proposals; expire their 30-second waiter deadlines; admit another
  batch. Source L1/L2/L7 admits this schedule without an application Q guard.
  Quorum activity and advancement of the append match/commit index are different
  facts; merely invoking check_quorum does not close this schedule.
  Required: timeout only detaches a waiter; custody ends on a proved release
  edge owned by runtime/application, not on timeout or transport response.

F2. Exact duplicates require two bounds. [Native-source reachability]
  Propose R, lose its answer while R is still unapplied, expire local maps,
  retry identical R. Existing request lookup is absent and pending map empty;
  another log copy can be proposed. When both apply, L9 keeps one result but
  both log positions and copies existed. A set keyed by requestId proves at
  most one result entitlement, not at most one retained proposal copy.
  Required: separate unique-result cost and command-copy custody cost; duplicate
  admission coalesces against active/native/durable custody, not only waiters.

F3. Leadership/process change cannot reset Q. [Native-source reachability]
  Persist an unresolved suffix, replace the runtime/process or move leadership,
  reopen from L10; new ProposalQueue maps are empty while suffix entries can
  still apply. Initializing credits to the configured maximum over-admits.
  Required: reconstruct before admitting new work from one exact application
  boundary plus surviving suffix; count results already retained separately.
  A missing/unreadable retained record is a HOLD, not an empty inventory.

F4. A database-only counter misses pre-persistence ownership. [Source trace]
  Queue proposal A behind an async Ready send; A's encoded bytes already exist
  in the runtime tail. Count only durable suffix, admit B. A then enters core,
  and Ready may be deferred before persistence. The log query misses both
  pre-core and core-held bytes. L3/L4/L6/L7 show the gaps.
  Required: admission debit before accepting bounded pre-core custody, followed
  by one-owner transfer to core/Ready/log; no await between final gate and core
  creation without a reservation covering the interval.

F5. Forwarded MsgPropose bypasses a local-only gate. [Source trace]
  Outer partition says leader; queued turn drains a newer leader message;
  RawNode.propose forwards the original request. Receiver steps MsgPropose and
  appends its entries without running receiver port.propose. Alternatively
  inject a legitimate peer-forwarded proposal through the existing wire seam.
  Required: current-leader creation gate covers local and forwarded proposals.
  Followers receiving already-ordered Append must not silently drop committed
  work because an application-history slot is currently full. Replication
  custody and fresh request admission are different contracts.

F6. Raft defaults do not supply the missing bound. [Exact locked source]
  wrapper lib.rs:453-468 starts Config::default and sets applied/timing,
  max_size_per_msg and max_inflight, not max_uncommitted_size.
  crate:config.rs:121-122 sets both max_uncommitted_size and committed entries
  per Ready to NO_LIMIT. Even changing max_uncommitted_size would not prove Q:
  crate:raft.rs:126-128 allows at least one oversized entry, :1217 resets the
  counter on becoming leader, and raw_node.rs:457 reduces it while generating
  committed entries before application/result durability. It does not retain
  credits for old-term suffix or result history.

F7. Freeing on commit, ACK or caught proposal error is unsound. [Source trace]
  Persist/commit R; application transaction fails before result+applied commit.
  Caller gets failure/unknown; R remains owed on replay. Freeing its result
  entitlement permits a new R2 to consume the space R still needs.
  L8/L9 provide the correct rollback boundary. A late success cannot double
  release an entitlement, including after the old waiter has disappeared.

F8. Suffix discard must be an authoritative transfer. [Source trace]
  Old term has R at i; new leader replaces suffix from i while new requests
  are queued. Releasing by requestId before replacement commits risks early
  reuse; releasing after another copy remains misses R's future result.
  L7 has actual replacement, but no identity/cost delta. Runtime must distinguish
  copy identity (group/origin, index, term) from exact request identity; only
  a proved lost copy can be removed. Remote forwarding/other copies must remain
  accounted. Stale reconstruction may not overwrite a live newer projection.

F9. Applied duplicates and retired requests need allocation-free handling.
  Retain R result, append exact R again: no new result row (existing L9).
  Advance retirement frontier, then apply an old in-flight R: it must be
  HISTORY_RETIRED/no new authority/no new result row under the chosen history
  contract; its copy debit still ends only at application/discard. Advancing G
  alone cannot erase the still-queued/native/log copy or reassign its debit.
  A rejected current-version request cannot become fresh after retirement.

F10. Critical reserve alone does not prove reauthorization. [Proposed trace]
  HELD; fill all APPROVE result slots with validly admitted requests refused at
  application. Later the deterministic readiness predicate becomes true. A new
  APPROVE still needs a result slot. If RETIRE needs the same pool, neither can
  proceed. Reserving HOLD, settlement and APPROVE is insufficient without a
  retirement path whose own bounded result does not need that pool.

F11. A maintenance cell can hide an unbounded history. [Proposed trace]
  Allocate one cell keyed by (partition, origin, G), retire, increment G and
  allocate the next. It accumulates forever. Instead one fixed cell stores the
  current G and at most the latest exact retirement receipt; a monotonic frontier
  protects all older retired identities. Querying old unavailable receipt must
  say HISTORY_RETIRED, never NOT_COMMITTED. Overflow must HOLD without wrapping.

F12. Retirement needs self-capacity at every earlier stage. [Proposed trace]
  Normal waiters/runtime tail are full; maintenance result cell is empty but
  RETIRE never reaches the core. Or runtime maintenance custody is occupied by
  an unknown prior RETIRE while a new nonce creates a different request. A fixed
  result slot alone fixes neither. Use one canonical RETIRE identity per current
  G, coalesce exact retries through runtime-owned custody, and reserve a bounded
  path in the existing queue/runtime admission owners. Do not call raw Raft as
  a force bypass. Scheduled ticks, replication and recovery must also progress.

F13. Retiring refusals must not retire obligations. [Proposed trace]
  A result row is pinned because another owner still uses it as an obligation
  proof. Delete it merely to reopen -> lost settlement/recovery evidence; refuse
  all retirement -> HELD forever. The result owner must define which release
  outcomes are historical query answers versus authoritative facts still owned
  by release/TX/query. Only the former can be retired under G. If the selected
  authority layout cannot free saturated refusal results without deleting an
  obligation, nonstarvation remains BLOCKED. One PREPARED participant maximum
  does not bound all historical rows or the bytes of its decision manifest.

F14. Replaceable maintenance receipt has its own exactness edge. [Proposed trace]
  RETIRE(G) commits, caller loses answer, restart; replay must return retained
  exact receipt, not execute G+1. Later RETIRE(G+1) commits, overwriting last
  receipt; replay G now returns HISTORY_RETIRED without claiming noncommit.
  Never include a caller nonce or mutable retirement selection in RETIRE(G)
  unless its multiple-conflict outcomes have an explicit bounded home. A
  canonical command with one fixed policy avoids that particular allocation.

F15. Physical capacity and settlement still need their own owners. [Source+gap]
  Retiring SQL rows does not automatically reclaim SQLite/WAL or log bytes;
  L10 materializes all retained log entries. Each Ready/native/message copy also
  consumes memory. Transaction bytes carry a participant manifest without a
  proven complete settlement bound. None is covered by the old release-only
  arithmetic. Full disk, unreadable source or lost application provenance must
  remain explicit HOLD/repair conditions, not guessed budget margin or rollback
  of committed authority.

PROPOSED MINIMAL OWNER CONTRACT TO VET (NOT PRESENT IN SOURCE)

Semantic question: may this current-leader operation create another outstanding
command whose deterministic application might require a result slot?
Decision owner: runtime proposal admission, using a typed cost/class supplied
by the canonical application command owner and exact result-capacity facts from
the committed-result owner. The application owner alone determines the applied
result. ProposalQueue owns waiter lifetime only. Transport owns delivery only.
The runtime projection is derived custody, not a second outcome ledger.

Identity keys must remain distinct:
  - exact request: origin + partition + canonical request identity/bytes;
  - release state version: authority CAS, not history G or transactionEpoch;
  - history G: request retirement protection;
  - copy: native group/origin + real log index/term once assigned;
  - live projection: replica lifecycle incarnation + runtime generation;
  - transaction: TX1 immutable identity including transactionEpoch.
The command must not carry a submission-time guessed log index as authority.

Required new internal seams, under existing owners:
  A. Bounded synchronous pre-core custody acceptance, including a canonical
     request identity, size class, duplicate-copy policy and potential result
     cost; no slot can disappear merely because a client waiter expires.
  B. Current-leader creation enforcement after inbound drain/reconstruction,
     including forwarded proposals. Actual log position/term transfer comes
     from core/Ready, not from caller guesses. Pre-core to core ambiguity has
     a typed UNKNOWN custody state, never automatic credit reclamation.
  C. Durable suffix inventory/replacement delta owned by runtime/store, with
     a coherent applied boundary and reconstruction on open/leadership/recovery.
     Existing all-log read is input, not a ready-made bounded scanner.
  D. Atomic application reservation exchange: successful/refused request result,
     any release-state mutation, retirement protection and applied progress
     commit together. Projection refresh follows commit; rollback retains debt.
  E. Result-owner fixed maintenance cell and history policy, carried through the
     existing snapshot/application-image dependency. No new global ledger.
  F. Event-driven wake on applied progress, suffix replacement/reconstruction,
     result retirement or leadership change, coalesced under existing queues.
     runtime-owner.js:1293-1299 already emits applied progress; the other
     credit deltas/wakes are new contracts, not assumed current events.

Proposed fixed maintenance protocol to attack in the next design review:
  - Exactly one persistent cell for partition+origin contains history G and
    the last applied retirement receipt. Its bytes are preallocated in the
    logical accounting. One maintenance command custody slot is distinct from
    its persistent result cell and from ordinary result-history capacity.
  - RETIRE(G) has deterministic canonical identity derived from domain,
    partition, origin, protocol version and exact current G; no free nonce,
    wall time, mutable caller selection or replica-local predicate. A fixed
    policy advances G and retires the release-result owner's eligible history.
  - At apply, exact current G atomically advances to G+1, deletes only eligible
    history and replaces its own last receipt with actual applied position.
    It does not change release authority, decide TX COMMIT/ROLLBACK, or delete
    participant/coordinator obligations. If protected rows survive, their
    independent capacity remains charged; no claim of guaranteed freeing yet.
  - Exact duplicate of last retained retirement returns that receipt without
    allocation. Older unavailable request returns HISTORY_RETIRED. A future G
    is not admitted under the prior contract; committed future-generation bytes
    require the explicit protocol-invalid containment decision, not inventing
    a refusal that may become fresh later. Max G does not wrap.
  - To meet HELD/full-refusals -> retire -> APPROVE, applying RETIRE must free
    at least one required APPROVE outcome slot even with current release version
    unchanged. The next APPROVE is a NEW request explicitly captured at G+1;
    old APPROVE bytes remain retired. No uncertain retry is silently retagged.
  - Before asserting progress, prove maintenance can enter the existing queue,
    receive its native copy/result credits, persist and apply while HELD/full;
    prove settlement is not parked behind a resource it must free; and prove
    failed maintenance application preserves exact custody on restart.
  - A crash before the SQLite commit restores old G/history/receipt. A crash
    after commit restores all three new facts. Lost notification cannot produce
    a second retirement. Later receipt replacement must retain the monotonic
    anti-replay frontier in the same application image and applied boundary.

Nonstarvation is conditional on a usable quorum, writable application storage,
valid retained origin/protocol state and eventual runtime/application service.
It is not a promise to progress through a permanently failed disk or missing
application image. These conditions must be typed and observable. No serving
eligibility prerequisite may be added for the maintenance that restores it.

TYPED FAILURE EDGES REQUIRED BY THE NEW CONTRACT

The following are semantic classes to bind to real exported constants and
consumer classification in the subsequent implementation; they do not claim
new symbols already exist:
  - malformed/noncanonical/oversize: NOT_ADMITTED, terminal for original bytes;
  - no current leader/changed origin: existing leadership or identity refusal;
  - transient credit full: NOT_ADMITTED/backpressure under existing retry budget;
  - exact request already in custody: JOIN/OBSERVE, no new copy/result debit;
  - exact retained result: RECORDED_RESULT, no new allocation;
  - retired missing result: HISTORY_RETIRED, commit status unavailable;
  - future history: HISTORY_GENERATION_AHEAD before proposal, original bytes
    retained under the bounded retry owner; future committed bytes fail closed;
  - unreadable inventory, unknown live transfer or wrong recovery generation:
    runtime/application HOLD, never count zero;
  - known pre-core refusal/discard: release only that proved local custody;
  - possible post-core proposal or unknown answer: UNKNOWN, retain obligation;
  - deterministic applied refusal: exact durable refusal plus unchanged release
    state, atomic result reservation exchange;
  - environmental apply failure: rollback all state/result/applied movement,
    retain custody and use existing runtime recovery;
  - pinned capacity/no eligible retirement progress: explicit CAPACITY_PINNED
    owner blocker with original identities, not successful closure;
  - generation exhaustion: terminal protocol capacity HOLD without wrapping;
  - retry budget spent: typed loud stop with immutable request identity and
    unresolved custody, not cancellation of committed work.

CACHED-VIEW AUDIT

ProposalQueue, pendingWriteOutcomes and handoff WeakMaps are waiter/observation
views; deadline, leadership and promise completion invalidate them without
releasing native/result obligations. Runtime status/role is a projection; final
checks happen inside the generation-checked turn after inbound drain. A proposed
custody map must transfer exact live entries rather than blindly replace itself
from a stale scan. Durable log/application reads must share an exact boundary;
read failure never supplies an empty view. Retained result cache misses re-read
the result owner plus retirement frontier. Transport ACK cannot refresh credit
or clear an unknown request. Snapshot source-local serving flags are not inputs
to receiver credit initialization or replicated application effects.
