All findings and smallest corrections
------------------------------------

R1 — Name the projection to which C/Q and the envelope apply; follower backlog
is a distinct unresolved bound. Lines 51-84 and 98-139.

The prose assigns one partition/origin capacity and charges every surviving
unapplied occurrence, but gates new creation at the current leader. A majority
can apply RETIRE/APPROVE repeatedly while a lagging replica still retains older
generations as incoming messages, native/durable history or unapplied work.
These may be many DISTINCT canonical commands, not just multiple copies of the
leader's current pending set. Leader-side Q reuse after local application does
not prove a per-replica or cluster-wide unresolved-suffix Q ceiling.

Minimal proposed trace: A/B apply generation G, retire it and admit G+1; C is
behind. Repeat. A's current admission inventory remains within C/Q while C's
backlog spans more generations than that inventory. On C's later reconstruction
or promotion, counting its surviving suffix cannot simply pretend Q still fits.
Current source routes already separate these states: runtime-owner.js:1136-1188
owns local apply, :1691-1724 drains local inbound, :1753-1815 can retain inbound
while persistence is blocked, and durable-store.js:207-248 reads the local full
record. This is a source/protocol trace, not an executed native exhaustion test.

Smallest correction: label the formula as the active leader's logical admission
projection. Explicitly retain follower backlog/log/transport containment and
promotion from an over-profile inventory as an existing runtime/store/snapshot
owner blocker. Admission stays held until the exact suffix is reconciled and
drained or installed through the owned image path. No dropped committed entries,
invented capacity, or per-replica Q claim. A stronger cluster bound requires its
own flow-control/snapshot proof and must not be inferred from this arithmetic.

R2 — Admission fairness alone does not cover repeated retirement invalidation.
Lines 155-157,178-180 and 207-219.

The document correctly preserves the competing-refusal starvation trace. There
is also a retirement-specific trace because RETIRE always advances even when
no rows are eligible and may overtake a pre-core admitted request:
  RETIRE(G) -> recovery APPROVE captured/admitted at G+1 -> RETIRE(G+1) ordered
  before that APPROVE -> APPROVE later observes retired G+1 -> repeat.
The recovery request can receive fair admission every round and still never
reach authority. A RETIRE may already be queued before the approval's core
transfer; this trace does not require reversing existing committed log order.

Smallest correction: include this trace as an explicit remaining blocker.
The future continuation must establish fair ordered progress through application,
or another reviewed invariant that prevents maintenance repeatedly invalidating
the designated recovery attempt. Define the retirement producer/trigger and
bounded recovery continuity; do not claim that another priority queue or a
reserved APPROVE slot already supplies that guarantee. This can remain HOLD;
the current packet need not invent a durable queue to resolve it.

R3 — The normal class needs a closed command-kind mapping. Lines 75,98-109.

The prior DECISIONS.md:52 closes the release kinds to INIT/HOLD/APPROVE; this
packet adds RETIRE. The new table names Normal release requests but never maps
an actual canonical kind to its C128/Q32. Classification cannot be assessed
from a generic requirement to derive it from kind if that mapping is missing.

Smallest correction: provide the exact mapping, for example INIT to normal if
that is the intended selection, with any unused headroom explicitly inert.
HOLD refusals remain HOLD-class and APPROVE refusals APPROVE-class; do not
move a loser into a normal pool after application or admit unknown command
kinds under spare normal capacity. If a new ordinary release command is intended,
it needs an explicit owner contract rather than a new implicit producer.

R4 — Pin retirement bytes and avoid charging consensus progress as a release
request. Lines 26-29 and 143-150.

The retirement identity still uses variables domain and format. This is weaker
than the selected exact canonical release request and leaves different byte
encodings/format interpretations admissible in a supposedly content-bound
decision. Choose the literal hash domain (including separator), UTF-8 canonical
serialization, retirement cell format, inherited field bounds and the entry-key
namespace. The fixed cell must preserve its exact receipt after replay/restart.

Also narrow 'all new log-entry creation must consume ... credit' to profiled
application command creation. Consensus election no-ops and configuration
progress cannot require a release-result entitlement that only their progress
can free. Existing application-transaction-owner.js:11-16 expressly distinguishes
payload-bearing NORMAL proposals from empty leader entries/configuration.
Their own bounded native/storage accounting remains runtime-owned; no generic
capacity exemption or alternate authority is proposed by this correction.
