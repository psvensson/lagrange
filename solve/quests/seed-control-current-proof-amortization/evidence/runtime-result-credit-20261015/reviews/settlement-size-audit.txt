Actual bounds and findings
--------------------------
F1 — Local staging is bounded; its limit is not a sealed command or settlement
limit. Evidence: partition-participant-transaction-constants.js:133-140 sets
MAX_OPERATIONS=256 and MAX_BYTES=1,048,576. staging.js:165-195 measures the JSON
encoding of all staged operations and refuses REPLAY_BUDGET_EXCEEDED before
updating the session or acknowledging provisional success. It dry-runs inside a
rolled-back synchronous SQLite transaction; BEGIN/staging remain volatile and
leader-local. request.js:291-319 permits only one nonterminal participant per
partition, then opens a local session. request.js:347-388 seals operationsText,
validationText, identities and stamp into PREPARE, retaining sealed retry bytes.

Counterexample to using 1 MiB as a complete-message bound: a near-limit valid
operationsText is itself a JSON string inside PREPARE, with escaping, identity,
validation and execution-envelope fields added. Full serialization is larger.
operationsOf() and isPinnedParticipantCommand() do not independently enforce the
session count/byte bound (bytes.js:111-137,315-369). The probe accepts 257 operations
and an operationsText of 1,048,640 B. This is a parser/admission fidelity finding,
not a demonstrated native path bypass: ordinary session staging rejects those
operations before producing PREPARE. The complete new contract must specify a
bounded canonical wire profile at both new admission and deterministic apply.

F2 — The global manifest and DECISION have no owner-enforced participant-count
or encoded-byte bound in the inspected path. participant-manifest.js:5-23 accepts
canonical ordered unique pairs without count/size caps; participant-set.js:32-47
durably appends every admitted identity BEFORE participant BEGIN, and :62-87
iterates the requested set without a protocol count cap. The normal coordinator
can enlist an arbitrary finite set of available partitions subject to resources
and its existing time budget. That time budget is not a numeric encoding bound.
bytes.js:140-196 validates and canonicalizes the full participants array, without
a cap. DECISION carries the whole decisionText to each participant (:283-293).

Minimal size schedule: one transaction enlists N distinct partitions, stages a
small operation on each, freezes N, prepares each once, then records a decision
with N [participantId, preparedDigest] pairs. Each partition still has at most
one PREPARED row, but each receives O(N) decision bytes and the whole fan-out is
O(N^2) payload bytes before transport copies. The probe proves grammar acceptance
through N=4096, not physical availability of 4096 partitions or a native run.
No finite N ceiling was established from the actual query/participant owners.

F3 — Several canonical-reader string fields are syntactically unbounded, and a
digest label is not a hash-shape validator. bytes.js:87-96 checks nonempty IDs,
safe-integer epoch and derived participantId; :140-149 accepts any nonempty
preparedDigest for COMMIT. execution-envelope.js:58-66 checks four nonempty
strings, not their byte lengths. The probe accepts a 65,536-B partitionId and a
65,536-B preparedDigest. These are parser-boundary examples, NOT claims the
normal producer emits them. Normal transaction identity is already stronger:
distributed-transaction-identity.js:1-36 mints 128 random bits as 32 lowercase hex,
and distributed-transaction-schema-enforcement.js:24-42,88-104 enforces this at
coordinator INSERT with safe-integer epoch/deadline. The same schema only requires
nonempty sessionId. Normal PREPARE produces a real SHA256 digest. Preserve those
actual producer constraints; specify independent byte caps where a complete
wire/custody claim depends on them. Changing the accepted grammar is a new owner
contract and needs a retained-obligation policy, not an undocumented restriction.

F4 — One active obligation does not bound retained history. The participant
schema retains operations_text even after UPDATE_DECIDED (constants.js:174-277;
especially :270-277). No DELETE/retirement statement exists in that owner.
apply.js:400-409 records one statement outcome per committed operation, then
:433-441 retains the terminal participant row while releasing its reservation.
Rollback also keeps its terminal row (:445-459). Terminal replay reads those
rows/results (:462-467). The inspected Q persistence owner inserts/updates
sql_transactions, sql_transaction_participants and sql_write_operations; no
owned durable retirement path was found. Decision-protocol.js:91-96 removes
volatile workflow state, not durable history. The 4096 limit in commit-point.js
:28-31,86-117 is only the volatile per-session last-ended-transaction map and
correctly returns unknown after eviction. It bounds none of these SQL tables.

Minimal reachable accumulation: T1 BEGIN -> stage one operation -> durable
PREPARE -> authoritative decision -> terminal; then T2 follows the same path on
the same partition. Repeat serially. This obeys one-active-participant and every
local staging limit while accumulating terminal participant rows, operation
outcomes on COMMIT and coordinator history. This is a source-backed reachable
schedule, consistent with earlier native history evidence; no new native run was
performed. Existing comments promising outcome compaction with a future
snapshot/log-bound quest (statement-outcome-constants.js:18-21) are not an
implemented retirement proof and conflict with any claim the current checkpoint
already preserves an application image. Carry the existing snapshot dependency.

F5 — The operation count is not a bound on application data, CDC obligations,
SQLite pages/WAL or snapshot payload. apply.js:397-441 executes carried SQL,
records outcome rows and captures CDC. A single accepted SQL statement can affect
many existing rows; the operation-text bound constrains input, not every effect.
statement-outcome.js:137-145 stores failure message and owner_result_text without
a local byte truncation policy; their exact producers must be included in any
new outcome bound. The successful TX1 operation result itself is the pair
{changes,lastInsertRowid} (statement-outcome-constants.js:144-149), not arbitrary
user result rows. Do not inflate that narrow result shape into a database-size
bound or claim every error/result payload is already bounded. CDC ACK limits of
256 events, 2 outstanding batches and 64 KiB (partition-cdc-obligation-constants.js
:60-63) bound that ACK lane, not total transaction effects or durable history.

F6 — Serialization is not finite request custody. statement.js:22-33 chains a
Promise per transaction operation in a session FIFO and imposes no queue count
or byte cap; independent sessions are independent queues. The recovery sweep's
synchronous in-flight gate (recovery.js:204-226) prevents duplicate sweeps, not
all requests, all replicas, all retained obligations or unapplied Raft entries.
Neither this FIFO nor P's one-nonterminal rule proves a durable global Q bound.
Minimal source schedule: callers enqueue K distinct operations on one session
while its first operation awaits a dependency; all K tails exist before progress.
This schedule is not a demonstrated native exhaustion failure. It shows why
finite admission/custody must be enforced before asynchronous retention and
reconstructed from durable state plus actual retained suffix after leadership
change, rather than inferred from a process-local map.

F7 — Preserve D3's phase distinction; do not continuously require drain after
grant. pause.js:218-232 invalidates an OPEN grant on term, leader, configuration,
membership generation, runtime generation or lifecycle incarnation change.
Staging, PREPARED rows and proposal/pending counts are deliberately absent.
:252-262 returns idempotent RESUMED for the same still-current OPEN release.
The CLOSED->OPEN path :264-280 checks releaseCensusDefect, then synchronously
rechecks lifecycle/leadership. release-contract.js:116-155 requires no local
staging/PREPARED/pending proposals and applied=commit=last at that grant boundary.

Counterexample to a proposed continuous-drain D3 rule: OPEN -> a legitimately
admitted BEGIN/stage -> drain becomes false -> D3 closes -> first PREPARE loses
permission -> reopening requires the staging to disappear. This would make normal
admitted work revoke its own authorization. It is NOT a current native bug;
the current invalidator correctly separates transition eligibility from ongoing
grant validity. Future immutable release binding, actual-prefix D2 enforcement
and current D3 generation validity must preserve this phase distinction. New
admission HOLD must still allow exact durable replay and authoritative settlement.

Proposed owner contract inputs and admission points (new, not implemented)
------------------------------------------------------------------------
1. Q creates a versioned immutable closure requirement from its actual canonical
   transaction/manifest/decision encoders: transactionId, transactionEpoch,
   profile version, exact expected manifest bytes/digest, participant count,
   maximum encoded COMMIT and ROLLBACK delivery bytes for that manifest, and its
   own required retained coordinator/decision/result records and byte budget.
   It must reserve initial durable history before acknowledging coordinator
   BEGIN, and incremental eventual closure before OPEN-manifest CAS admits each
   participant. The manifest is already an obligation before PREPARE; reserving
   only at PREPARE is too late. Freeze retains the exact full manifest/profile.
   Existing CAS/readback remains authoritative (transaction-set-methods.js:32-63).

2. P creates its requirement from the local sealed PREPARE and owner-validated Q
   profile, not a caller-supplied boolean priority: transaction/participant/epoch,
   exact preparedDigest, release admission binding (the separate proposed repair),
   operations count/text bytes, complete encoded command bytes, maximum terminal
   decision/result delivery and per-operation outcome count/bytes. Any information
   not currently carried from Q to P is an explicit NEW byte-field/interaction
   contract, never presumed present. The first PREPARE path must validate and
   reserve before proposal/ack; deterministic application must enforce the same
   replicated profile/count/byte rules at the actual committed prefix. Runtime
   local transport pressure cannot alter the replicated terminal result.
   A matched existing durable PREPARE/terminal replay takes the existing identity
   validation/replay path before new admission rules. Preserve the accepted
   transactionEpoch replay finding as an independent repair requirement.

3. R accepts a typed immutable requirement from Q/P/O, deduplicated by the exact
   transaction/participant/request plus content digest. Claim happens before
   asynchronous custody; actual retained command bytes and copies remain charged
   through unknown outcome, retry and leadership change. Timeout/demotion is not
   a release event. Atomic committed application converts the relevant claim
   into its retained outcome/remaining obligation; authoritative retirement or
   proved non-admission releases it. This is an interface requirement, not a
   claim current process maps implement it. Runtime needs one resource key for
   the contended partition/runtime budget, not one independent quota per session.

4. Recovery asks Q/P/O for retained obligations at their authoritative boundary,
   reconstructs actual suffix custody, and treats unavailable/incomplete authority
   as held debt. Do not copy source-local volatile credits in a snapshot. Q alone
   reads/writes the recorded global decision; R/release cannot choose ROLLBACK to
   reduce size. One exact decision replay must share its original custody/result,
   not allocate another authoritative annotation.

5. Proposed typed failures need final owner vocabulary before implementation:
   NEW_ADMISSION_CAPACITY_HELD (transient, existing retry/budget),
   CANONICAL_PROFILE_UNSUPPORTED (hard for new work only),
   RETAINED_SETTLEMENT_SIZE_UNAVAILABLE (held, authority unreadable), and
   RETAINED_SETTLEMENT_EXCEEDS_AVAILABLE_CUSTODY (explicit operator/design blocker,
   obligation preserved). These names are proposals, not current exports.
   Reasons carry the actual held partition, transaction, epoch, digest, measured
   requirement and limiting owner; no generic empty/success interpretation.

Already acknowledged larger obligations
---------------------------------------
Do not apply a new 64-participant or wire-size ceiling to an existing PREPARED
row or recorded decision. Q must enumerate the actual retained manifest/decision
and P the actual participant rows; measure the complete exact settlement encodings
and retained results. Account those obligations in TX/query-owned settlement
custody while ordinary new obligation admission remains backpressured. This is
separate from release-request history/credits and must not consume the reserved
HOLD/reauthorization resources. Admission policy and settlement delivery remain
different paths through the same trusted semantic owners.

For an actual finite retained set that fits the supported transport/native/storage
budgets, measured custody plus bounded concurrent delivery can be finite. That
conditional observation does not establish a universal numeric reserve for the
present unbounded grammar. If even one exact retained decision cannot fit, a
single 'critical slot' does not solve the problem. Report the measured requirement
and explicit blocker; retain the decision/obligation. Do not split or truncate
the manifest, replace a recorded decision, reject terminal replay, borrow release
budget, claim PAUSE rolls back work or invent a second persistence path. A new
streaming/reference decision protocol would be a Q/P owner-contract change
requiring separate review; it is not proposed as a hidden workaround here.

Retirement remains necessary even with bounded new requests: accepted serial
transactions otherwise grow history indefinitely (F4). Retiring Q/P/O data needs
one owned proof/frontier preserving exact outcomes for the retained interval and
typed historical-unavailable/retired semantics outside it; absence cannot mean
NOT_COMMITTED. Pinned undecided/prepared obligations retain exact data. Existing
enforcement and recovery prerequisites must survive in the application image at
one applied boundary. Source-level row counts and raw JSON bytes do not bound
SQLite file/WAL/snapshot allocation. These are concrete unresolved dependencies.
