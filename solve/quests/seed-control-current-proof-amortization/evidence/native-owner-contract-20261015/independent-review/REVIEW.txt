3. Findings with minimal traces

F1 — BLOCKER: the proposed settlement classification assumes an owner/state that TX1 does not have.
Addendum:142-150,175-180 requires a replicated staging row before a pre-HOLD PREPARE can be settlement. Model:624-641 implements a committed BEGIN creating that row. Actual BEGIN at request.js:291-319 opens a local WeakMap session; ACTIVE/PREPARING are not durable participant rows. First replicated PREPARE carries operations, validation, immutable digest and a stable participant prepare entryId (bytes.js:261-271), but no release admissionEpoch. A follower stages nothing and learns the transaction from PREPARE.
Minimal owner trace: leader local BEGIN(t) + staged SQL -> sealed/pending PREPARE(t) -> committed HOLD -> first PREPARE applies on a follower with no local or replicated staging row. The proposed table cannot call this unchanged existing settlement: it either refuses work that the old owner could prepare, or requires a new replicated BEGIN protocol. Previously durable PREPARED/terminal decisions are a different case and must remain settleable. Which first PREPARE may cross a fence requires the explicit transaction/release owner decision; a local staging boolean cannot settle it deterministically.
Additional mismatch: revision 2:54 names a ".withReleaseColumns DDL precedent", but no such symbol exists in src. The store currently owns participant rows and the write-generation singleton, not an existing per-release-epoch ledger. The schema/retention/outcome extension must be specified honestly under that owner.

F2 — BLOCKER: T5's spent-epoch and D3 rules contradict its own definitions.
Addendum:119-128 defines spent(E) iff E <= L, then says invalid identity leaves L unchanged, creates no row, yet consumes E.
Minimal model trace: invalid DECISION(E1) -> L=0, no row -> valid DECISION(E1, fresh census) -> APPROVED, L=1. E1 was reused.
Second trace: APPROVED1 -> invalid DECISION2 -> gate remains OPEN from row1, although T5's D3 cell says CLOSED.
The latter is not a recommendation to let invalid traffic revoke legitimate authority. Preserve a single epoch/current-disposition authority and explicitly resolve the contradiction. A separate invalid-epoch authority would not be the smallest correction.

F3 — BLOCKER: stale first PREPARE silently adopts a new authorization.
Addendum T7's general immutable binding rule conflicts with case (d), which permits unstaged PREPARE whenever current admission is open. Model:654-677 never checks PREPARE.admissionEpoch.
Minimal trace: APPROVED1 -> HOLD2 -> APPROVED3 -> PREPARE(t, admissionEpoch=1, no staged row) -> PREPARED with stagedEpoch=3. Built-in D-no-silent-adoption remains green because its check is only on writes.
This is distinct from settling a previously durable PREPARED row. The first-PREPARE decision must use the chosen immutable binding and deterministic prior state without reclassifying existing durable decisions.

F4 — BLOCKER: D4 reports command intent as the decided result; refused request replay is not immutable.
Model:737-764 reads disposition from entry.cmd.disposition rather than the applied result. "COMMITTED" can correctly describe D1 while the reported APPROVED value is still wrong.
Minimal trace: request a APPROVED(E1) wins -> distinct request b APPROVED(E1) is EPOCH_CONFLICT -> d4Read(b) returns COMMITTED, disposition APPROVED, applied=true.
Also: APPROVED1 -> HOLD2 -> DECISION3 carrying the pre-HOLD census -> D2 census_stale refusal -> D4 reports APPROVED.
Exact refused-request trace: a wins E1; b loses E1, annotated winner E1; HOLD2; reapply the exact b entry -> another durable annotation naming winner E2/HOLD. One replica now has extra durable state for the same prefix; A-deterministic-effects fires. The model's reapply API is a replay abstraction, not proof that native applies a log index twice.
annotateConflict (312-314) names current authority, without the winning request's entryId/bytes. Distinguish the immutable outcome for the queried request, the retained winner at its contested epoch, and current serving authority. Unknown/retired history must remain typed unavailable, never invented. Successful rows alone cannot provide retry outcomes for refused commands.

F5 — BLOCKER to the claimed authorization proof: T6 is not implemented, and the census oracle can check the wrong prefix.
Addendum:129 and corrected draft require HOLD's census binding. Model:459-514 accepts HOLD without any census; the official runner constructs such HOLDs.
Minimal trace: APPROVED1 -> HOLD(E2,S1,no census) -> HOLD row2 is accepted.
Separately, submit assigns index = log.length+1 before commitment (178-190), and commit never updates it. The census check reconstructs state from entry.index-1, not the actual applying replica's pre-state (402).
Minimal trace: APPROVED1; submit DECISION2 with census(prefix1), reserving index2; commit/apply BEGIN(t) as actual log2; commit the pending decision at actual log3, still index2 -> it accepts the stale census despite the changed obligation set. The check and its invariant share the same incorrect prefix calculation.
These are model fidelity defects, not a claim that raft-rs assigns positions this way. Native supplies the committed position. Corrected D0/census inputs still need an explicit mapping to committed membership/configuration/origin/schema/transaction state; the current local census cannot simply be consulted in D2.

F6 — BLOCKER to the unconditional resource claim: retention lacks a capacity case when obligations pin all old rows.
Addendum:232-250 promises bound 4, never retire current/unresolved rows, and unlimited decisions/HOLDs. Model:321-337 leaves overflow when nothing can retire.
Minimal model trace: for e=1..4, APPROVED(e) then BEGIN(t_e,e); HOLD5 -> all four old rows pinned, current row5 protected, retained rows=5. Built-in checks stay green; fixed scenario G has no unresolved obligations.
This is NOT a demonstrated native schedule: native TX1 admits one nonterminal participant per partition, and release D0 requires drain. Prove and encode the actual maximum pinned population and reserved closure capacity, or specify bounded pressure at the existing owner. Do not invent a new queue or evict obligations. Independently, APPROVED1 plus eight conflicting requests leaves one release row and eight durable annotations; the claimed row bound does not bound annotations/request outcomes by count or bytes. Proof-only trace/log arrays are not counted as production leaks.

F7 — MODEL FIDELITY: modeled transaction settlement is weaker than the native owner.
APPROVED1 -> BEGIN(t) -> PREPARE(t) -> COMMIT(t) -> ROLLBACK(t) overwrites the terminal model decision (680-688). Native apply.js:478-509 retains the first terminal decision, validates digest/binding, refuses conflicting decisions and rejects absent COMMIT. The query settlement owner likewise follows the recorded winner. "Existing applier rules unchanged" is not demonstrated by this model.
Do not repair native transaction behavior to match this abstraction. Its obligations/census/replay oracle needs a faithful abstraction of the existing terminal rules.

F8 — MODEL FIDELITY: D3 never compares the command's identity with current identity.
A structurally nonempty foreign partition identity is accepted in a release decision and D3 opens. applyGate checks identityValid(CURRENT_IDENTITY), not equality with the row's binding. The real release contract verifies releaseId hashing and partition/configuration/build/member facts (release-contract.js:56-69,122-191). Membership changes being out of scope does not validate wrong static identity. Reestablishing a restarted local incarnation is also not modeled; no recovery-liveness conclusion follows.
