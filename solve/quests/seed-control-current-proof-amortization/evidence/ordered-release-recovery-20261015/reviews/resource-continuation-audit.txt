Consumed surfaces and single ownership
--------------------------------------
The result/application owner records the exact retirement receipt, pending
handoff bytes/reservations, deterministic disposition, release state and applied
position. Runtime owns new-entry admission, physical occurrence custody,
ordered execution, reconstruction and whether a replica can create new work.
Durable store owns the exact retained/replaced suffix. ReplicaHandler's existing
release continuation owns only discovering and redriving the exact obligation.
TrackedServiceRegistry and operation-port events are wakes, not permission.
Query and participant/TX1 owners retain global decision and settlement authority.
Snapshot/application owners retain image provenance and atomic restore.

Keep distinct: origin; partition; exact K/content digest; history G; release
version; retirement receipt; pending handoff; physical log occurrence O; actual
applied boundary; runtime/service incarnation; transactionId/transactionEpoch.
Clearing a volatile pending map, caller waiter, transport ACK or old occurrence
cannot clear the durable handoff or choose a transaction decision.

RC1. A reserved opportunity is not bounded runtime intake or service.
runtime-owner.js:961-986 serializes by chaining a Promise tail with no count or
byte cap. :1945-1982 validates inbound shape then pushes an envelope with no
count/byte cap. :1691-1742 drains inbound until empty BEFORE executing the
queued command. sendMessages may await peer delivery (peer-delivery.js:88-127;
runtime-owner.js:1143-1173), so more inbound can arrive during that drain.

Trace: durable handoff K exists; its command is queued; each awaited inbound
Ready send permits another admitted envelope; the drain need not become empty.
K has its reserved entitlement but no service. Independently, many local callers
can already have retained bytes behind the Promise tail. The draft correctly
calls its scheduler NEW; its concrete contract must also bound pre-tail intake,
inbound count AND bytes, per-turn service and the handoff's eventual turn.
An existing 64 Ready-cycle bound (:1191-1199; group-constants.js:32) is not a
command/entry-byte cap or fair scheduler. Do not raise it as the repair.

RC2. A leader admission profile does not bound a lagging replica's backlog.
Existing accepted entries arrive through Append, are stepped by :1709 and
persisted by durable-store.js:404-413. They are prior history, not a new request
for local release entitlement. A fast leader can apply, retire history and
admit subsequent bounded batches while a follower's applied prefix lags. The
follower can later receive an arbitrary finite number of those batches without
violating the leader's instantaneous admission profile. On restart or later
leadership, that replica can hold more pending occurrences than the profile.

Required distinction: bounded receiver VOLATILE intake may defer/not accept
additional retransmittable envelopes; it must not acknowledge application,
discard accepted application history, refuse replay on current result pressure,
or reject a complete committed prefix because its aggregate size exceeds the
fresh-admission limit. Runtime can hold NEW creation while counting retained
over-profile debt, yet must permit owned consensus, ordered apply and catch-up
progress. Resource debt is not proof of corrupt/lost history and must not be
mapped to holdForReseed, which stops ticks (operation-port.js:331-350).

RC9. Cadence alone is not a retry storm ceiling, and every scheduler stop must
have a consequence. enqueue :140-147 coalesces one due timestamp per hosted

MAX_CONCURRENT_ATTEMPTS limits only running background tasks. report :159-172
suppresses an unchanged signature for 30000ms but changing signatures can log
more. Pending handoff must join one physical custody/result claim and events
must coalesce into bounded work, not create a new request or another timer loop.

arm :116-137 reports timer-registration failure and clears its volatile pending
map; it does not leave a registered-but-dead timer. For the NEW durable handoff
that failure must remain a visible scheduled-work-unavailable condition whose
owner recovery/re-registration/startup event rereads the cell; it cannot be
reported as discharged. shutdown, unhosted and replaced-service exits are
lifecycle exits only. Unknown/malformed/unreadable cell state stays an explicit
HOLD. Do not encode it as empty pending and rely on a nonexistent retry.

RC10. Pending-handoff reservation needs a separate physical-accounting rule.
The draft correctly adds exact K bytes to the fixed cell and preserves the
retirement receipt after K completes. It must charge those bytes while they
coexist with outer RETIRE_FOR_APPROVE bytes, K pre-core/native/Ready/suffix
copies, and its future result. A reserved future occurrence is not an actual
log occurrence; transfer of that reserved allowance into an admitted physical
copy must be atomic with respect to the serialized runtime view. Exact pending
retries cannot claim another entitlement; unexpected duplicates still cost
physical bytes. Authoritative suffix discard refunds only the discarded
occurrence and retains the cell's obligation to offer exact K again. A local
miss or stale reconstructed view cannot override newer live custody.
Current store.persistReady/appendEntries (:404-443) exposes no typed occurrence
replacement delta; current application transaction (:51-99) is the correct
atomic state/result/applied boundary, with afterCommit only a derived wake.

RC11. Retained TX/query obligations and snapshot dependencies remain separate.
Release sizing cannot reject larger acknowledged DECISION bytes or refuse
settlement/replay to make its Q fit. Preserve the previous settlement audit:
local staging is 256 operations/1MiB but does not bound full PREPARE, global
DECISION or terminal history. Query keeps decision/manifest/discharge custody;
P keeps prepared rows/terminal replay; release only consumes the outcomes.
If measured retained settlement cannot fit its supported path, retain it and
name the exact owner/capacity blocker. Do not borrow or spend the handoff's
closure opportunity to conceal unbounded TX grammar, and do not block settlement
on D3 OPEN. Application image/native import remains the existing snapshot
owner's dependency, not a way to forget backlog without proving its effects.

Smallest bounded source-backed interface extension
-------------------------------------------------
These are semantic signatures to review, NOT present exports or production
authorization. They stay inside the existing runtime/store/result/release
owners and operation-port boundary. No raw Raft object, new queue service,
permit service or alternate workflow algorithm is proposed.

I1. Result/application owner: readReleaseContinuation(service identity,
    application boundary) -> PENDING{origin,G,K,exactBytes,charges,createdAtActual
    Position}, NONE{origin,G,actualAppliedPosition}, or UNAVAILABLE/UNSUPPORTED.
    Receipt and current handoff are separate. Reading NONE authorizes no new
    request until runtime proves predecessor-prefix/custody reconciliation.
    Read current owned storage, not a CDC projection or stale build/census.

I2. Runtime: claimNewCreation(exact encoded requirement, current incarnation)
    -> JOIN, admitted ticket, retained result, or NOT_ADMITTED typed reason.
    Claim count/bytes and result entitlement BEFORE Promise-tail retention.
    Gate forwarded MsgPropose at the current leader too; Append is replication
    custody, not new client admission. Public callers cannot self-select the
    recovery class. A validated pending cell identifies exactly one K eligible
    for the protected opportunity. Old-origin or unknown inventory stays held.

I3. Runtime/transport: acceptInbound(envelope) -> accepted bounded volatile
    custody or typed not-accepted/retryable delivery. Bound aggregate count and
    bytes before retaining/cloning; count message/entry encoding expansion.
    Rejected volatile Append must remain retransmittable by Raft; no ACK/result
    may falsely certify application. Already retained/committed bytes are not
    deleted when intake is full. Give replication/ticks/config/settlement and
    the eligible handoff bounded service in the same serialized owner.

I4. Runtime/store: readCustodyWindow(expected origin/application frontier,
    cursor, count/byte budget) -> exact bounded occurrences, next cursor,
    COMPLETE or typed invalidated/unavailable/oversized obligation.
    Read actual positions and classify canonical bytes, including duplicates.
    Store suffix replacement returns an exact committed replacement delta.
    Reconcile slices in runtime serialization; a changed prefix/generation or
    newer live transfer invalidates/reconciles a scan rather than clobbering it.
    The current whole-record reader and native constructor do not implement
    this. Metadata-only length/count preflight can detect a too-large record
    before materializing payload, but is not a supported bounded restore by
    itself. One oversized retained entry needs its existing owner's explicit
    policy; it must not be silently omitted to satisfy a page size.

I5. Runtime: serviceOwnedWork(bound current generation, bounded count/bytes
    per slice) advances ordered predecessor apply/inbound/consensus and offers
    pending K. It must not require complete inbound emptiness as the only
    chance to run K, nor skip committed prefix entries to run K early. After a
    bounded accepted batch, the same owner schedules the next slice; clocks
    and lifecycle fences remain unchanged. Fixed admission priority without
    this service rule is insufficient. Native Ready batching/restoration is
    an explicit missing owner capability where current arrays exceed the
    selected window. No numeric window is justified by this source-only audit.

I6. Existing release continuation: reconcile partition -> validate current
    hosted lifecycle and runtime availability -> read pending FIRST -> if
    pending, offer exact K through runtime and observe its existing result;
    if none AND inventory reconciled, only then evaluate current ordinary
    build/origin/census/new-release intent. Failure to read/drive never clears
    durable pending. Actual apply, handoff-state publication, current service
    registration, reconstruction and startup all enqueue the same owner key.
    Extend the existing relay to expose coalesced applied-progress wakes; do
    not turn a request-lifetime observer into a second recovery owner. Preserve
    per-partition serialization and bounded attempt lifetime under the existing
    deadline handoff, independently of the durable obligation's longer life.

I7. Over-profile runtime mode: hold NEW creation, preserve counted actual debt,
    allow ordered replay/required consensus/owned closure and measured TX/query
    settlement. A later applied/retired/discarded frontier or accepted owner
    snapshot can permit a fresh inventory and reopen only creation capacity.
    Do not reuse membership participation, history-loss reseed or D3 permission
    as a quota bit. Those facts have different owners and consequences.

This is a narrow custody/continuation extension. It does not set a total database
quota, alter global transaction decisions, redesign snapshot storage or claim
current source already meets the proposed bounds.
