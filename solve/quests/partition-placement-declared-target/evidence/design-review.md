## Canonical runtime target

1. `replication-target-authority.js` remains the sole decoder of an observed persisted partition declaration. `getPolicyForPartition` must read that partition, decode it, obtain usable table policy, and return a fresh policy with `targetReplicaCount` from that answer. Do not mutate cached table policy. The existing cache/gateway seam is an observation, not a new linearizable-read assertion.
2. `targetReplicaCount` is the single planner policy field. Message-group and runtime-service owners already produce it. Remove the partition `replicaCount` alias and fallback-three chain from `MovePlanner.calculateTargetState` (move-planner.js:280) and have it call the existing `getPolicyTargetReplicaCount` reader (state-methods:163). That reader accepts the canonical field only, requires a safe integer, permits zero only for runtime-service's existing zero-target contract, and refuses unavailable/invalid targets. No numeric coercion, flooring, alternate field, availability-derived target, or default target is allowed at this boundary.
3. Both coordinator target readers (rebalance-coordinator-topology-guard-methods.js:317 and :348) consume that canonical field only. Missing service, missing policy, malformed target, or policy error cannot become RF3. ADD/REPLACE must enter the existing named blocked-admission state/reason before either recovery-cure exception or target-count permission. Priority-surplus REMOVE retains its existing target-unavailable denial. Restore a valid target and both decisions must recover normally.
4. The partition branch of any retained count facade must agree with the canonical target. In particular, `calculateTargetReplicaCount` (state-methods:195) currently clamps/steps using default min3/max7 and odd adjustment; its production references are the exposed wrapper/applyPolicy wrapper, while direct uses are tests. Either remove that unused alternate partition calculation or delegate its partition result to the canonical reader. Do not report row RF1 as RF3 or a valid row RF9 as RF7. This is a partition consistency requirement, not a redesign of the non-partition placement strategies. Desired target, actionable available-node count, and REMOVE safety minimum remain distinct quantities.

## Table policy has no replication-target setter

No existing production owner was found that turns table-policy replicaCount changes into partition target mutations. The concrete partition row writers are seed creation, initial application partition creation, and split/merge child creation. Split/merge inherits the decoded parent declaration. `updateTablePolicy` writes only tables.table_policies/updated_at and emits policyUpdated; no production event consumer rewrites partitions.replica_count. Creating such a multi-partition reconfiguration owner is outside this repair.

Therefore:

- Remove replicaCount from DEFAULT_TABLE_POLICY, configured table-policy default resolution, table-policy output and its unused defaultReplicaCount instance field. Keep the legitimate `partition.defaultReplicaCount` creation configuration and the existing row producers unchanged.
- One shared table-policy request validator must explicitly reject replicaCount requests before mutation. Use a named unsupported/refusal result, not successful inert persistence. The same rule applies to a table-policy targetReplicaCount request: that field belongs to the resolved partition policy, not stored table policy. Do not add a new accepted alias.
- Reuse that rule at updateTablePolicy and CREATE's `resolveCreateTablePolicy` before metadata writes. The SQL parser currently emits only splitStorageThreshold, but the owner accepts AST tablePolicy objects; that seam must not silently accept an ignored target request. Preserve the typed code through the CREATE caller. AdminOwnerOperations must map the terminal unsupported request to its existing REFUSED channel with an explicit HTTP status, not generic 500 or retryable owner_not_ready.
- Remove the unused `getReplicationSettings(tableId)` API rather than return a second target. Remove the unused `setTablePolicy` wrapper or reduce to the sole meaningful request API without a default-expansion path that recreates unsupported fields. Source search found neither method called in production; their tests must be reconciled to actual capabilities, not used to preserve an inert API.
- Keep valid minReplicaCount/maxReplicaCount, thresholds, and placement constraints as table policy. A default value for an omitted field of a valid, observed table policy is an authored policy default; it is not evidence that an absent table or failed read exists. Validation must no longer compare a fictitious default table target against min/max. Minimum safety may restrict a REMOVE; it must not overwrite the partition's target.
- Existing stored table-policy target fields must have an explicit disposition: refuse them as unsupported/unusable through the canonical read error, rather than silently ignore them while returning apparent success. Do not automatically rewrite durable policy rows in this read repair. The revision must document this data prerequisite; any needed migration requires its own real mutation owner and evidence. Fresh-state formation creates empty table-policy objects and does not require a compatibility interpretation.
- Update policy tests that used replicaCount merely as an arbitrary mutable field to an actually supported field while preserving their CAS, stale-base, cache, and unrelated-threshold assertions. Preserve the actual public split/merge threshold update capability and its integration tests.

## One unavailable-policy route

All unavailable policy in this interaction must remain unavailable. A missing partition, undeclared target, missing table row, malformed stored policy, missing policy owner, invalid safety minimum, or failed read must never be substituted with a policy default, empty object, cached-absence grant, or hard-coded minimum three. Normalize the read failure at the existing policy boundary to the named owned refusal, retaining cause/reason and `deferRetry:true`. Terminal unsupported mutation requests remain terminal and must not carry this retry marker.

`getTablePolicy` currently returns defaults for an absent table (service:216); `getPolicyForPartition` does so for an absent partition (:261); `getCriticalMinReplicaCount` returns three for missing service, malformed values, or any exception (priority-publication-safety-rows.js:275); split/merge getTablePolicy returns `{}` without its owner (core-methods:154). These are the concrete paths to remove or route to the one refusal. A valid observed sparse policy may still inherit its declared non-target defaults. Cache hits must not turn an explicitly absent/unavailable current row into a successful policy answer.

The safety reader must require a valid positive integer minimum, not Number coercion plus Math.floor. Preserve the exact valid minimum, including five: the universal REMOVE SIMPLE_FLOOR uses that value directly. Do not replace it with majority, target RF, or a lower fallback. Existing safety failures are not permission to deliver or mark the operation failed.

The existing liveness owners are sufficient. checkRebalance catches retryable failures and schedules its existing queue/timer; a bare new code without deferRetry would skip cadence. Operation owner execution catches the safety throw and calls deferTransitionRetry, retaining the operation and its owner key. Split/merge records a failed evaluation while its periodic owner remains live. No new timer, supervisor, deadline, or retry loop belongs in this change.
