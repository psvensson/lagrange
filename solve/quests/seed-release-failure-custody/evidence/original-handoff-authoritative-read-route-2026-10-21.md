## Exact dependency chain

The seed plan acquires the bridge SQL engine before release and registration (`src/bootstrap/pipeline/seed-startup-plan.js:34-46`). The bridge attaches the real router, cache, partition-services provider, optional topology snapshot owner and optional readiness owner; migration auto-wire and distributed transaction recovery stay off (`src/bootstrap/owners/seed-runtime-bridge-owner.js:46-66`). That is an existing early dependency, not proof any query can yet be delivered.

The normal gateway builds the frozen read-authority token (`src/control-plane/control-plane-system-table-gateway-read-dispatch.js:66-88`; `control-plane-system-table-gateway-read-contracts.js:298-322`). The MG read must reach this ingress, preserve OWNER_RPC_REQUIRED and REQUIRED leader mode, and must not hand-construct the downstream token. CDC selects `INITIAL_PARTITION_IDS[tableName]`, forwards the token and defaults to CONTROL_PLANE_RECOVERY_ELIGIBLE (`src/cdc/cdc-integration-service-owner-rpc-read-execution.js:356-431`). Thus reading either MESSAGE_GROUPS or SERVICES needs the exact system partition for that table, not a message-group handler serving SQL.

The query executor then needs these independent facts:

| Fact | Current consumer and refusal |

| Partition service candidate | `src/query/query-executor-partition-routing-snapshot.js:171-215` obtains partition-type SERVICES rows from routing overlay and system cache. No rows means no candidate, even if an initialized native partition exists in the provider map. |
| ACTIVE candidate and address | `query-executor-partition-service-resolution.js:126-147` rejects inactive or unaddressed services before any readiness grace. This ACTIVE-shaped routing input is not automatically an exact canonical registration birth. |

`src/query/canonical-leader-routing.js:128-195` accepts an owner partition leader, a retained leader, or a unique service-role witness only with a partition present. Existing retained runtime identity also requires an ACTIVE service for the retained node (`query-executor-canonical-leader-routing-methods.js:125-177`). These mechanisms do not derive current leadership from an original grant or from DB existence.

## Existing recovery mechanisms do not remove the prerequisite

A fresh topology snapshot is not an allocation declaration. `BootstrapTopologySnapshotOwner` resolves existing observed/published partition rows and SERVICES role rows (`src/bootstrap/owners/bootstrap-topology-snapshot-owner-leader-identity.js:35-91`). Its fresh-window predicate uses equal created/updated timestamps; its one-service fallback requires an existing published partition (95-126). `seedBootstrapRoutingOverlayFromSnapshots` requires PARTITIONS plus matching partition-type SERVICES rows (`src/query/sql-query-engine-bootstrap-routing-overlay.js:460-510`). The ordinary runtime handoff seeds this overlay from supplied bootstrap snapshots (`src/bootstrap/shared/startup-sql-runtime-handoff.js:99-123`); the early bridge constructor does not do so. Calling the snapshot owner to read local DBs (authoritative-rows.js:478-505) is not the demanded live leader RPC and cannot certify original grant or current authority.

CDC's existing reseed path is narrower: it runs only after TABLE_NOT_FOUND/PARTITION_NOT_FOUND, requires connected nodes, constructs addressed ACTIVE-shaped candidates, and invokes `installRecoveryRoutingOverlayEntry` (owner-rpc-read-execution.js:256-323). That overlay installer refuses when a canonical leader already exists and uses the existing bootstrap leader selector (bootstrap-routing-overlay.js:528-572). This is not evidence that a lone local cold owner has a connected peer, reaches the triggering error, or supplies an exact original incarnation. It must not be cited as an already-proven original-grant route.

READINESS_INTERNAL deliberately removes downstream readiness from structural routing, but still uses `hasLiveTransportEvidence` and therefore actual `getConnectionState(nodeId) === CONNECTED` (`query-executor-bootstrap-deferred-routing.js:4-16`; `src/control-plane/live-transport-evidence.js:31-48`). The router accessor reads `nodeConnections` with no special self shortcut (`src/transport/message-router-delivery-behaviors.js:712-715`). A local exact handler is not by itself a connected self-node record. The caller cannot select this purpose merely to suppress a denial; its applicable owner purpose and self transport engagement require review.

The priority-recovery read grace requires explicit token recovery routing and positive PROCESS_ALIVE, CLUSTER_MEMBER_HEALTHY, LOAD_READY, CONTROL_PLANE_PUBLISHED and METADATA_PUBLICATION_HEALTHY facts, with a restricted failed-dimension/reason set (`query-executor-priority-recovery-bootstrap-routing.js:73-89,137-223`). It is not an unpublished-startup exemption. The existing system-table leader exception likewise requires already addressed active services, a canonical leader and explicit evidence-absent denial reasons; substantive membership/transport denials remain denied (`partition-routing-snapshot.js:63-115`). Neither mechanism invents the absent route.

## Handler, read witness, and public admission are separate

The actual transport handler distinguishes Raft from application payloads, then applies removal-serving admission; QUERY counts as serving work and an active removal fence rejects it except the existing participant-session exception (`src/partition/partition-service-entry-apply-base.js:247-261,281-328,336-370`). A blanket removal fence therefore cannot implement the intended external-only restriction while allowing this ordinary internal query.

Remote QUERY takes the actual initialized service through `executeQuery`; read statements use the existing statement admission and bounded SQLite collection (`src/partition/partition-service-remote-query-methods.js:251-281`; `partition-service-write-metrics-base.js:60-128`). The read witness is built before SQL execution from the local runtime's role, Raft status term, partition/node/replica IDs and owner clock (remote-query-methods.js:120-139). CDC rejects a successful required-leader answer lacking a valid witness (owner-rpc-read-execution.js:60-83,462-470).

The validator checks observed state, matching partition, LEADER role, nonempty serving node/replica and nonnegative finite observation time (`src/control-plane/control-plane-authoritative-read-witness.js:5-25`). It does not validate term, read-index, quorum acknowledgements, allocation identity, SERVICES birth or create-attempt token. Do not reinterpret this existing leader witness as the literal v2 peer/quorum serving proof or as exact-original registration identity. Exact original generation/value checks belong to the row/handoff owner after the real answer; this read path does not supply them automatically.

The default QUERY payload contains SQL, parameters and selected execution identities/limits; it does not carry the frozen read-authority token to the sink (`src/query/query-executor-partition-request-builders.js:84-114`). That token guides caller routing and returned-witness validation. It is not currently a sink-side proof that the request is privileged original-handoff work. The author's public-ingress fence must preserve the real internal call while independently denying public traffic; marking every QUERY internal or relying on the caller's token would not establish that boundary.

## Minimal missing owner interaction and proof

The smallest next design decision is an explicit input contract to the existing routing/topology/overlay owner, backed by the admitted complete original cohort and its exact live physical owners. It must provide the exact system partition, original replica/incarnation, exact registered address/handler, current leader observation and applicable readiness/transport evidence for MESSAGE_GROUPS and SERVICES readback. It must remain a bounded route for contacting the owner, not a fabricated canonical row, absence-based grant, or locally authoritative data answer. The existing gateway, candidate selector, actual QUERY handler and returned-witness checks can then remain the execution chain. Whether an existing overlay API is safe unchanged for those facts requires the complete contract review; this note does not approve feeding grant-shaped pseudo-snapshots to it.

The circular dependency otherwise remains concrete: readback needs a SERVICES-derived route/canonical leader; the recovery operation needs that authoritative readback to resolve its one submitted SERVICES birth before completing registration/publication. Waiting for broad cache hydration or ControlPlaneSetup to create the route violates the proposed nonserving bounded operation and can activate unrelated writers. A prospectively admitted exact original runtime can supply routing evidence only through its named owner interaction, not through a claim that all metadata is absent.

Required discriminators: initial canonical rows unpublished; actual early gateway engaged; exact original route and real registered handler reached; successful native SELECT plus leader witness; wrong original identity/token rejected by the handoff owner; missing route/leader, follower answer, malformed witness and retired/replaced endpoint remain unavailable without resubmission; public ingress remains denied while the genuine internal call succeeds. Preserve the literal v2 serving gate and cold mid-handoff HOLD. Until these prerequisites are specified and measured, the source-only verdict is **missing bounded routing/ingress correspondence**, not a usable complete original-handoff route.
