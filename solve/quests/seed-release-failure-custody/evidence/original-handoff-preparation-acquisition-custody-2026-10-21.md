# Complete-cohort preparation: acquisition before constructor return

Read-only correspondence for the `retained-seed-original-handoff` draft review, inspected at `e69db481f37ab5633d64de7b6e7345426d9286b3` with product source identical to `393f411ca09449898465cc3cb7320c03fba2aba8`. This supplies the constructor-failure and resource-custody category of the complete contract review. No source/test/seal/log/receipt changes or experiments were performed.

**A collection that receives only successfully returned prepared owners does not cover acquisition failures. The existing lifecycle/preparation owner must already retain an acquisition slot when the raw DB is opened, and the raw returned handle must enter that slot before any pragma, formatting constructor, readback or callback can throw.** The slot owns a resource obligation; it is not allocation permission or a second ledger/controller.

## Existing MG and partition seams

- `src/message-group/message-group-consensus-port.js:148-167` assigns `service.db = new Database(service.dbPath)` at 150, before pragmas at 151-152 and operation-port construction at 154-155. If a pragma or later constructor throws, the DB remains on the pre-existing service object. The port assignment itself happens only after the port constructor returns, so it cannot stand in for raw-DB custody.
- MG initialization catches opening failure and attempts `closeMessageGroupConsensus` (`message-group-service-raft-lifecycle.js:214-234`). That close captures the exact port and DB, installs the in-flight settlement before running close code, clears a field only after the corresponding close succeeds, and clears the settlement on either fulfillment or rejection to allow retry (`message-group-consensus-port.js:209-239`). A DB close throw leaves the exact `service.db` reference intact. The outer registered-MG initializer attempts shutdown and handler retirement separately; failed cleanup retains the exact service in the existing map when its slot is vacant or already identical, then aggregates primary plus cleanup failures (`src/bootstrap/shared/message-group-transport-handler.js:78-107`). This is a concrete existing resource-custody pattern, not proof arbitrary new preparation code inherits it.
- `src/partition/partition-service-raft-init-base.js:337-389` performs directory/snapshot work and DB opening/formatting in one synchronous section. It assigns `this.db` at 370 before journal/sync pragmas, legacy detection, committed-outcome/participant stores and schema DDL. A schema/registry/lifecycle constructor failure therefore need not lose the raw handle if the service is strongly retained. The explicit legacy-refusal close at 379 clears the field only after close; a thrown close skips the clear, but also interrupts construction of the intended legacy error, so it is not an example of preserving both causes.
- `src/partition/partition-service-lifecycle-methods.js:37-42,79-83` closes the actual port before DB and clears references only after success. However, the seed partition creator stores the service in `partitionServices` only after `await partition.initialize()` (`src/bootstrap/phases/seed-partitions-phase.js:249-315`). Its catch records progress and rethrows. This path does not by itself establish a strongly retained unopened-preparation collection, and a failure before handler registration cannot rely on the router retaining the service. Do not copy a success-only map insertion into the proposed metadata preparation.

The existing `MessageGroupService` and `PartitionService` object constructors do not themselves open these DBs; native opening occurs in their initialization paths above. A new metadata-only constructor that both opens and formats before returning would remove the useful raw-handle custody seam unless it owns that seam internally.

## Borrowed-handle constructors can fail after durable effects

`createRaftRsOperationPort` receives the host DB, constructs `RaftRsPeerIdentityRegistry`, reserves the local and bootstrap identities, computes bootstrap membership, constructs the lifecycle owner, then may construct the native dispatcher (`src/raft/raft-rs-operation-port.js:180-225`). This is not a metadata-only preparation API and must not be called before ISSUE merely to obtain these formats.

The peer registry borrows the DB, creates its table and performs additive ALTER migrations (`src/raft/raft-rs-peer-identity.js:137-148`). Reservation reads and INSERTs can throw (`193-214`). The lifecycle constructor similarly borrows the DB, creates/migrates its table, reads identity/history, inserts a fresh lifecycle row or stamps an unstamped row (`src/raft/raft-rs-replica-lifecycle-owner.js:79-95,109-169`). Its injected `mintIncarnation` is an explicit synchronous callback. None of these constructors closes the borrowed DB on failure. Partial format/reservation writes are not rolled back as one whole constructor operation.

`RaftRsDurableStore` borrows the DB and creates/migrates record tables (`src/raft/raft-rs-durable-store.js:269-301,309-327`). Creation of an entirely absent record is grouped in one transaction; a partial pre-existing record is deliberately not filled into a false virgin record. Additive column migrations follow separately. The runtime constructs this store at `src/raft/raft-rs-runtime-owner.js:1862-1871`. These existing loss fences and partial durable effects must survive a preparation failure; closing a DB does not erase or revoke them.

`commitDurably` provides synchronous per-DB durability, not cohort atomicity or resource ownership (`raft-rs-durable-store.js:189-204`). Its work callback is synchronous owner work. Its final pragma restoration may itself throw; using this primitive does not eliminate the need to preserve any available primary and cleanup errors. This note authorizes no unrelated rewrite of that primitive.

## Distinguish native Database-constructor failure from formatter failure

The locally installed dependency inspected is better-sqlite3 **11.10.0**. Its JS constructor validates inputs, loads the native addon, then constructs the native DB and installs it on the wrapper (`node_modules/better-sqlite3/lib/database.js:9-72`). For ordinary filesystem opening, the native constructor calls `sqlite3_open_v2`; on an unsuccessful open it throws a SQLite error and explicitly calls `sqlite3_close` before returning. Its separate failed-buffer-deserialization path also closes before returning (`src/better_sqlite3.cpp:468-519`, especially 489-509). Successful construction wraps the DB and returns it.

There is no application-accessible DB handle if `new Database(...)` itself throws. A pre-existing application slot can record the failed acquisition, but cannot retain or retry a handle never delivered by the dependency. The inspected native paths assert that their internal close succeeds; they do not return a recoverable handle or typed failed-close debt. This is a dependency ownership boundary, not evidence of a reachable native leak, nor a proof against fatal allocation/native failures. No such native failure was injected here. The normal application seam covers **successful raw DB return followed by a throwing formatter**, which is the concrete gap in a returned-owner-only collection.

For an exposed DB, native `JS_close` throws while busy or while iterators remain, before it removes the DB from the addon set or invokes actual close (`better_sqlite3.cpp:729-738`). `CloseHandles` closes statements/backups and invokes `sqlite3_close`, asserting success (`438-449`). Preserve an application reference on a thrown close; do not equate rejected close with closure. Do not rely on eventual native destructor/GC as bounded cleanup evidence.

## Synchronous is not automatically non-reentrant

The current openers invoke logger/progress callbacks; the partition sync-section wrapper runs supplied work and instrumentation in try/finally (`src/diagnostics/event-loop-gap-watchdog.js:219-225`). Lifecycle formatting can call injected `mintIncarnation`; the durability primitive calls its work function. The SQLite wrapper also supports a `verbose` callback, and native statement logging calls it synchronously (`better_sqlite3.cpp:425-435`), although the inspected production MG/partition opens do not configure that option. These are callback boundaries even without an await.

The proposed critical section must use closed, reviewed owner operations and ordinary owned data slots, exclude arbitrary callbacks/getters/proxies/verbose hooks from the acquisition-to-retention gap, and establish its in-progress/invalidated state before any permitted callback can reenter. An observer hook inserted before raw-handle retention would reopen the same hole. Real async abort callbacks cannot interleave a genuinely synchronous no-reentrant section, but later native-opening awaits still need the already specified live-brand check and cleanup join.

## Minimal contract and discriminator

Use the existing lifecycle/preparation owner to strongly retain a resource-only acquisition slot before opening. After raw `new Database` returns, assign the exact handle into that owned slot immediately; only then run pragmas, registry/lifecycle formatting, commit/readback and final prepared-owner construction. A formatter's throw must leave the slot available to cleanup. Successful close discharges only that exact slot/handle; failed close keeps it strongly retained, blocks exclusive directory release and preserves primary plus cleanup errors. Prepared-object return is a later success event, not the start of custody. Do not register an arbitrary caller callback as the sole handoff mechanism.

The focused proof should throw after a real raw DB opens but before the formatter returns, then fault close on that exact DB: verify no native Raft opening or ISSUE success, exact object remains owned, primary plus cleanup failure survive, directory custody remains, and a permitted retry closes that same object before discharge. A separate normal Database-open refusal proves no formatter/issuance occurs, but cannot be mislabelled a test of failed close on an inaccessible native constructor handle. Partial PREPARING/format facts remain nonauthorizing HOLD; this preparation support neither waives cold progress obligations nor creates a new public cleanup handle.
