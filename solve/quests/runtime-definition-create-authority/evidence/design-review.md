## One canonical interpretation, with distinct permission meanings

`src/rebalancer/runtime-service-policy.js:19` is the smallest existing owner for the effective runtime placement interpretation. It should consume the existing Binding lineage contract, not copy it into the handler. A single canonical decision should be consumed by placement and CREATE; presentation adapters may project that answer without retaining old fallback interpretations. Prefer one exported decision shape over retaining the old permissive number helper beside a stricter CREATE-only predicate.

The current `hasRequestBindingServiceDefinitionLineage` is deliberately only a marker detector (`request-binding-service-definition-contract.js:106`). It is not validation: a partial marker or reserved service-id prefix currently earns policy target 3. Reuse the existing `getBindingServiceDefinitionSourceKind`/source-kind contract, which validates service-id derivation, lineage strings, projection identities and normalized declaration (`:113`, `:151`), plus canonical status. Malformed markers must not fall through to the non-Binding branch. An active valid Binding has the system policy target even when its stored count is zero; retain that producer-owned storage meaning (`:302` and the builder's explicit zero field).

For non-Binding rows consume only canonical `replica_count`, with the non-negative safe-integer contract already used by `postgres-wire-scale-contract.js:43`. Remove camelCase count aliases, coercion and invalid/missing-to-default-3 permission in the touched interpreter. Preserve legitimate built-in zero and positive scale intent. Crucially, **unavailable/invalid target is not target zero**: zero authorizes scale-down planning, so mapping every ineligible or malformed definition to zero would introduce destructive permission. Keep valid scale-zero, inactive definition, malformed definition and unavailable observation distinguishable. The existing active-definition discovery and exact compiled-row equality checks in `runtime-service-rebalancer-setup.js:311`/`:348` retain their own roles; do not discard the compiled owner evidence when sharing the interpretation predicate.

All current target consumers must have an explicit disposition: `unified-rebalancer-policy-scheduler-methods.js:79`, `admin-runtime-service-views.js`, `service-discovery-catalog.js`, and `remote-cache-service-rows.js`. Placement must refuse/retry unavailable target through its existing scheduler rather than use an invented count. Presentation may report unavailable; it must not restore default 3 or zero through a local fallback. ## Route and execution consume the same decision

`runtime-service-bound-creation-route.js:242` currently filters the definition to a bare row, decides generic versus bound, and generic CREATE reads it again (`runtime-service-generic-replica.js:40`). Use one named resolution for the unrouted attempt and carry that resolved definition through existing generic execution. If a later read is deliberately required, it must re-enter route classification as well: route from row A followed by execution of a changed row B cannot bypass the bound/generic distinction. This needs no durable memo beyond the existing execution lifetime.

Remove the optional-method ladder and bare-row CREATE resolver. Retain the separate cache resolver only for its existing REMOVE use, outside this repair's claim. Do not rename that unrelated use into proof that every repository legacy path has disappeared.

Named errors must survive both route and generic outcome emission. The current route catch maps every exception to DEFERRED using `error.code` (`:272`), while generic definition errors use `errorCode` and `deferRetry`. An implementation that merely throws the existing generic error at the earlier route would lose its name or turn permanent ABSENT/INELIGIBLE into retry debt. Map the canonical outcome explicitly through the existing settlement/emitter owner: UNAVAILABLE is retryable; confirmed absence/ineligibility keeps the intended permanent refusal. Unknown/malformed resolution must be UNAVAILABLE, never the current default-to-ABSENT.

Preserve journal-first behavior. A matching retained creation still routes/resumes from its full retained origin before mutable definition lookup; its existing current-execution, current-physical-generation, wake, retirement and shutdown fences remain intact. A mutable definition failure must not erase an admitted retained creation or authorize a generic substitute. No change to bound removal, reservation, resource grants or creation journals is proposed.
