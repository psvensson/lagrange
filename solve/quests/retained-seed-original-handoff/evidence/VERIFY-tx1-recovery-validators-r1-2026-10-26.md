Two defects block keeping 9ab8ecc74 as is:

**RC-1 (safety, new with this commit): the held stage refusal is stamped `commitPointReached: false` from the unvalidated cache-row status.**
`distributed-transaction-coordinator.js:487` returns `withCommitPoint(held, tx)`; `distributed-transaction-commit-point.js:65` derives the field from `tx.status`, which for a `recoveryDiscovered` obligation is the discovery snapshot's progress hint (R2 design: "status remains a progress hint"; R10). The module's own contract says `false` means "the engine establishes that nothing was committed". Measured (`logs/D-probe-crash-window.log`): a durable row holding a recorded COMMIT whose status is still PREPARED (the window between the decision write and the COMMITTING status write; the valid-recovered witness shows that order `decision:COMMIT, transaction:COMMITTING`) is discovered and bound to the live session; the client COMMIT at head answers `TRANSACTION_DECISION_IN_DOUBT` with `commitPointReached: false`, and the next re-drive COMMITs the transaction. The two consumers misread that answer: `src/runtime/pgwire-transaction-outcome.js:131` answers the engine's own error instead of 08007 (probe `logs/PG-probe.log`: with the stamp `kind=engine_error outcomeUnknown=false`; without the field or with `true` `kind=error sqlState=08007`), and `src/query/application-database.js:123-125` (`isCommitOutcomeUnknown`) classifies the failure as "nothing committed" instead of the typed outcome-unknown error. At base the same window answered the client a truthful success (through the client-owned adoption the commit removes), so this is a regression of the answer's truth, not an inherited one.
Exact change: in `commitOwned` return the refusal without the negative commit-point claim, e.g. `if (held) return held;` (field absent = unknown, which both consumers already handle as 08007 / outcome-unknown), or stamp only when `commitPointReached(tx)` is true. Add the crash-window witness to `test/query/transaction-recovery-decision-validation.test.js`: a discovered row with a recorded COMMIT at status PREPARED, bound to its session; the session COMMIT answer carries no `commitPointReached: false`, and the re-drive COMMITs.

**RC-2 (latent red, claim (E) is false for test readers): three strict assertions distinguish own-null from absent.**
`test/integration/helpers/tx1-in-doubt-decision-reader.js:35` and `test/integration/helpers/tx1-postkill-authority-replay.js:92,105` use `node:assert/strict` `assert.equal(restored.decision, null)`. With `decision: null` dropped from the restored record the value is `undefined` and strict equal throws (`logs/E-probe.log`: base PASSES, head `THROWS ERR_ASSERTION, actual undefined, own key false`). They are reached only by `seed-migration-interrupted-decision.integration.test.js`, whose child dies today at the O3 hold `original-allocation-directory-custody-unavailable` before running them (identical leaves base/head), so this is a latent red that fires the moment the hold lifts. The live record (`distributed-transaction-coordinator.js:343-362` `registerTransaction`) indeed has no `decision` key, so the shape change itself is right; the readers must follow the shape.
Exact change: in both helpers assert the live shape (`assert.equal(restored.decision, undefined, ...)` / `assert.equal(tx.decision, undefined ...)`, or `assert.equal(Object.hasOwn(restored, 'decision'), false)`), three sites.

No other required change. Approve-after-fix recommended; the two changes are local and do not touch the repaired owner path's semantics.

## Findings

**(a) Superseding the poison-row invariant (`transaction-recovery-poison-row-attribution.test.js`, sealed by 8d0fb8c1a).** The witness asserts that `recoverFromSystemTables` throws a typed `TRANSACTION_RECOVERY_INCOMPLETE` naming `frozen_participant_count` / `commit_mode` for a poison cache row, i.e. discovery REFUSES. The accepted R2 refinement says the opposite for the same input ("Cache rows discover exact IDs only ... Missing, unreadable, malformed and unavailable authoritative rows HOLD with zero fanout"), and the current head's own epoch gate already throws a different dimension for these fixtures (they predate the canonical epoch requirement). Both facts say the sealed contract is superseded, not merely red. I agree with the implementer that this is an owner decision (R09), and that the correct successor is an attribution contract on the HOLD (the re-drive's `decisionReadState: invalid` should name the failed dimension and row identity, which `validateRecoveredTransactionDecision` already produces and `authorityCandidate` currently swallows in its `catch {}` at `recovery-authority.js:85-88`). Recommend: owner supersedes the poison-row witness with a hold-attribution witness; `validateRecoveryRowsBeforeMutation` then has no role and is deleted (owner decision 6 forbids de-export now, so leave it until that decision).

**(b) Behaviour change: session stages on a `recoveryDiscovered` obligation.** Correct reading of Invariant 0 ("the client transaction must not own the decision") and of R2 (recovery reads the authoritative row before any stage; "A refused admission is never counted as a completed statement"). Wake/re-drive path and bound: `startRecoverySweep` runs `runRecoverySweep` every `RECOVERY_SWEEP_DEFAULT_INTERVAL_MS` = 1000 ms (`distributed-transaction-coordinator-constants.js:40`; activated at `sql-query-engine-lifecycle-and-callback-dispatch.js:194`), plus `resumeRecoveredTransactions` at activation and at the BEGIN advanced-readback handoff (`sql-query-engine-transaction-persistence-methods.js:retainAdvancedDistributedTransactionReadback`). Each sweep includes every `tx.recoveryDiscovered` (`recovery.js:265`) and calls `redriveAuthoritativeRecovery`: FROZEN + all PREPARE evidence -> COMMIT on the next tick (<= 1 s); undecided without that proof -> held until `isTransactionBudgetExceeded(tx)` on the row's own `timeout_deadline` (default `TIMEOUT_BUDGET_DEFAULT.TRANSACTION_BUDGET_MS` = 60 000 ms, `src/control-plane/timeout-budget.js:20`), then freeze + bound ROLLBACK; retryable control-plane errors defer the sweep with backoff capped at `RECOVERY_SWEEP_DEFER_MAX_MS` = 30 000 ms. Completion runs `endTransaction` (`decision-protocol.js:91`), which releases `transactionsBySession` and lets the session BEGIN again. So a client waits at most (remaining transaction budget) + 1 s + <= 30 s deferral, EXCEPT for INVALID / LEGACY / UNAVAILABLE / MISSING authority, which hold without bound by design (R2: hold, zero fanout; needs the owner). The lost-answer live case: the engine's `persistDistributedTransactionParticipantSet` already resolves a lost CAS answer by exact readback (`sql-query-engine-transaction-set-methods.js:52-61`), so the coordinator's catch (`participant-set.js:23-28`) fires only when the readback disagrees (another owner advanced the row, or the write failed); the obligation is then re-driven against that authority within the bound above. Consumers of `TRANSACTION_DECISION_IN_DOUBT`: no src consumer branches on the code itself; the two consumers that read the answer's `commitPointReached` misread the stamped `false` (RC-1). Minor: the stage refusal carries `decisionReadState: undefined` (no read has happened) rather than a named state (R07); `recoveryObligationStageRefusal` returns `Object|null` where the sibling admission (`admitExpectedTransaction`) returns a typed `{state}`; the decision-boundaries audit does not flag it, so a note, not a required change.

**(c) `commit()` adopting the session's held transaction when `expectedTransactionId` is null (`coordinator.js:467-468`, same in `rollback` :502-503 and the admission default at `executeWriteStatement`).** After this commit a COMMIT that adopts a discovered obligation can no longer decide it, so the decision surface is closed. The adoption surface remains: discovery binds a row to `ownerKey = session_id` (`recovery.js:524`), `restoreRecoveredWorkflowRow` installs it as that session's transaction when no live owner exists, and `getTransaction(sessionId)` then reports a transaction the client never began (the DEFAULT session `QUERY_SESSION.DEFAULT` after a restart, or a client whose session id collides with an old row): `hasActiveTransaction`, `admitParsedStatement` and pgwire's session state all see it; BEGIN answers `TRANSACTION_ACTIVE` (`logs/A-probe-head.log` LOST_ANSWER_LIVE begin-again), every write on that session is held in doubt until the sweep ends the obligation (bound above). This is pre-existing (at base it was far worse: the writes ran inside the recovered tx and the COMMIT decided it) and is the R2 gap the design names ("without replacing a newer session owner"); the owner-level repair is for discovered obligations not to occupy the live session namespace at all (owned by recovery under their own key, or bound to the session only on an exact `expectedTransactionId`). Record as a finding for the recovery owner; out of this commit's scope.

**(d) Re-wiring claim (G1 above).** The implementer's stated evidence for not re-wiring `validateRecoveryRowsBeforeMutation` is wrong (TX1 Q1 does not go red); the correct evidence is the R2 design text plus the new witnesses (6 go red under re-wiring). The commit message should be corrected when the required changes land; no code change follows from this.

**(e) Validator-swallowing `catch {}` (`recovery-authority.js:85-88`).** The one validator produces the attributed dimension and row identity; the authority discards it and answers a bare INVALID. Not a regression (base answered a bare null), but it is exactly the attribution the superseded poison-row contract wanted; see (a).
