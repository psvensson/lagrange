## The earliest writer is before the activation scheduler

`src/raft/replica-leadership-state.js:62-79` applies native leadership, mints the current tenure, and immediately calls `queueRoleUpdate` and `queueLeaderNodeUpdate`. Only afterward does its event subscriber invoke the service's `onLeader` callback (153-158). Demotion also queues a role mutation (94-102). A guard only on `scheduleLeaderOwnedActivation` misses these actual early writers.

Partition wiring records the observation, schedules activation, then invokes the participant determinism self-check (`src/partition/partition-service-raft-lifecycle-wiring.js:70-81`). The activation can be immediate for one replica. Its callback checks `isShutdown/isLeader`, queues durable leader reassertion, attempts rebalancer leadership, schedules mirror resumers and emits LEADER_ELECTED (`partition-service-leader-activation-methods.js:90-119`). These are separate effects, not an atomic registration operation.

Role and leader mutation helpers read actual SERVICES/PARTITIONS rows and have scheduled retries (`partition-service-metadata-mutation-helpers.js:63-125,199-280,283-345`). The role guard uses logical IDs, optional observed role and updated_at; the leader guard uses partition ID plus optional observed leader/updated_at. They are not already bound to the proposed original grant, reserved SERVICES birth, foundation generation and current original-operation tenure. Leader `prepareFlush` checks current leadership, but does not by itself check the new operation is still live. `reassertDurableLeaderNodeId` queues the helper at metadata-delivery-methods.js:367-372. The existing shutdown calls helper shutdown (partition-service-lifecycle-methods.js:190-191), but that is not proof an accepted asynchronous publication/readback already in flight has settled.

Therefore R2's permitted publication class needs the same existing row/lifecycle interaction as R1: exact original operation, physical member, current native tenure and reserved foundation/birth at the effect boundary, including post-await readback and any scheduled retry. Native observations remain observations; callbacks can record them without automatically acquiring a publication right. Deferred work after closure must be refused before a new effect, while accepted committed/uncertain work remains an owned obligation.

First construction requires background-ready leadership plus that complete bundle (160-167). The early SQL bridge merely consumes the existing coordinator; it does not mint one (src/bootstrap/owners/seed-runtime-bridge-owner.js:50-60).

The positive exclusion must retain the whole chain: no ControlPlaneSetup invocation/returned coordinator assignment (`bootstrap-service-control-plane-runtime-methods.js:55-89`), no startup runtime-surface wiring of a coordinator, no partition `setRebalanceCoordinator/rebindCoordinator` (partition-service-split-accessor-base.js:701-727), no already acquired rebalancer, and no secondary leadership sink. The secondary sink is driven independently of partition rebalancer construction (leader-activation-methods.js:63-85); installation/runtime-service setup can attach it. Dependency absence prevents first acquisition, not retention of a previously injected/acquired rebalancer. The bounded cold public witness can positively assert null dependencies, zero constructors/leadership effects, and no setup/rebind/sink calls while real native leader callbacks execute. This is an existing-owner exclusion, not a new rebalancer policy.

## Mirror resumers act on real transition obligations, including acknowledgements

`resumeDurableMirrorReplicationWorkers` schedules split and merge resumers in Promise continuations and logs rejection rather than propagating it (partition-service-split-mirror-queue-methods.js:116-133). Split checks leader/no existing worker, then accepts SPLIT_BACKFILLING, SPLIT_CATCHUP or SPLIT_CUTOVER_ACTIVE where metadata names this source (146-164). A retiring source can send CLEANUP_COMPLETED even without reconstructing a worker (174-179); otherwise the existing reconstruction/start owner runs (182-191).

Merge checks MERGE_BACKFILLING, MERGE_CATCHUP or MERGE_CUTOVER_ACTIVE and source membership, may send SOURCE_MIRROR_REMOVED for a retiring source, or reconstruct durable deltas and start its existing handle (`partition-service-merge-replication-resumption-methods.js:41-105`). These retirement acknowledgements remain real effects. A claim of zero newly allocated worker does not exclude them.

Crucially, `findDurableMirrorTransitionForService` reads `systemTableCache.getAll(TABLES.TABLES)`, normalizes transition metadata and returns the first matching source (src/partition/partition-mirror-replay-cursor.js:143-162). It is a projection reader of durable transition facts, not a read-only cold durable inspector. Missing cache/no matching row is only current absence of a wake/input, not proof the underlying obligation does not exist. Once resuming, its replay cursor reads committed applied deltas from the actual partition log (110-127).

The delayed resumer entry checks role and existing worker, not `isShutdown` or the prospective original-operation token. Thus the author must bind its actual entry/effect to the exact admitted original operation or prove the typed cold exclusion remains true through that entry. A callback captured before closure and released afterward is a necessary discriminator; merely clearing the leader activation timer does not cancel an already queued Promise continuation.

## Read-only cold facts must cover replay, not only materialized rows

Before native creation, the existing allocation/lifecycle inspection must reject an ineligible cohort using actual owner facts: exact identities/incarnations/history/rights; actual TABLES transition state and metadata for declared members; source retirement/ack/replay-watermark obligations; participant/coordinator application debt where relevant; and the durable consensus application frontier that can change those facts. An empty fresh cache, all-UNUSED handoff rights, known system-table names or no current in-memory worker is not that proof.

Existing durable-store facts include hard-state commit index and applied index as exact decimal strings (`src/raft/raft-rs-durable-store.js:596-621`). Its static `readCommittedEntriesIn` is DDL-free but reads NORMAL proposals **at or below the applied index** (624-651); it cannot prove there is no committed-but-unapplied transition command. `readAppliedIndexIn` is DDL-free (654-669), and `hasDurableRecordIn` skips constructor DDL but returns only presence (705-723). Full record methods and peer/lifecycle facts remain their existing owners' knowledge. If the prospective cold inspector needs a read-only application-frontier classification not exposed by those methods, add it within that durable owner; do not instantiate the formatting constructor for inspection or duplicate its record/codec interpretation in a bootstrap caller.

The exact proposed first-unit exclusion must either classify pending committed application through the actual application owners or return an explicit ineligible/HOLD before native entry for an unclassified frontier. A later registration-time transition check is too late. This note does not prescribe a new blanket commit==applied policy or waive genuine retained replay; that finite boundary is the author's decision for corrected review. Uncommitted suffixes, malformed/missing owner records and unknown commands cannot be silently treated as harmless or erased.

## Native and SQL replay remain operational

The existing runtime restores the actual durable record, enforces participation/opening-history gates, creates the native node and settles participation (src/raft/raft-rs-runtime-owner.js:487-535). Reconstruction may campaign a sole voter only when the durable participation gate is open (552-564). Committed application runs transactionally with applied-state advancement (1074-1101); suppressing those callbacks would break consensus semantics.

Partition committed SQL uses its existing recorded-outcome and prepared-transaction owners, applies admitted SQL, records the result, records CDC, advances write generation and schedules after-commit effects (`partition-service-entry-apply-base.js:618-680`). Coordinator settlement and participant commands delegate to their respective existing owners (613-616,671-680). These obligations must either be admitted/classified by the original unit or make it ineligible before opening; they cannot be skipped to preserve a cosmetically empty snapshot.

MG committed CDC calls `cdcHandler.applyImmediate` with `skipSubscriptionCheck: true`, then emits its after-commit announcement (`src/message-group/message-group-service-raft-timing.js:35-80`). Thus genuine replay can repopulate TABLES transition input even if no fresh CDC subscriptions were acquired. MG leader activation also updates rebalancer leadership and resubscribes existing subscriptions (message-group-service-leadership-state-runtime-methods.js:45-95). The prospective cohort validation must account for these exact committed/cache effects; it must not rely on subscription absence to suppress replay.

The partition leader determinism self-check is another finite callback: it runs only with an open DB and an applied write origin, and logs failure for retry at first BEGIN (partition-participant-transaction-self-check.js:68-77). It belongs to the existing transaction owner, not ordinary rebalancer acquisition. Preserve its meaning and report it separately from completed handoff.

## Additive tail-reader clarification: expected original work remains admitted

The full read-only API is already exposed: `RaftRsDurableStore.readDurableRecordIn(db, groupId)` at durable-store.js:586-587 delegates to the constructor-free reader at 207-247. It reads hard state, applied state, snapshot and **all** ordered log entries through existing owner SQL, using safe integers and exact decimal representations. Failed table reads throw a table-named error (165-170). No native creation, store-constructor DDL or new record parser is needed. The earlier conditional reference to a possibly missing read-only frontier API must not be read as claiming this full-record API is absent.

The committed pending interval is `appliedIndex < entry.index <= hardState.commit`, compared in the owner's exact integer domain. Entries beyond commit remain a distinct persisted, not-yet-committed suffix; snapshots, compacted ranges, missing entries and inconsistent progress must be judged by the existing record/opening owners. Reading a record is not executing it or inventing consensus commitment. `readCommittedEntriesIn` is narrower and is unsuitable for this interval, as stated above.

The existing application transaction owner defines the interpretation boundary (`src/raft/raft-rs-application-transaction-owner.js:11-17,60-83`): only NORMAL entries with nonempty string payload carry an application command. Empty NORMAL leader entries are native no-ops, and configuration changes stay with native membership/context application. For an application payload, use the existing `decodeCommittedProposal` UTF-8/JSON codec (`src/raft/raft-rs-proposal-codec.js:53-59`), as the operation port does (raft-rs-operation-port.js:112-119). Do not create a bootstrap JSON/SQL replay interpreter.

ENABLE's actual committed application command is `PARTICIPANT_GENERATION_ORIGIN` (partition-participant-transaction-constants.js:12-24). Its existing builder binds partition ID and the canonical origin entry ID (partition-participant-transaction-bytes.js:303-309); its pinned validator is at 343-357. Its application owner records the origin or answers the already recorded original result idempotently (partition-participant-transaction-apply.js:565-579). Genuine pending original ENABLE/origin work therefore cannot be rejected solely because commit exceeds applied, nor may it be skipped. The existing participant apply owner remains authoritative. A pinned syntax check alone does not substitute for the original cohort/member/current prior-existence facts.

Expected original participant-policy or role/foundation SQL must likewise be classified by its existing producer and application owner against the complete exact original identity/template, including target table, immutable keys, parameters and reserved generation. `QUERY` or a recognized SQL command type is not an allowed-effect proof: the same command family can update TABLES transition metadata. `admitCommittedCommand` is preproposal admission and does not itself identify every semantic effect of arbitrary committed SQL. MG CDC/CDC_BATCH must be bound to the allowed exact source/table/row effects; valid message-group command syntax is not enough to allow a replay-carried split/merge transition.

Thus the corrected contract should explicitly retain expected NOOP, original ENABLE/origin, original policy and exact permitted row-publication tails, with their native/application owners performing the real replay after admission. Contrary split/merge/retirement/application effects are ineligible before native creation; genuinely unknown/corrupt facts are named unavailable/HOLD. **Do not replace the sealed intact-ESTABLISHED/all-UNUSED case with a blanket commit-equals-applied requirement.** If existing producer shape/effect correspondence is insufficient to classify a legitimate original tail, that finite owner interaction must be specified rather than silently excluding the promised case. No new generic replay engine or disabled native callbacks follows from this clarification.
