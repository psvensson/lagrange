## Why the proposal assertion originally failed

The early measurement was not a settled steady-state Raft group: although
`leaderReplicaId()` returned a leader, the founding no-op had not reached a
majority and followers had no acknowledged progress. In raft-rs Probe
state, another Append can wait for an earlier response. The original test
assumed that leader election alone meant a fully caught-up group.

The corrected witness **does not merely drop the failed assertion**.
It explicitly drives all three native voters until the leader has committed
its first entry and both followers report progress >=1, and fails if that
stabilization cannot be established. It then proposes without another tick
and requires both peer Append messages to be emitted before the next heartbeat.
The identical corrected test passed on both lab machines.

**Interpretation:** steady-state proposal-driven Raft Append delivery is
observed on a realistic rs-raft operation-port fixture independent of a
heartbeat tick. Neither the time required for an end-to-end real-network
write commit nor Veilid delivery cost was measured.

## Native timing vs configured timing: current mismatch confirmed

The source defaults on the studied baseline include
`raft.heartbeatIntervalMs=50`, `raft.tickIntervalMs=20`,
`raft.electionTimeoutMinMs=1000`,
`raft.electionTimeoutMaxMs=3000`.

In the actual native core path:
- `heartbeatTick=3` -> **60 ms nominal**, corroborated by real-host p50
  around 60–62 ms on the two retained diagnostic runs. The public
  `heartbeatIntervalMs=50` is **not** the actual 50 ms cadence.
- Native base electionTick `ceil(1000/20)=50`, and pre-votes observed at
  ticks 64 and 66, in the native randomized window. This is not evidence
  that the configured 3000 ms max controls the native election window.
- Live millisecond-only `configureTick` left native heartbeatTick=3.
  Configuration acceptance was not proof that the live core changed
  heartbeat/election tick counts; the core's initial config and runtime
  `group.timing` metadata are separate, as previously observed statically.

This is a **measured defect in configuration-to-behavior reporting**, not
permission for this N0 test lane to change Raft algorithms, membership or
time budgets. It belongs to the future one-owner Raft timing contract.

## Remaining work before saying N0 is entirely complete

1. **Real wire boundary**: record on-host MessageRouter/WebSocket frame size,
   physical bytes and RTTs on genuine separate machines, with exact-SHA
   counter provenance and bounded on/off tracing; the measured native
   276-byte heartbeat is *not* physical packet size.
2. **Per-group and per-node breakdown**: measure heartbeat, vote/pre-vote,
   Append/AppendResponse, CDC, transport ACK, ping and snapshot traffic,
   including pressure and timer scheduling delay distribution, not only
   one three-voter group's idle heartbeats.
3. **Native timing owner discrepancy**: retain a versioned desired/effective
   timing report and red test for a changed millisecond-only profile on
   live groups. Do not change the core to satisfy a claim without explicit
   rs-raft owner review and new independently witnessed core behavior.
4. **Multi-group envelope**: measure 100/1000 groups under
   host resource/thermal constraints before extrapolating 100-node
   Veilid bandwidth. Do not multiply the 276-byte observation into a
   customer capacity promise.
5. **Exact main-base compatibility**: the planning branch uses a
   different `package-lock.json` and rs-raft runtime; it was not
   executed on the lab. Bring this test into a stable agreed rs-raft
   base only after that work's acceptance and dependency authorization.
6. **Sealed implementation Quest and certification receipt**: plan N0
   instrument/probe consumers on a frozen accepted baseline with
   explicit source and test scopes, independent reviewers and real
   red negative controls. The private lab job isn't final certification.

**not proof** that production at 16 groups has acceptable p99 response
time. The measured scheduling tail must remain an N3/N5 performance
falsifier when long timing profiles are evaluated; no arbitrary deadline

## N0.8 — measured physical-network scenario readiness

A new `test/distributed/scenarios/n0-physical-network-baseline.js`
runs only within the *existing distributed harness*. It fails closed
unless at least three nodes have **three distinct host identities**
provided by that harness and Docker really uses host-network mode.
It determines which interface reaches the peer host IPs from
`/proc/net/route`, then reads cumulative kernel interface bytes
from `/proc/net/dev` before/after a bounded idle window.
It rejects missing/ambiguous routes, invalid counters and zero observed
traffic. The result distinctly says the interface counters **include
unrelated host traffic** and exclude application-exclusive attribution,
per-peer TCP RTT, and Veilid relay traffic. No guessed physical byte
costs have been substituted.
