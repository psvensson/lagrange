## Today (for the owner): two production mechanisms found by this gate

FACT chain (v1 §1-2, B §1, verified again): partitions run rs-raft only (partition-service-core-base.js:468-470); the client's `BEGIN IMMEDIATE` (partition-service-transaction-base.js:573) and the rs-raft record share the one connection (raft-init-base.js:383, :457 -> raft-rs-runtime-owner.js:1270); while `db.inTransaction && ownTransactionDepth === 0` (raft-rs-durable-store.js:187-191) `perform` refuses every runtime command except READ_STATUS (runtime-owner :1190-1198), and the port's tick timer goes through that gate (raft-rs-operation-port.js:217 -> :203 -> owner :1343).
- **M1: a leader stops ticking under an open client tx -> election in ~1 s.** Correction adopted from B §0: election length is the core's ELECTION_TICK 10 randomised to [10,20) ticks with tick = heartbeat 150 ms / 3 = 50 ms (raft-rs-group-constants.js:13-18; port :47, :73-78), PRE_VOTE and CHECK_QUORUM off; so 500-950 ms after the last heartbeat a joiner campaigns and the other joiner grants. v1's "1-3 s" (raft/constants.js:50-52) is the liferaft-era input and only reaches the port as tick/heartbeat intervals. With CHECK_QUORUM off the stale leader never steps down on its own and answers LEADER from the undrained core (`readStatusNow`, owner :1341-1342) until its first admitted drain.
- **M2: leader self-deadlock on an abandoned session** (B §1, NEW): the hold-sweep heal is deferred while `this.role` is LEADER/CANDIDATE (:385-401, :450-455); `this.role` only changes when a drain announces; a drain needs admission; admission needs the heal. Durability fitness cannot demote (`DEMOTION_UNSUPPORTED`, partition-service-durability-fitness.js:227). A pgwire client that dies with an open tx (no auto-ROLLBACK, C row 2) wedges that replica until process restart; the joiners elect around it; writes routed to it defer 2 s each (constants :49).
- **T-A measured M1 and exposed the stronger M2 consequence.** In two fresh RF=3 lab runs, the staging replica's log, applied index and term stayed frozen for the whole ACTIVE hold while the other replicas elected past it. All four autocommits issued through the holding node were answered after about 2.0 s as definite, non-deferred `DISTRIBUTED_PARTICIPANT_FAILURE`; one joiner-routed autocommit was acknowledged by the new leader. No replica's consensus log shrank across ROLLBACK or COMMIT, so user rollback did not erase acknowledged Raft rows. That literal durability clause passes only because persistence admission excluded consensus writes from the user transaction: the acknowledged row remained absent from the staging replica, which was still frozen 32-70 s after release. More seriously, the client's ROLLBACK did not release the staging replica's SQLite transaction: `STUCK_TRANSACTION_HEAL_DEFERRED` began at BEGIN+60 s and continued, with durability-unfit and successorless-demotion diagnostics. COMMIT again left the transaction row on exactly one replica. The measured witness is F-TX-ACTIVE-OWNS-CONNECTION in `transaction-active-owns-connection.integration.test.js`; raw run detail is in `mechanism-2026-09-26.md`. The predicted `leader_node_id` latency, marker absence, post-release catch-up and rowid collision were not established and are not gate premises.

## 1. Connection/file ownership (unchanged from v1 §1; two additions)

A 3.2 (verified): the checkpoint/install pipeline is dead for partitions at this head: snapshot-checkpoint-store.js:59-60,154 and snapshot-boundary.js:12 read `_raft_state`/`_raft_log`, tables rs-raft never creates. Consequences: the mid-prepared-snapshot question is moot today; `hasPendingPreparedTransactions` (store :195-213) is a PREPARE-marker scan that must read `_transaction_prepared` or be dropped when the pipeline is revived; `_raft_rs_*` are absent from RAFT_CHECKPOINT_EXCLUDED_TABLES (separate owner; flagged). **Correction to A 2.1 from the lab:** a shadow made by `serialize()` copies `_raft_rs_log` and `_raft_rs_snapshot` before the shadow can drop them. The drop makes the shadow semantically clean but does not undo the copied bytes or release pages; at 32 MiB the lab copy stayed 32 MiB after the drop and shrank to 0.04 MiB only after a later `VACUUM`. Therefore BEGIN cost and the cap are full-file/history size, not scrubbed state size. With the rs-raft checkpoint/compaction path dead, that history has no bound at this head.

## 2. Unrelated committed entry while ACTIVE (v1 §2 with B's timeline)

T-A establishes the owner-level fact needed here: the holding replica stops participating in consensus, another leader may commit past it, and closing the application transaction is not proof that the held canonical connection was released or caught up. It does not establish the pre-measurement prediction that a particular marker is absent or that the staging replica catches up after release. The READY_PERSISTENCE 120 s bound remains rare (a Ready is only "taken" inside a core entry). Under the shadow model this interaction disappears because the canonical connection is never inside the client transaction.

## 5. Payload sufficiency (v1 §5, restrictions tightened)

Sufficient with restrictions R1-R5 (v1) plus: **[INV-1] deterministic command identity** `entryId = tx:<sessionId>:<transactionEpoch>:<PREPARE|COMMIT|ABORT>` (A D1, B D4): the pending-write registry, in-flight dedupe (`getPendingCommittedWriteOutcome`, write-metrics :672-675) and the settled-key answer (:693-701) all key on `entry.entryId`; a random id per attempt makes every coordinator retry a new command (a 2PC COMMIT retry would find the prepared row gone -> held group). Digest (A 5.3): SHA-256 over canonical JSON of the ordered `(type, sql, params, entryId)` tuples plus `snapshotIndex`, `expectedPartitionVersion` and the command identity; canonical params encoding is the F-BLOB fix. **[INV-4] write-set keys are PK keys; non-PK-keyed write statements (predicate WHERE on non-PK columns, sub-selects, `x = (SELECT ...)`) are refused inside a transaction at statement time** (recommendation; A 6.1 + B 2a): today `resolveTransactionWriteSetKey` (:158-186) returns null when no PK is derivable (routing-key parse fails, caught :181-183) and `trackTransactionWriteSetKey` silently tracks nothing, so `UPDATE t SET x=1 WHERE y>5` has an empty write set: first-committer-wins would be blind and the replay at index j re-evaluates the predicate against state-at-j (RYOW != committed effect). The resolver already runs in the shadow path, so the refusal is one typed error at staging. The alternative (table-level key `${table}:*`) is Owner Q-A1. Staging dedupe (A D7): a key SETTLED in `_partition_statement_outcomes` is answered from the row without staging; a key already in the batch is answered with the tracked result.

## 6. ACTIVE workspace: shadow database (v1 §6e) with the temporal rules

Design unchanged (per-session copy; client `BEGIN IMMEDIATE`, statements and session reads on the shadow; canonical connection never in a transaction; A 2.1 confirms the copy lacks nothing semantically: no functions/ATTACH/triggers/TEMP anywhere, `foreign_keys` OFF on both). Additions:
- **[INV-2] snapshot mark:** in the SAME synchronous turn as `this.db.serialize()`, read `_raft_rs_applied_state.index` = i (partition-committed-log.js:36-39 `readPartitionAppliedIndex`); the shadow is exactly "state after i"; `snapshotIndex = i` rides in every command (B 2a, A 6.2). `db.backup()` is rejected as the copy primitive: it yields, and under continuous apply from the same connection it is updated in place, so the mark would have to be read at completion; from another connection it restarts (B 2a). Lab addition: `serialize()` preserves SQLite's WAL header bytes `(2,2)`, and better-sqlite3 cannot execute the first statement on that anonymous Buffer (`SQLITE_CANTOPEN`). The owned image must normalize header read/write versions to rollback journal `(1,1)` before opening; measured cost was about 0.003 ms.
- **Copy cost is a liveness hazard (B 2a, NEW):** `serialize()` blocks the event loop; ticks are timer callbacks; a copy longer than ~350-800 ms (election 500-950 ms minus up to 150 ms since the last heartbeat) recreates M1 once per BEGIN. See §13 for the cap and STOP class.
- `:memory:` partitions: `serialize()` works; never reuse the split-accessor live-handle fallback (split-accessor-base.js:314-322) for a shadow (A 2.5).
- Disposal (A 2.4, B §6): idle-shadow expiry replaces the hold sweep's canonical ROLLBACK (:403-411) and its leader carve-out; an expired session is marked locally aborted so a late COMMIT is a typed refusal; per-partition cap on count and bytes with a typed BEGIN refusal (Owner Q-A5); file-backed shadows (if ever used) need a closed-handle boot sweep like `cleanupStaleTransferStaging` (raft-init-base.js:373-374). `isInTransaction()` (:851-856) = "shadows open"; removal drain (`waitForRemovalServingDrain`, :33-58) ignores durable PREPARED rows (A 2.3 iii).
- Two executions, one owner (A 7.1): the shadow result is a preview and a divergence witness, never an input to apply and never the client's final answer for the transaction; the final answer is apply's outcome rows. Where the two can disagree the model fences (schema INV-6, snapshot INV-2, keys INV-4) or declares (rowid under interleaving, non-deterministic SQL R1).

## 7. Durable PREPARE and the isolation machinery (v1 §7, materially amended)

- **[INV-3] epoch = log index** (A 6.2, B 2a; answers v1 §15.1): the coordinator epoch stays identity only; a commit's epoch is its apply `index`; `_row_commit_epochs(key, commit_index)` written by EVERY apply, autocommit included (same key resolver). Conflict at PREPARE/1PC-COMMIT apply at index j: key K conflicts iff `commit_index(K) in (i, j)` or K is in another session's `_transaction_prepared` write set. B's lost-update argument for `UPDATE x=x+1` holds in all three orderings. Retention (A 1, NEW SHAPE): keep the latest index per key (bounded by distinct keys; deleted keys linger); the rule runs inside apply so it is deterministic; a pruned key answers "no conflict" only if pruning is never done (Owner Q-A4 decides latest-per-key forever vs bounded + typed SNAPSHOT_EXPIRED at PREPARE).
- **[INV-5] prepared write sets lock later applies until the decision** (A 4.2, B 2b): while a `_transaction_prepared` row exists, the apply of ANY later command checks its keys against prepared write sets and fails the later command deterministically (PREPARE -> PREPARE_CONFLICT; 1PC COMMIT -> NOT_COMMITTED; autocommit statement -> new deterministic retryable code PREPARED_KEY_LOCKED as its outcome row). Enforced at apply from replicated tables only; a leader pre-check before propose is an optimisation, never the authority. Released only by COMMIT/ABORT apply, never by time (RA; the participant hold sweep's 60 s release goes away).
- PREPARE apply (A 4.2 exact): (1) settled-key check on `tx:..:PREPARE`; (2) conflict check vs `_row_commit_epochs` and vs other sessions' prepared keys; (3) SAVEPOINT, run each op, capture `changes`, ROLLBACK TO, RELEASE (dry-run); (4) write `_transaction_prepared(session_id, transaction_epoch, log_index, term, digest, snapshot_index, write_set_json, operations_json, changes_json, prepared_at)`; (5) outcome PREPARED. A deterministic failure in (2)/(3) = PREPARE_CONFLICT/PREPARE_FAILED, no row. 2PC residual (A 4.2, B §5): PK locks do not cover secondary UNIQUE/CHECK violations created by a later entry on a non-write-set key, so a COMMIT apply can fail deterministically after the global decision. Options: (a) also lock the touched unique-column values carried from the shadow post-image; (b) narrow the 2PC promise to PK-keyed writes on tables without cross-row constraints, with a typed mixed outcome `COMMIT_DIVERGED` (coordinator COMMITTED final; participant records COMMIT_DIVERGED, never retried nor rolled back; operator alert; client not told committed on that participant). Owner Q-A2/Q-B3; recommendation (b) first, (a) as a successor.
- **[INV-6] schema fence via last-DDL index** (A 2.2, NEW): `MIGRATION_ALTER_TABLE` is an ordinary proposed write (entry-apply-base.js:873-887) applied to the canonical while the shadow keeps the BEGIN-time schema; `PRAGMA schema_version` is a per-file cookie and cannot be the fence. The MIGRATION_ALTER_TABLE apply writes a partition-owned `_schema_generation(last_ddl_index)`; PREPARE/1PC-COMMIT apply refuses with typed SCHEMA_CHANGED (no mutation) when `last_ddl_index > snapshotIndex`.
- Partition version (A 2.3 i): each staged statement is fenced at delivery by `rejectStalePartitionEpochWrite` (entry-apply-base.js:573-600, :683-688) against the system cache; the command carries the single `expectedPartitionVersion` the batch was staged under (a mixed batch is refused at staging) and prepare/commitTransaction re-run the same fence at proposal admission on the leader, NOT at apply (the cache is not replicated state).
- Delete `preparedTransactions`, `preparedStateLostSessions`, `activeTransaction`/`transactionOperations` aliases (session-methods.js:44-69), `reconstructPreparedState` (:67-140), `committedWriteLog`/`rowCommitEpoch`/`isSnapshotExpired` (A 1): all replaced by tables. `activeTransactions` stays as the shadow registry (process-local by design): a PREPARE/COMMIT at a leader with no shadow, no prepared row and no outcome row answers typed NOT_COMMITTED and proposes nothing (A 1).

## 8. 1PC command (v1 §8 + timing)

`TRANSACTION_COMMIT {entryId: tx:S:E:COMMIT, sessionId, transactionEpoch, snapshotIndex, expectedPartitionVersion, operations[], writeSet, digest, timestamp, proposedBy, proposedAt}`; apply: settled key -> outcome row for (S,E) (COMMITTED: idempotent replay; ABORTED: NOT_COMMITTED, no mutation) -> conflict/lock/schema checks -> SAVEPOINT batch -> per-op outcome rows + command row + `_transaction_outcomes` COMMITTED + `_row_commit_epochs` -> afterCommit: resolve (ack) and per-op side-effect plan. Rounds (B §3): today 5 + 2n system-partition rounds and zero data-partition rounds; model = 6 + 2n; the two participant rows and the per-statement rows are observability and can be dropped to 3 rounds (ACTIVE, batch, COMMITTED): Owner Q-B5. **[INV-9] timeouts after hand-off -> UNKNOWN/deferred, never ABORT/FAILED** (B §3, 2c): tx-op delivery is 15 s (sql-query-engine.js:35) < pending write 30 s (constants :19), so the coordinator abandons the message while the batch is pending; the retry rebuilds the SAME entryId (INV-1) and is answered idempotently; `COMMIT_DEADLINE_EXCEEDED` ("handed to consensus, may still commit", cdc-stream-base.js:280-290) must surface as `PARTICIPANT_COMMIT_OUTCOME = UNKNOWN`, not as the write's failure (raft-write-commit.js:170-178); once the batch has been handed to consensus (1PC) or COMMITTING is durable after PREPARED (2PC), `abortTimedOutTransaction(tx, COMMITTING)` (protocol.js:305-311) becomes deferred/UNKNOWN re-driven by the sweep. Recommend splitting the 60 s budget into ACTIVE (client think time) and COMMIT (aligned to the 30 s pending deadline): Owner Q-B6.

## 9. 2PC commands (v1 §9 + fail-closed rules)

PREPARE as §7; `TRANSACTION_COMMIT {entryId: tx:S:E:COMMIT, sessionId, transactionEpoch, digest, decision: COMMIT}`; `ROLLBACK {entryId: tx:S:E:ABORT, ...}`. **[INV-10] fail-closed ABORT/COMMIT apply from the outcome row** (A 5.4, B 4e): apply order = settled command key -> `_transaction_outcomes` (COMMITTED: COMMIT answers idempotent success, ABORT refuses; ABORTED: ABORT idempotent, COMMIT refuses NOT_COMMITTED) -> prepared row present: confirm digest, compare per-op `changes` with the PREPARE vector (mismatch = state moved under a lock = divergence, §10 policy), apply, clear the row -> none of the three: fail closed (true skew). v1's "missing prepared row = version skew" was only the last arm. COMMIT apply emits CDC for its partition while the other participant is pending: cross-partition atomic visibility is not promised and is stated (B §5).

## 10. Outcome reconstruction after process/leader loss (v1 §10 + committed-read rule)

**[INV-7] every TRANSACTION op is leader-bound with redirect + re-pin + epoch fence** (A D6, B D3): `handleTransactionMessage`/`executeTransactionControl` (entry-apply-base.js:384-446) get the `handleRemoteQuery` :690-706 shape (LEADER_REDIRECT + leaderAddress; the router re-pins, partition-delivery :330-341); BEGIN leader-binding is an invariant, not an option (closes C §5's routing fork and A 5.2's same-entryId case). **[INV-8] outcome reads only from a quorum-confirmed leader with applied >= commit, else UNKNOWN** (B 4d, D7): a status read can interleave between commit and apply across a Ready's async send, and with CHECK_QUORUM off a partitioned stale leader would answer NOT_COMMITTED for a tx the new leader committed. This is O1/O2's committed-read owner; until it lands this quest carries the interim rule "UNKNOWN unless quorum-confirmed" (Owner Q-B8). Authority asymmetry stated (A 4.1): 1PC = the participant's `_transaction_outcomes` row IS the decision and the coordinator row is derived; 2PC = the coordinator's COMMITTING row is the decision and participant outcomes are obligations. Delete protocol.js:584-586. Dead coordinator (B 2d): FACT, the recovery loader `loadDistributedTransactionRecoveryState` (sql-query-engine-transaction-recovery-methods.js:152-159) reads ALL `sql_transactions`/participant/write-op rows from the system cache with no node filter, so every node's sweep adopts every non-terminal row (budget filter recovery.js:404-411); the missing piece is not adoption but (i) concurrent re-drive from several nodes (safe only under INV-1 idempotent commands) and (ii) the lock lifetime: decision no earlier than budget 60 s + defer 1-30 s + election ~1 s ≈ 62-91 s of key lock (reads never blocked). Recommendation: keep the sweep as the decider (PREPARED without COMMITTING -> ABORT is safe), make the re-drive explicitly idempotent, and put a lock-age tripwire in the partition (Owner Q-B4). T-C both directions as v1.

## 11. CDC and post-commit effects (v1 §11 + the full side-effect plan)

One path: per-op `generateCDCEvent` from the batch apply's afterCommit on the leader (entry-apply-base.js:1102-1117 shape); delete transaction-base.js:707-709. Ordering (B §5): SQLite commit (batch + outcome rows + `_row_commit_epochs` + applied index) -> afterCommit: resolve (ack) and CDC; CDC locally observable before the client sees COMMITTED is acceptable because the durable outcome precedes it in the same commit. **The batch must run the whole per-op side-effect plan, not CDC alone** (A 2.3 ii, 7.2; B 2f): `applyWriteSideEffectPlan` :751-767 feeds `handleSplitReplicationAfterWrite` (split-accessor-base.js:466-490; SPLIT_CATCHUP delta queue / CUTOVER_ACTIVE mirror, `cloneSplitEntry` :498 clones per `sql`) and `handleMergeReplicationAfterWrite` (merge-replication-methods.js:525-545), `scheduleSizeUpdate`, managed-split evaluation; a batch command has no top-level `sql`, so the mirror clones the per-op entries by routing key, or the split target misses transactional rows (today's defect reappearing one hop over). **[INV-11] split/merge fence + per-op mirror:** the epoch fence applies to BEGIN/PREPARE/COMMIT (§7) and split/merge cutover readiness is gated on an empty `_transaction_prepared` (bounded by the lock lifetime; rebalancer re-checks every 60 s). Failure isolation unchanged (effects isolated, application-transaction-owner.js:19-29).

## 12. Provider neutrality (v1 §12 confirmed by A 7.4)

Surface = `readStatus`, `propose`, `applyCommittedEntry({command,index,term,effects})`, `store.transaction` atomicity; SAVEPOINT inside it is host SQL; callback synchronous. No rs-raft change. Open bound: max entry size (look up the core config; cap the batch in bytes). liferaft: dead path.

**[INV-12] divergence policy for a non-leader deterministic failure** (B 4b, A 4.2): outcome rows are per-replica; no replica can compare them. Any deterministic batch failure on a NON-leader (or a `changes`-vector mismatch at 2PC COMMIT apply) is divergence evidence: persist a divergence flag in the file, hold the group (existing fail-closed semantics, runtime-owner :812-822), surface to the rebalancer for replacement. Never "continue with STATEMENT_FAILED" silently. Deterministic failure on ALL replicas (the leader included) is the ordinary NOT_COMMITTED outcome.

## 13. STOP assessment (the copy cap)

The shadow copy must be synchronous `serialize()` under a byte cap read in the same turn as the applied index (INV-2). Liveness bound: the whole synchronous BEGIN path must stay below 350 ms to remain inside the leader's heartbeat slack (B 2a: election 500-950 ms minus <= 150 ms). The lab measured the real full-file path under a public-session apply stream: serialize, two-byte WAL-header normalization, open, and drop all `_raft_rs_*` tables. A history-shaped `_raft_rs_*` fixture supplied the bytes without mutating real Raft records.

| host | image | serialize | open | scrub | usable total | 350 ms |
|---|---:|---:|---:|---:|---:|---|
| lenovo-laptop | 32.18 MiB | 34.15 ms | 18.78 ms | 15.76 ms | 68.69 ms | pass |
| lenovo-laptop | 128.43 MiB | 112.61 ms | 66.36 ms | 31.22 ms | 210.19 ms | pass |
| lenovo-laptop | 256.68 MiB | 243.85 ms | 135.31 ms | 56.91 ms | **436.08 ms** | **fail** |
| tv-dator | 32, 128, 256 MiB targets | measured | measured | measured | all below 350 ms | pass |

The controller preserves exact JSON on each lab host; the explicit f1ff6e6d2 gate made the cross-host decision visible. The 32 MiB copy's post-drop page count was unchanged; a subsequent 1.30 ms `VACUUM` reduced the shadow from 32.18 MiB to 0.04 MiB, too late to reduce BEGIN's allocation or copy. The timing harness runs the synchronous SQLite copy from a second process so public apply continues; T-A separately establishes what a blocked partition event loop does to consensus.

This resolves the former UNPROVABLE-STATICALLY question. The default managed split storage threshold is 10 GiB, not <= any cross-fleet-safe measured cap, and traffic can split independently. More importantly, the dead rs-raft compaction pipeline means full-file history can cross a cap even when live application state is small. The 32 MiB proposal is safe in these two measurements, but adopting it would mean explicit transactions silently disappear for larger or older partitions. That is the weaker contract the directive disallowed.

**Gate verdict: STOP before implementation.** A transaction-base-only shadow cannot provide the promised contract through the partition lifecycle. Resume only after the owner chooses a larger workspace owner (paged/overlay snapshot or revived rs-raft compaction with a partition-size invariant), or explicitly changes the product contract to refuse transactions above a full-file cap. No such weaker contract is proposed here.
