## 0. One correction to the inputs (FACT)

Partitions build their consensus port with **no provider selection**: `partition-service-core-base.js:56` `RAFT_RS_PROVIDER = Object.freeze(new RaftRsWasmProvider())` and `:468-470` `createOperationPort(request) { return RAFT_RS_PROVIDER.createPartitionPort(request); }`. `liferaft-provider.js:190 createPartitionPort` has **no caller** in src, and `new PartitionRaftStorage(...)` is constructed nowhere (index.js export only); `SQLiteLogAdapter` is only built by the worker services on their own log DB (message-group-worker-service.js:296, partition-worker-service.js:242). So every "per provider" answer below is: **rs-raft is the only live partition backend**; the liferaft shared-connection log is a dead path for partitions at this head and is answered only as "what the model must remain correct under if it is ever re-wired".

Invariant 0 today: the open client tx and Raft persistence/apply share one connection and one file. rs-raft refuses to join it: `persistenceAdmission()` durable-store :187-191 (`db.inTransaction && ownTransactionDepth === 0` -> USER_TRANSACTION_OPEN), enforced on every store write (:196-205) and, at the runtime, on every port command except READ_STATUS (`perform`, runtime-owner :1190-1198), on inbound drain (:1249-1251), on group reconstruction (:601-603), and a Ready already taken waits up to `BOUND_MS: 120000` (runtime-owner-constants :133-136) then a READY_PERSISTENCE host failure (:318-319). Ticks enter through the same gate: port :217 `execute({type:'tick'})` -> :203 dispatch -> owner :1343 `perform(group, command)`. **So the client tx never encloses Raft persistence or apply (A4 achieved that), but it makes them WAIT, and on a leader it stops ticks/heartbeats/inbound for the tx's lifetime.** That is the half of Invariant 0 ("apply must not wait behind / be owned by the client tx") that is violated today. Under liferaft it would be the other half (joined and erasable, C §6), unreachable at this head.

## 2. Unrelated committed entry while a client tx is ACTIVE (rs-raft)

FACTS: (a) holder = leader (normal routing): another session's write reaches `applyWrite` -> `startPartitionRaftWriteCommit`; `proposeUnlessDeferred` (raft-write-commit.js:40-60) sees HOST_FAILURE/USER_TRANSACTION_OPEN, retries for `USER_TRANSACTION_WRITE_DEFER_BUDGET_MS` = 2 s (constants :49), then answers `WRITE_DEFERRED_USER_TRANSACTION_OPEN` with `deferRetry` (:85-94) to the router. No entry can commit anywhere because the only proposer is gated. (b) holder = follower (BEGIN staged on a follower, C §5): the leader commits with the other follower; the holder queues inbound (:1249-1251) and applies after the tx ends; nothing of it enters the client's transaction (store.transaction refused, not nested). Neither case runs apply inside the client tx, so ROLLBACK cannot erase it.

UNPROVABLE-STATICALLY: whether the leader's inability to tick for >1-3 s (election 1000-3000 ms, raft/constants.js:50-52; heartbeat 150 ms) makes the followers elect a new leader mid-transaction. If yes (my reading of raft-rs: followers campaign on their own election tick), the sequence is: new leader commits the unrelated write with the two followers; the old leader drains and applies it after the client's ROLLBACK/COMMIT; the client's later COMMIT still commits locally (:697, no role check) but `proposeTransactionMarker` returns at :941-943 (not LEADER) so no marker is proposed; if the tx's rows collide with rows committed meanwhile, this replica's later apply fails SQLITE_CONSTRAINT deterministically and records STATEMENT_FAILED where the others recorded APPLIED (statement-outcome constants :56-62): silent divergence of both rows and outcome rows.

Prediction for T-A (untracked witness `test/integration/transaction-active-owns-connection.integration.test.js`, 20 s hold, ROLLBACK then COMMIT variants, autocommit INSERTs from a second seed session and a joiner): the two autocommit rows end on all three replica files in both variants, i.e. "an acked write survives client rollback" **passes today**; either they commit during the hold on a newly elected leader (seed file catches up after release) or they are deferred/timed out (30 s PENDING_REQUEST_TIMEOUT, constants :19) and only commit after release. What T-A will show instead: the leader-liveness cost (deferrals, `_raft_rs_hard_state.term` increment on the joiners, `partitions.leader_node_id` change) and, in the COMMIT variant, the tx row on the seed file only with no TRANSACTION_COMMIT marker in any log if leadership moved. Measurement to record: term before/after on each replica, per-insert answer + latency, seed applied index during the hold.

## 3. The canonical commit/apply owner (FACT)

`applyWrite` (write-metrics-base.js:657-735): `buildPartitionWriteEntry` :659 -> pending-outcome dedupe :672-675 -> `admitCommittedCommand` (origin WRITE_PATH) :678-687 -> settled-key answer from the outcome row `answerSettledWrite` :693-701 (idempotent retry, no new log entry) -> commit mode from `raft.readStatus()` :704-709, REJECTED unless leader :712-720 -> `startPartitionRaftWriteCommit` (raft-write-commit.js:217-231) -> `executePartitionRaftWriteCommit` :108-215: register the pending answer keyed by entryId with a 30 s deadline (`waitForCommittedWrite`, cdc-stream-base.js:266-300) -> `proposeWithinDeferralBudget` :66-80 -> `raft.propose(entry)` :47 -> await the commit promise :169 -> side-effect plan with `emitCdcEntry: null` :188-198 (CDC belongs to apply) -> `acknowledgedResult` with the durable commit witness.
Apply (`applyCommittedEntry`, entry-apply-base.js:1017-1152) for SQL types: entry key `entry:${entryId}` (:1064; cdc-stream-base :369-385) -> settled key never re-executed :1070-1076 -> `db.prepare(sql).run(...params)` :1079 -> deterministic vs environment failure classification (statement-outcome.js:143-152; codes constants :56-62; environment = fail closed, redelivered) -> outcome row in the same transaction :1086-1091 -> afterCommit: `resolveCommittedWrite(entryId, {changes, lastInsertRowid, witness})` :1096-1101 and CDC `if (this.isLeader)` :1102-1117. Typed outcomes: deferral (USER_TRANSACTION_OPEN), proposal refusal, COMMIT_DEADLINE_EXCEEDED release (cdc-stream-base :280-290), leadership refusal, STATEMENT_FAILED reported as the write's failure (raft-write-commit :170-178).
Atomicity: rs-raft `applyCommittedEntryTransaction` (application-transaction-owner.js:41-63) runs `applyCommittedEntry` + `putAppliedState` in ONE `store.transaction`; any throw rolls back all of it, runs afterRollback effects, and the runtime holds the group (runtime-owner :812-822). afterCommit effects run only after the SQLite commit, isolated (:19-29). liferaft (dead path): `prepareCommitApply` -> `applyCommittedEntry` with an effects bag (liferaft-provider.js:210-216, commit-scheduler :44-45) but no store transaction.
Generalizable to a batch: **yes**. The propose/await/idempotency/witness/ack unit is command-agnostic (it keys on `entry.entryId`); only the apply branch is per-`command.sql`. A batch branch that executes `command.operations` in order inside the same apply transaction gets all-or-nothing for free under rs-raft. One addition is needed for "statement k fails deterministically": statements 1..k-1 already ran inside the store transaction, so the batch must run under a SAVEPOINT (better-sqlite3 nests `db.transaction` as a savepoint; the durable-store comment :203 relies on that) so the ops roll back while the command's failure outcome row and the applied index still commit. Under liferaft the partition apply would have to open its own `db.transaction` when `!db.inTransaction` (partition-side, provider-neutral; irrelevant today).

## 5. Are canonical write entries sufficient as the batch? (audit)

Shape (FACT): `{type: QUERY (engine SQL) | INSERT/UPDATE/DELETE/UPSERT (+tableName,data,whereClause) | ..., sql, params, entryId, operationId, idempotencyKey, splitMirrorOrigin, sessionId, timestamp (HLC string), proposedBy, proposedAt}` (write-metrics :96-109, :203-213; write-kernel :155-171) plus the tracked `changes` (:217). Replay is literally `db.prepare(sql).run(...params)` on every replica (:1079); encoding is `JSON.stringify` (raft-rs-proposal-codec.js:34).
- Non-deterministic SQL: no guard anywhere (grep). The pg layer even rewrites `NOW()/CURRENT_TIMESTAMP` to `datetime('now')` (pg-function-registry.js:89-90,175), so a pgwire INSERT with NOW() diverges across replicas **already today for autocommit writes**. The batch inherits exactly the autocommit determinism contract; it is not worse. `random()`, `datetime('now')`, `DEFAULT CURRENT_TIMESTAMP` columns, `last_insert_rowid()` called *inside* SQL are the divergent constructs; rowid/AUTOINCREMENT assignment is deterministic given identical prior state, which replication provides.
- Read-modify-write: the batch is the statements, not the reads; values the client computed from workspace reads are bound as params -> deterministic. `UPDATE ... SET x = x + 1` is deterministic given identical prior state; whether that prior state is the one the client saw is the isolation question (7/15), not a determinism one.
- BLOB params (F-BLOB): `JSON.stringify(Buffer)` -> `{type:'Buffer',data:[...]}`, an object better-sqlite3 cannot bind -> TypeError -> classified deterministic binding failure (constants :72-76) -> STATEMENT_FAILED on every replica while the leader's workspace `stmt.run` with the real Buffer succeeded. Inherited defect; must be fixed at the entry/codec level for both paths.
- Binding equivalence: positional arrays round-trip; integers > 2^53 lose precision in JSON; both workspace (:216) and apply (:1079) spread `params` identically, so parity holds for anything JSON-representable.
- `changes`: the tracked value is leader-workspace evidence; apply recomputes `info.changes` per op. PROPOSAL: use it as a cheap divergence witness (mismatch at apply -> typed host failure, group held, never silently continue). Owner decision.
Conclusion: **sufficient with named restrictions**: (R1) same determinism contract as autocommit, to be documented and later guarded at parse time in one place for both paths; (R2) no BLOB params until F-BLOB is fixed at the codec/entry; (R3) per-op `changes` advisory or a divergence witness; (R4) each op keeps its own entryId (per-op outcome rows) and the command has its own; (R5) the digest is over the ordered `(type, sql, params-JSON, entryId)` tuples. No new row-mutation language.

## 6. ACTIVE transaction workspace (PROPOSAL, with facts)

Facts that bound the design: WAL (writers serialize; readers never block writers); no `busy_timeout` anywhere (C), so a SQLITE_BUSY at apply is an environment failure -> apply held and redelivered (statement-outcome.js:143-152); a second connection to the replica file is an existing pattern: `openSplitSnapshotDatabase` (split-accessor-base.js:314-327) opens `new Database(dbPath, {readonly:true})` + `BEGIN` as a snapshot reader and falls back to the live handle for `:memory:` partitions; whole-file copies exist as `db.backup()` (snapshot-checkpoint-store.js:269); reads inside a tx are already a branch (`applySnapshotReadFilter`, write-metrics :77-82) and writes are already a branch (:113-119); a session is pinned to the BEGIN address (query-executor-partition-delivery.js:337-341) so all its statements reach one replica.
- (a) Second connection B, `BEGIN IMMEDIATE`: B holds the WAL write lock for the tx's life -> apply on A gets SQLITE_BUSY -> apply waits (held/redelivered) behind the client tx: **violates Invariant 0's wait clause; rejected**. B with `BEGIN` (deferred) and reads only: a true consistent snapshot at BEGIN (better than today's row filter) that never blocks apply; but the first client write needs the write lock, so the writes must live elsewhere -> (a) alone is not a workspace; it is the read half of (e).
- (b) Per-tx scratch DB seeded copy-on-read: UNIQUE/PK/CHECK fidelity needs the whole key space, and arbitrary WHERE cannot be seeded by predicate -> either copy the whole table (then it is (e)) or accept false accepts at statement time with the real failure at COMMIT apply (semantics change: error moves from statement to COMMIT). Rejected as primary.
- (c) Record without executing, overlay on reads: SQL rewriting/merging for RYOW, constraint dry-runs on a snapshot; highest complexity, smallest SQL subset. Fallback only.
- (d) SAVEPOINT on the canonical connection (unused `SAVEPOINT_PREPARE`, constants :105): a SAVEPOINT opens a transaction on `this.db`; `db.inTransaction` becomes true; the rs-raft admission refuses every command exactly as today. **Rejected by Invariant 0**; identical to the status quo.
- (e) **Shadow database per session (recommended)**: at participant BEGIN, copy the partition state (`this.db.serialize()` -> `new Database(buffer)` in memory for small partitions; `db.backup(tempPath)` -> file for large ones; both work for `:memory:` and file partitions) and run the client's `BEGIN IMMEDIATE`, all statements and all session reads on the **shadow** connection. The canonical connection is never in a transaction, so apply, ticks, proposals and heartbeats are unaffected; open tx + unrelated apply + ROLLBACK trivially leaves committed state intact (the shadow is discarded). Validation, constraints, RYOW, result metadata (`changes`, `lastInsertRowid`) are exact SQLite semantics; isolation is a physical snapshot at BEGIN (strictly stronger than today's `rowCommitEpoch` filter, which autocommit writes never populate: `rowCommitEpoch.set` only at transaction-base :714). The write-set tracker (:158-197) and the ordered `operations[]` are produced exactly as today; COMMIT/PREPARE ship the batch, never the shadow rows. Hosting owners: a new `partition-transaction-workspace.js` under the transaction base; the snapshot/copy owners (snapshot-checkpoint-store, split-accessor's snapshot reader) for the copy; `preparePartitionReadStatement` is keyed per handle (read-statement-owner.js:1-20) so it works on the shadow; the schema cache/`createTable` is not needed (the copy carries the schema). Residual: rowid/AUTOINCREMENT values seen in the shadow can differ from apply if an autocommit write interleaves (see 5/R3 and 15). UNPROVABLE-STATICALLY: copy cost per BEGIN vs partition size (measure `serialize()`/`backup()` latency and bytes on the storage-load soak sizes and on the split threshold); if the owner rejects the cost there is no cheaper workspace that preserves SQL semantics, and the honest answer is STOP or (c) with a restricted SQL subset.

## 7. Durable PREPARE representation (PROPOSAL)

Carry the **complete ordered canonical batch in the PREPARE command** (`operations`, `writeSet`, `transactionEpoch`, `digest`); no staged-batch reference exists (the shadow is process-local) and a replicated reference would first require replicating the same bytes. Prepared state lives in a partition-owned replicated table written by the PREPARE apply inside the apply transaction, e.g. `_transaction_prepared(session_id, transaction_epoch, log_index, term, digest, write_set_json, operations_json, prepared_at, PRIMARY KEY(session_id, transaction_epoch))`, cleared by the COMMIT/ABORT apply. A new leader reconstructs `preparedTransactions` from that table (replacing `reconstructPreparedState` :67-140 and its rs-raft-only `readPartitionCommittedCommands`, partition-committed-log.js:24-27). Conflict evidence: today `checkWriteConflicts` (:205-232) reads the in-memory `committedWriteLog`, populated only by `commitTransaction` (:721), lost at leader change, blind to autocommit. Make it replicated: the COMMIT apply writes `(write_set_key, commit_epoch)` rows to a replicated `_row_commit_epochs`, and the first-committer-wins check runs **at PREPARE apply** (deterministic on every replica against replicated state); its result is the PREPARE outcome (PREPARED or PREPARE_CONFLICT) reported to the coordinator from the afterCommit effect. The BEGIN-time refusal (13) and the epoch source (15) hang off this.

## 8. 1PC command (PROPOSAL)

`TRANSACTION_COMMIT {type, entryId, sessionId, transactionEpoch, operations: [canonical entries, each with its own entryId], writeSet, digest, timestamp, proposedBy, proposedAt}`. Path: coordinator `commitParticipant` -> participant `commitTransaction` closes the shadow, builds the command, and calls the canonical unit (`startPartitionRaftWriteCommit` behind the same admission (origin TRANSACTION_OWNER), settled-key answer for `entry:${command.entryId}`, leader-only commit mode). Apply executes the batch under a SAVEPOINT inside the apply transaction, writes one `_partition_statement_outcomes` row per op and one for the command, the `_transaction_outcomes` COMMITTED row and the `_row_commit_epochs` rows, then afterCommit resolves the pending write with the durable witness. COMMITTED is reported to the coordinator only from that afterCommit on the serving participant: by construction "quorum committed AND this participant applied AND the outcome row is durable" is one SQLite commit. A deterministic statement failure at apply = the command's STATEMENT_FAILED row, no mutation, `_transaction_outcomes` NOT_COMMITTED, and the participant reports the failure; an environment failure holds the group and redelivers (unchanged).

## 9. 2PC commands (PROPOSAL)

- `PREPARE_TRANSACTION {entryId, sessionId, transactionEpoch, operations, writeSet, digest, ...}`: apply = conflict check against `_row_commit_epochs`, write `_transaction_prepared` (or a PREPARE_CONFLICT outcome), touch no application rows; afterCommit answers the participant's pending write; prepare success = PREPARED durable on a quorum and applied here.
- `TRANSACTION_COMMIT {entryId, sessionId, transactionEpoch, digest, decision: COMMIT}` (no operations): apply reads the prepared row (it exists on every replica because PREPARE precedes COMMIT in log order; a missing row is version skew -> fail closed like UNRECOGNISED :1041-1056), confirms the digest, runs the identical batch routine of §8, records outcome rows, deletes the prepared row, stages CDC/resolve in afterCommit. **One transition, one owner** for 1PC and 2PC: `applyTransactionBatch(ops, identity)` inside `applyCommittedEntry`.
- `ROLLBACK {sessionId, transactionEpoch}` (ABORT): apply deletes the prepared row and writes `_transaction_outcomes` ABORTED; applies nothing. RECORDED_ONLY for PREPARE/ROLLBACK (:1146-1151) disappears.

## 10. Participant outcome after process/leader loss (PROPOSAL over facts)

Durable states, all from replicated tables: `_transaction_outcomes` COMMITTED -> COMMITTED; `_transaction_prepared` row and no outcome -> PREPARED/UNKNOWN; ABORTED row -> NOT_COMMITTED; neither row -> NOT_COMMITTED **only** when the answering replica is the current leader whose applied state covers its commit index (otherwise UNKNOWN). Today TRANSACTION_OUTCOME goes to the session-pinned address (partition-delivery :337-341; the pin clears only on a successful COMMIT/ROLLBACK, sql-query-engine.js:561-562), so a follower can answer NOT_COMMITTED for a committed transaction (C §2); the handler (:875-902) must answer UNKNOWN + `LEADER_REDIRECT` when not leader (same redirect shape as handleRemoteQuery :690-706) and read only the tables (drop `preparedStateLostSessions`/open-map inputs). Remove `protocol.js:584-586` (2PC miss -> COMMITTED unconditionally): the resolver is always wired (instance-initializer.js:219-230), so both modes use it. The participant hold sweep must stop ROLLBACK-ing durable PREPARED state by elapsed time (:375-448); only the coordinator's decision (or its recovery sweep, recovery.js:365-505) may ABORT. T-C(i): COMMITTED row durable, process restarted, maps gone -> COMMITTED. T-C(ii): prepared row durable, no COMMIT applied -> UNKNOWN, coordinator stays COMMITTING and re-drives; never COMMITTED. Collides with O1/O2 (committed-read owner decisions): the "leader answers from applied state" rule is that decision's territory.

## 11. CDC after authoritative apply (PROPOSAL over facts)

Today: transactional CDC from `commitTransaction` :707-709 on the staging replica before/without consensus (M, measured -30 ms); autocommit CDC from apply :1102-1117 leader-only. Proposal: delete :707-709; the batch apply's afterCommit runs, per op, the same `if (this.isLeader) trackPendingCDCEvent(generateCDCEvent({...op, changes: info.changes}))`. The generator re-reads INSERT rows by primary key (partition-sql-parser.js:189) and runs after the SQLite commit (effects order: application-transaction-owner.js:62-63), so it sees applied rows. Order: command committed by quorum -> batch applied + outcome rows + applied index in one commit -> afterCommit: resolve (ack) and CDC. Failure isolation: effects are isolated (:19-29) and CDC failures are logged (:1105-1115); nothing rolls back. Known inherited limit: a follower that becomes leader never emits CDC for entries it applied as a follower (same as autocommit today).

## 12. Provider-neutrality check

Every step uses only: `raft.readStatus()` (leader gate), `raft.propose(entry)` (raft-operation-port.js:5-16), the `applyCommittedEntry({command,index,term,effects})` callback, and partition-owned tables (`_transaction_outcomes`, `_partition_statement_outcomes`, new `_transaction_prepared`, `_row_commit_epochs`, application tables). The shadow workspace never touches `this.db` in a transaction. rs-raft needs **no change**: apply atomicity is given by `store.transaction` (application-transaction-owner.js:41-63); a SAVEPOINT inside it is ordinary better-sqlite3 nesting; JSON payloads already carry `operations[]` (M: the marker with both ops sits in every `_raft_rs_log`). Flags: (i) entry size: a batch is one proposal; the rs-raft max entry/message size is UNPROVABLE-STATICALLY here (look up the core's `max_size_per_msg`/`max_uncommitted_size` config in raft-rs-runtime-owner; bound the batch in bytes and refuse beyond, owner decision). (ii) liferaft (dead path) has no apply transaction: the partition apply would wrap the batch in its own `db.transaction` when `!db.inTransaction`; partition-side, no provider edit. (iii) Dropping `readPartitionCommittedCommands` from the tx owner removes an rs-raft-table coupling. (iv) Nothing here needs `applyTransactionRolledBack` or the persistence admission to change; they remain provider-internal facts the model is correct under.

## 13. The 40 s / "Transaction already active on this partition" refusal

FACT: `beginTransaction` :560-565 refuses a second session because the ONE connection can hold one `BEGIN IMMEDIATE`; the 60 s hold sweep, its leader carve-out (:385-401, "re-mints acked indices") and durability fitness exist to recover that held connection by elapsed time (C §5; the ~40 s outage did not reproduce, M step 4). PROPOSAL: with a shadow per session the refusal loses its reason: N sessions = N shadows; conflicts are decided at PREPARE/COMMIT apply (first-committer-wins) with a documented typed conflict outcome for the loser (acceptance J); idle shadows are discarded by the sweep with no consensus effect (no ROLLBACK on the canonical connection, so the leader carve-out and the "hold >= 60 s => unfit" rule become moot for transactions). Whether to cap concurrent shadows (memory) is an owner decision.
