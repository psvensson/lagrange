## 0. Correction to the gate's timing premise (NEW SHAPE)

The 1000-3000 ms election window (raft/constants.js:50-52) and the per-replica jitter are liferaft-era inputs: `raftTimingConfig` (raft-init-base.js:411-436) reaches the rs-raft port only as `tickIntervalMs`/`heartbeatMs` (port :74-78, `configureTiming` :260-268); election length is the core's fixed ELECTION_TICK 10, randomised by raft-rs to [10, 20) ticks = **500-950 ms** after the last heartbeat; heartbeats every 3 ticks = 150 ms. Every "1-3 s" below in the gate is 0.5-1 s. With CHECK_QUORUM false a leader never steps down on its own; it only learns of a higher term by stepping a message.

## 1. Today's leader liveness under an open client tx (T-A mechanism; FACT + predicted timeline)

Predicted timeline (seed = leader, joiners J1/J2, 20 s hold):
- t0: participant `BEGIN IMMEDIATE` (transaction-base :573). Last heartbeat left <= 150 ms earlier.
- t0+50 ms..: every tick deferred (debug-level; not in the warn-level capture the witness keeps).
- t0+0.65-1.1 s: a joiner's election elapses (500-950 ms since its last heartbeat); it campaigns at term+1, the other joiner grants (PRE_VOTE off, no seed vote needed): new leader at t0+~0.7-1.2 s. - seed-session autocommit INSERT: applyWrite reads undrained LEADER (:704-709) -> `propose` -> USER_TRANSACTION_OPEN deferral retried 2 s (raft-write-commit :66-80) -> `WRITE_DEFERRED_USER_TRANSACTION_OPEN` + deferRetry (:85-94); latency >= 2 s per attempt; whether the router's retries re-resolve to the new leader before exhausting attempts decides ack-in-hold vs ack-after-release. - t0+20 s release: `ROLLBACK`/`COMMIT` frees the connection; the next tick (<= 50 ms) is admitted; `perform` drains inbound FIRST (:1199-1203): the seed steps term+1, becomes FOLLOWER, announces, then applies the queued AppendEntries -> the autocommit rows land on the seed file; seed term +1 after release.
- COMMIT variant: :697 local COMMIT succeeds (no role check) -> `proposeTransactionMarker` :941 reads the still-undrained LEADER -> `raft.propose` enqueued -> admitted -> drain makes it a follower -> raft-rs drops the follower's proposal -> debug log. Result: tx row + `_transaction_outcomes` COMMITTED on the seed only; no marker in any log; if the tx INSERT consumed a rowid/PK the autocommit rows also use, the seed's later apply of those entries fails SQLITE_CONSTRAINT (STATEMENT_FAILED on the seed, APPLIED on J1/J2) or, with implicit rowids, the same logical autocommit row gets different rowids on the seed vs the joiners (T-D physical inequality today).
- Ready bound: a Ready is only "taken" inside a core entry; the client BEGIN can straddle a Ready's async send window, so P(READY_PERSISTENCE host failure) ≈ send-time / 150 ms per BEGIN, and only if the tx then outlives 120 s. Rare; moot under the shadow.

**NEW MECHANISM (today): leader self-deadlock on an abandoned session.** Hold sweep heal is deferred while `this.role` is LEADER/CANDIDATE (:385-401, `isStuckTransactionHealPermitted` :456-461); `this.role` changes only when a drain announces; a drain needs admission; admission needs the heal. Durability fitness cannot demote (DEMOTION_UNSUPPORTED, durability-fitness.js:225-228, 267-271: "The port has no step-down operation, so no demotion runs"). A pgwire client that dies with an open tx (no auto-ROLLBACK, census #2) wedges the leader replica until process restart; the joiners elect around it, so the partition stays writable elsewhere, but the seed replica never heals and every write routed to it defers 2 s. T-A can measure this with a >60 s hold variant (expect STUCK_TRANSACTION_HEAL_DEFERRED once per second, LEADER_DURABILITY_UNFIT at ~62 s, no recovery).

## 2. Shadow-model interleavings

2a. **Snapshot mark = log index, not coordinator epoch (NEW SHAPE, endorse with a rule).** Coordinator epochs are per-node counters seeded by `now()` (coordinator.js:110-118): not comparable across coordinators, never set by autocommit. Rule: in the SAME synchronous turn as `this.db.serialize()`, read `_raft_rs_applied_state.index` = i; the shadow is exactly "state after i". Conflict predicate at PREPARE / 1PC-COMMIT apply (at index j, deterministic on every replica): key K in writeSet conflicts iff `_row_commit_epochs[K].log_index in (i, j)` OR K belongs to another tx's `_transaction_prepared` write set. Autocommit apply must also write `_row_commit_epochs[K] = index` for its keys (same key resolver, transaction-base :158-181). Lost-update proof for `UPDATE x=x+1` (K derivable): autocommit A at index a, tx T snapshot i, apply c > a: a < i -> T saw A's value, replay applies +1 on top (correct); i < a < c -> conflict, T NOT_COMMITTED (A's increment stands); a > c -> A applies on T's result. No case loses an increment. **Timing hazard (NEW MECHANISM):** `serialize()` is synchronous and blocks the event loop; ticks are timer callbacks. A copy longer than ~350-800 ms (election 500-950 ms minus up to 150 ms since the last heartbeat) re-creates today's election-per-transaction on the leader, once per BEGIN. `db.backup()` yields but is a moving target: under continuous apply from another connection the online backup restarts (livelock: BEGIN never returns inside the 60 s budget); from the same connection it is updated in place, and then the mark must be read at backup completion, not at BEGIN. Required: a byte cap for `serialize()` (order 10-50 MB ≈ 10-50 ms) with a typed BEGIN refusal above it until a measured paged design exists; measurement = copy ms vs bytes on soak/split sizes, with apply traffic running.
   **Re-execution semantics (NEW SHAPE, weakens §6e's "exact SQLite semantics"):** the batch is SQL replayed at index j. Statements whose effect depends on rows outside the write set (predicate WHERE on non-PK columns, sub-selects, `x = (SELECT ...)`) are re-evaluated against state-at-j, so the committed effect can differ from what the shadow showed the client (RYOW result != committed result), and keyless statements produce no write-set key (resolver returns undefined :158-181) so first-committer-wins is blind to them. Options: refuse non-PK-keyed write statements inside a tx at statement time in the shadow (the resolver already runs there), or document "SI on PK keys, re-evaluation elsewhere". Recommend refusal; R3 `changes` equality is only a weak drift witness.

2b. **Prepared locks (NEW MECHANISM).** Without them: autocommit write to K at index between PREPARE(j) and COMMIT(k) is overwritten by the batch at k with no check (the gate checks only at PREPARE). Semantics: keys in `_transaction_prepared` are locked from PREPARE apply to COMMIT/ABORT apply; enforced AT APPLY (deterministic) for later PREPAREs (PREPARE_CONFLICT), later 1PC COMMITs (NOT_COMMITTED), and autocommit statements (new deterministic code PREPARED_KEY_LOCKED, retryable; a leader pre-check before propose is an optimisation, never the authority). Release only by COMMIT/ABORT apply; never by time (directive). Availability cost is 2d.

2c. **Leader change between PREPARE apply and COMMIT (NEW MECHANISM).** `handleTransactionMessage` -> `executeTransactionControl` (entry-apply-base :384-446) has no role check, no redirect, no epoch fence (unlike `handleRemoteQuery` :678-706). Under the model a follower's `commitTransaction` reaches the leader-only commit mode (:712-720) and is refused; the coordinator retries the same pinned address (pin clears only on success, partition-delivery :330-341) until the 60 s budget, then `abortTimedOutTransaction(tx, COMMITTING)` (protocol.js ~:312-318) - an ABORT after a COMMIT the old leader may already have quorum-committed. Required: (i) TRANSACTION ops answer `LEADER_REDIRECT`+leaderAddress when not leader and the router re-pins; (ii) once the coordinator's COMMIT decision is durable (2PC COMMITTING after PREPARED; 1PC after the batch was handed to consensus) a timeout maps to deferred/UNKNOWN, never ABORT/FAILED; (iii) ABORT apply refuses when `_transaction_outcomes` is COMMITTED and COMMIT apply refuses when ABORTED (fail closed both ways, from replicated tables). T-B must include the redirect, not only the durable prepared row.

2d. **Coordinator crash after PREPARED (NEW MECHANISM / owner decision).** Participant locks are held until a decision; the only decider is the coordinator's row. The sweep re-drives from `loadDistributedTransactionRecoveryState()` (initializer :242-243) into `transactionsBySession` filtered by budget (recovery.js:404-411); whether a surviving node's sweep adopts a dead coordinator's rows is UNPROVABLE here (no node filter found in the 40 lines read; needs the loader's SQL). If not adopted: locked keys are unavailable for writes indefinitely (today the participant time-releases at 60 s). Arithmetic if adopted: decision no earlier than budget 60 s + sweep defer 1-30 s + one election 0.5-1 s ≈ 62-91 s of lock; reads are never blocked (prepared state is not visible). Required: an explicit cross-node recovery owner (membership says coordinator node dead -> any node may decide from the durable row; PREPARED without COMMITTING -> ABORT is safe).

2e. **Snapshot / new replica (REFUTED as a risk, one condition).** Install runs only at the closed-handle boot boundary as a whole-file atomic rename (snapshot-install.js:1-10); `_transaction_prepared`, `_row_commit_epochs`, outcome rows travel in the file at applied index s; COMMIT at k > s applies from the row, k <= s is already in the file. Condition: all three tables live in the replica file, none in process memory (the gate says so).

2f. **Split during PREPARED (NEW MECHANISM).** The mirror clones applied entries per `sql` (split-accessor :475-482, `cloneSplitEntry` :498); a batch command has no top-level sql, so the mirror must clone the per-op entries by routing key. The split snapshot copies rows, not prepared batches: a COMMIT applied on the parent after cutover mutates keys the child owns and the child never sees. Required: the epoch fence (`rejectStalePartitionEpochWrite` :620-660) applied to BEGIN/PREPARE/COMMIT, and split/merge cutover readiness gated on an empty `_transaction_prepared` (bounded by 2d's lock lifetime; rebalancer re-checks every 60 s).

## 3. 1PC timing and deadlines

Rounds today (each `persist*` is an awaited replicated autocommit write to the system partition): BEGIN row (1), per recorded write op `persistTransactionRecord` + `persistWriteOperationRecord` (coordinator.js:406-407: 2 per statement, if `recordWriteOperation` is wired for in-tx statements - verify caller), COMMITTING status (1), participant COMMITTING row (1), participant COMMITTED row (1), COMMITTED status (1) = 5 + 2n sequential system-partition rounds and ZERO data-partition rounds. Model: +1 data-partition round (the batch) -> 6 + 2n. Removable without losing the durable decision: both participant rows (observability; the decision is the participant's `_transaction_outcomes` row plus the coordinator's COMMITTED row) and the per-statement rows for 1PC (the batch carries the statements) -> 3 rounds: ACTIVE, batch, COMMITTED. Owner decision.
Deadlines (NEW MECHANISM): budget 60 s counts from BEGIN and includes client think time; tx-op delivery 15 s < pending write 30 s, so the coordinator abandons the message while the batch is still pending and retries; the retry must rebuild the SAME command entryId = f(sessionId, transactionEpoch) so `pendingWriteOutcomes` dedupe (:672-675) and the settled-key answer (:693-701) make it idempotent (per-op entryIds alone do not cover the command row). A quorum slower than the remaining budget hits `createTransactionTimeoutError` (protocol.js:521-527) -> `abortTimedOutTransaction(COMMITTING)` while the batch may still commit -> client told FAILED, rows committed. Honest mapping: COMMIT_DEADLINE_EXCEEDED release ("handed to consensus, may still commit", cdc-stream-base :280-290) must surface as `PARTICIPANT_COMMIT_OUTCOME = UNKNOWN` (today it is returned as the write's failure result, raft-write-commit :170-178) and COMMITTING+timeout must be deferred (`success:false, deferred:true`), re-driven by the sweep. Recommend splitting the budget: ACTIVE budget (idle client) vs COMMIT budget aligned with the 30 s pending deadline.

## 4. Failure atlas for the batch apply

(a) deterministic on all replicas: SAVEPOINT rollback, command STATEMENT_FAILED + `_transaction_outcomes` NOT_COMMITTED everywhere (fine). (b) deterministic on ONE replica: outcome rows are per-replica local, not replicated, so no replica can compare; the leader's outcome is the client's truth. Policy (NEW SHAPE): a replica whose batch outcome disagrees with the command's leader-declared expectation cannot know it; the only systemic answer is to treat any deterministic batch failure on a NON-leader as divergence evidence: persist a divergence flag in the file, hold the group (existing fail-closed semantics :812-822), surface to the rebalancer for replacement. Do not "continue with STATEMENT_FAILED" silently. (c) environment (SQLITE_FULL; SQLITE_BUSY only from another WRITER connection - the file-backed shadow writes a different file, readers never block in WAL): apply held/redelivered; pending write released at 30 s -> must be UNKNOWN (see 3), not FAILED. (d) crash between quorum commit and the serving participant's apply: replay applies on restart; the coordinator's retry meets NO_ACTIVE_TRANSACTION_COMMIT (:684) -> commit miss (protocol.js:113-123) -> TRANSACTION_OUTCOME. Redirect rule required and insufficient alone: the leader answers NOT_COMMITTED only if `appliedIndex >= commitIndex` (a status read can interleave between commit and apply across a Ready's async send), and a partitioned stale leader (CHECK_QUORUM false) answers NOT_COMMITTED for a tx the new leader committed -> false FAILED. That is a committed-read problem (O1/O2 territory); until it lands, an outcome read from a leader that has not confirmed its term with a quorum is UNKNOWN. (e) stale COMMIT after ABORT: refuse from the ABORTED row; duplicate COMMIT: same entryId -> settled key; a rebuilt COMMIT (different entryId) with no prepared row must answer COMMITTED idempotently when the outcome row is COMMITTED - refine the gate's "missing prepared row = version skew" to: missing + COMMITTED -> idempotent success; missing + ABORTED -> refuse; missing + no outcome -> fail closed.

## 5. CDC timing

Order in the model: SQLite commit (batch + outcome + applied index) -> afterCommit: resolve (ack message) and CDC (entry-apply :1096-1117, same effect; effects run after the store transaction, application-transaction-owner :62-63). CDC is locally observable before the client sees COMMITTED; acceptable: the durable outcome precedes it in the same commit (REFUTED as a violation). 2PC: P1's COMMIT apply emits CDC while P2 is pending; cross-partition atomic visibility is not promised and must be stated. **NEW MECHANISM (2PC atomicity):** key locks cannot make P2's COMMIT certain: a secondary UNIQUE/CHECK/FK/trigger constraint can be violated by an autocommit write committed in (i, PREPARE) on a non-write-set key, so COMMIT-after-PREPARE fails deterministically on P2 after the global decision -> P1 committed, P2 NOT_COMMITTED. PREPARE apply must dry-run the batch (SAVEPOINT, rollback) AND the locked set must cover what the dry-run depended on; for secondary uniques that means locking the touched unique-column values (carried from the shadow post-image). Otherwise the promise narrows to PK-keyed writes on tables without cross-row constraints, with a typed heuristic-mixed outcome. Owner decision; 1PC is unaffected (single decision at apply).
