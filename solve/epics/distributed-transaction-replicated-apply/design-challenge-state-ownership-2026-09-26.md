## 2. The shadow workspace

2.1 (a) What the copy lacks: REFUTED as a semantics risk. The canonical connection sets only `journal_mode=WAL` (file-persistent) and `synchronous=NORMAL` (raft-init-base.js:384-385); no `db.function`/aggregate registration, no ATTACH, no triggers, no TEMP tables anywhere in src/partition, src/raft, src/query (grep empty); `foreign_keys` defaults OFF on both handles. `preparePartitionReadStatement` is per handle. The copy carries `_transaction_outcomes`, `_partition_statement_outcomes` and every `_raft_rs_*` table: harmless to statements, but NEW SHAPE for cost: `serialize()`/`backup()` copy the rs-raft log too, so the go/STOP measurement (report §6) measures log size, not state size; the shadow copy must drop `_raft_rs_log`/`_raft_rs_snapshot` after copy (the checkpoint store's `scrubCopy` shape, snapshot-checkpoint-store.js:216-220) or the number is wrong.

2.2 (b) Schema change while a shadow is open: NEW MECHANISM. `MIGRATION_ALTER_TABLE` is an ordinary proposed write (entry-apply-base.js:873-887) applied on the canonical; the shadow keeps the BEGIN-time schema; the digest covers statements only. `INSERT INTO t VALUES (?,?)` after ADD COLUMN fails deterministically at apply (SQLITE_ERROR, statement-outcome-constants.js:56-62) after the client saw statement success, and `INSERT INTO t(a,b)` after ADD COLUMN ... DEFAULT succeeds silently with a row the client never previewed. Autocommit has the same plan/apply race but for milliseconds; a session widens it to its lifetime. `PRAGMA schema_version` is a per-file cookie (a snapshot-installed replica inherits the source's), not replica-deterministic, so it cannot be the fence. Required fence: a partition-owned replicated `_schema_generation` (or the log index of the last applied MIGRATION_ALTER_TABLE), written by that apply; the command carries `snapshotIndex` = the canonical `_raft_rs_applied_state` index at shadow-copy time; PREPARE/COMMIT apply refuses (typed SCHEMA_CHANGED, no mutation) when `last_ddl_index > snapshotIndex`. `snapshotIndex` is also the epoch answer in 6.2.

2.3 (c) Partition version / split / merge / removal: NEW SHAPE x3. (i) The only epoch fence is `rejectStalePartitionEpochWrite` (entry-apply-base.js:573-600), run per statement at delivery (:683-688) against `systemTableCache tables.active_partition_version` (:607-616); nothing fences the TRANSACTION message, and nothing fences at apply for any command (autocommit included). So the batch's statements were each fenced when staged, and COMMIT can propose after a cutover. Required: the command carries the `expectedPartitionVersion` the statements were staged under (refuse a mixed batch), checked by the same fence at proposal admission in prepare/commitTransaction on the leader; NOT at apply (the system cache is not replicated state; a deterministic apply must not read it). (ii) The split/merge mirror is a post-commit consumer on the leader write path, `applyWriteSideEffectPlan` :751-760 -> `handleSplitReplicationAfterWrite` (split-accessor-base.js:466-490: SPLIT_CATCHUP delta queue, CUTOVER_ACTIVE mirror) and `handleMergeReplicationAfterWrite` (merge-replication-methods.js:525-545); report §14 omits it. The batch's side-effect plan must feed every op to it or the split target misses transactional rows: today's "rows followers lack" reappears as "rows the split target lacks". (iii) `fenceServingAdmissionForRemoval`/`waitForRemovalServingDrain` (transaction-base.js:33-58) poll `isInTransaction()` = map sizes (:851-856). With the model, ACTIVE shadows may block removal drain but a durable PREPARED row must not (it is replicated; removal can proceed); redefine `isInTransaction` as "shadows open".

2.4 (d) Memory/disposal: NEW SHAPE. The hold sweep's `db.exec(ROLLBACK)` on the canonical (:411) and its leader carve-out (:391-401) must go; `collectExpiredActiveSessions` (:341-360) becomes "dispose idle shadows" with no consensus effect. File-backed shadows (`backup(tempPath)`) need a closed-handle boot sweep (the `cleanupStaleTransferStaging` shape, raft-init-base.js:373-374) and a per-partition cap (count and bytes). In-memory shadows are process RSS = partition bytes x sessions. Owner decision on the cap; the model must name the refusal when it is hit (today's TRANSACTION_ALREADY_ACTIVE :562-565 is the only precedent).

2.5 (e) `:memory:` partitions: REFUTED as a blocker. `serialize()` works on memory databases, so `new Database(buffer)` is a real shadow; the split-accessor fallback (split-accessor-base.js:314-322, live handle when `dbPath === ':memory:'`) must NOT be reused: it is a read trick, and a shadow that writes to the live handle is the status quo.

## 4. Coordinator vs participant authority

4.1 Today: the client's answer is `runCommitProtocol`'s result (protocol.js:206-340); `sql_transactions.status` (persisted via `submitMutation`, sql-query-engine.js:108-140) is the recovery authority (recovery.js:265-360 resumes COMMITTING/PREPARED, rolls back PREPARING); participant `_transaction_outcomes` is consulted only on a 1PC commit miss (protocol.js:580-600); a 2PC miss is COMMITTED with no evidence (:584-586). The model must state the asymmetry explicitly: in 1PC the participant's durable outcome IS the decision and the coordinator row is derived; in 2PC the coordinator's COMMITTING row is the decision and participant outcomes are obligations. Delete :584-586 (agreed).

4.2 NEW MECHANISM: 2PC PREPARE apply as written (report §9: "conflict check, write prepared row, touch no application rows") validates nothing COMMIT apply will do. A dry-run at PREPARE (SAVEPOINT; run ops; ROLLBACK TO) validates only against the state at PREPARE's index; any later entry (autocommit write, another tx's COMMIT) can invalidate it before COMMIT applies. Classic 2PC requires prepared = locked. Required: while a `_transaction_prepared` row exists, apply of ANY later command checks its write set against the prepared write sets and fails the later command deterministically (typed PREPARED_CONFLICT outcome row; it reads replicated state only, so every replica agrees), until COMMIT/ABORT clears the row. Exact PREPARE apply: (1) settled-key check on `tx:...:PREPARE`; (2) conflict check vs `_row_commit_epochs` (6.2) and vs other sessions' `_transaction_prepared` keys; (3) SAVEPOINT; run each op, capture `changes`; ROLLBACK TO; RELEASE; (4) write the prepared row with `operations_json`, `write_set_json`, `snapshotIndex`, digest, and the per-op `changes` vector; (5) outcome PREPARED. Deterministic failure in (2)/(3) = PREPARE_CONFLICT/PREPARE_FAILED outcome, no row. COMMIT apply compares its per-op `changes` with the vector; a mismatch is state moved under a lock = divergence (R3 fail closed). Residual the owner must accept or reject: write-set keys are PK keys; a secondary UNIQUE/CHECK violation created by a later entry is not lockable this way, so a COMMIT apply STATEMENT_FAILED after a global COMMIT decision remains possible. Define it: coordinator COMMITTED is final; the participant records `COMMIT_DIVERGED` (never retried, never rolled back), surfaced as an operator alert; the client is not told "committed" on that participant.

## 5. Idempotency and identity

5.1 NEW SHAPE: `executeTransactionWrite` (write-metrics-base.js:193-235) has no settled-key or duplicate check (census row 6). A client retry of a staged statement (the write coordinator keeps one entryId per (idempotencyKey, partition): distributed-write-coordinator.js:562-575) is staged twice in the shadow: RYOW shows a double insert or a PK error the apply would not reproduce (apply dedupes per op via `entry:${entryId}` if per-op rows are written as ops run). Staging must (i) answer a key SETTLED in `_partition_statement_outcomes` from the row without staging, and (ii) answer a key already in the batch as the tracked result.

5.2 Same entryId as autocommit and in a batch (routing fork C §5): only reachable when BEGIN lands on a follower; under BEGIN leader-binding (§15.5, required, not optional) it cannot happen; the apply-side per-op settled check then makes it a replay-skip, which would silently make a "rolled-back" statement durable. State leader-binding as the invariant that closes it.

5.3 Digest: define concretely: SHA-256 over canonical JSON of the ordered `(type, sql, params, entryId)` tuples plus `snapshotIndex`, `expectedPartitionVersion` and the command identity; canonical params encoding is the F-BLOB fix.

5.4 Stale COMMIT after ABORT (and any duplicate): apply order = settled-key on the command entryId -> outcome row for (session, epoch) (COMMITTED: answer idempotent replay; ABORTED: answer NOT_COMMITTED, no mutation) -> prepared row present: apply -> none of the three: fail closed (true skew). The report's "missing row -> fail closed" is only the last arm.

## 6. Isolation contract

6.1 NEW MECHANISM: `write_set_key` is undefined for predicate writes. `resolveTransactionWriteSetKey` (:158-186) uses `whereClause`/`data` PK, else `extractSplitRoutingKey` -> `extractRoutingKeyFromSql` (partition-split-routing.js:327-354, parses the SQL for a PK value); no PK => it throws SPLIT_REPLICATION_ROUTING_FAILED, caught at :181-183, returns null, and `trackTransactionWriteSetKey` :190-192 silently tracks nothing. `UPDATE t SET x=1 WHERE y>5` has an EMPTY write set today and in the model: the PREPARE-time check accepts a lost update, and `_row_commit_epochs` written from `writeSet` is blind to it. Options: table-level key `${table}:*` when no PK is derivable (coarse, correct), or apply-derived keys (pre-image `SELECT pk WHERE <predicate>` per op; exact, needs the parser). Owner decision; the model cannot claim first-committer-wins without one.

6.2 NEW MECHANISM (answers §15.1): the epoch. Coordinator epochs are a per-coordinator counter seeded by `now()` (coordinator.js:110-118), incomparable across coordinators; autocommit has none. Use the partition log: a tx's snapshot = `snapshotIndex` (canonical `_raft_rs_applied_state` at shadow copy, 2.2); a commit's epoch = the apply `index`; conflict iff `max(commit_index for key) > snapshotIndex`. Totally ordered, replicated, comparable, free, and it doubles as the schema fence. Autocommit apply writes `(key, index)` per statement (in scope: one row per apply; keys per 6.1). The coordinator epoch stays as identity only.

## 7. Ownership boundaries

7.1 Two executions, one owner: the shadow and apply both run `stmt.run`. It is one owner (SQLite semantics, applied twice) only under an explicit rule the report lacks: the shadow result is a preview and a divergence witness (R3), never an input to apply and never the client's final answer for the transaction; the final answer comes from apply's outcome rows. Where the two can silently disagree the model must fence (2.2 schema, 6.2 snapshot) or declare (rowid under interleaving, non-deterministic SQL R1). Without that rule it IS two owners of statement semantics.

7.2 CDC: one path (apply afterCommit per op); no second path. Post-commit side effects: the batch must run the whole side-effect plan per op (CDC, split/merge mirror 2.3, `scheduleSizeUpdate`, managed split evaluation :763-767), else the mirror becomes a missed consumer, not a second owner.

7.3 Retry owners: three exist (coordinator participant retry protocol.js:511-560; partition pending-write 30 s deadline; router deferRetry). The model adds none, but all three are only safe under deterministic command entryIds (1, 5.4).

7.4 rs-raft: CONFIRMED no provider change. Needed surface = `readStatus`, `propose`, `applyCommittedEntry({command,index,term,effects})`, `store.transaction` atomicity (application-transaction-owner.js:41-63); a SAVEPOINT inside it is host SQL. Constraint to state: the apply callback must stay synchronous (:50-52 throws on a thenable), so the batch apply and every table write are sync; only effects may be async. Max entry size remains the open bound. liferaft: dead path.

## Amended model deltas required

D1 Deterministic command identity `tx:<session>:<epoch>:<PREPARE|COMMIT|ABORT>`; leader entry points read outcome/prepared tables before proposing; apply order per 5.4.
D2 Command fields: `snapshotIndex`, `expectedPartitionVersion`, `schemaGeneration` (or derive from `snapshotIndex`), digest per 5.3.
D3 Epoch = log index (6.2); `_row_commit_epochs(key, commit_index)` written by every apply (autocommit too); deterministic retention rule.
D4 Write-set key definition for predicate writes (6.1), or the model drops the first-committer-wins claim.
D5 2PC: prepared write sets lock later applies; PREPARE dry-run + `changes` vector; COMMIT_DIVERGED residual named (4.2).
D6 Every TRANSACTION operation leader-bound with redirect (not only OUTCOME); BEGIN leader-binding is an invariant, not an option.
D7 Staging dedupe (5.1).
D8 Side-effect plan per op incl. split/merge mirror; `isInTransaction` = shadows only; removal drain unaffected by PREPARED rows.
D9 Shadow copy scrubs `_raft_rs_log`/`_raft_rs_snapshot` before measuring; boot sweep for shadow files; cap + refusal shape.
D10 Snapshot pipeline: `hasPendingPreparedTransactions` reads `_transaction_prepared` or is dropped (separate owner; pipeline dead under rs-raft today).
