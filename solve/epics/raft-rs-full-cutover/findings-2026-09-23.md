# Findings recorded for the raft-rs-full-cutover epic (2026-09-23)

Found while proving other units; recorded here for their owners (R17), not
fixed in place.

## F1. Leader step-down and candidacy deferral are dead on the frozen port (production defect, both backends)

`src/raft/tracked-leader-demotion.js` `performTrackedLeaderDemotion` requires
`raft.change(...)` and returns false when it is absent; the frozen operation
port has neither a step-down nor a candidacy-deferral operation, and
`src/partition/partition-service-durability-fitness.js:358` calls
`this.raft?.deferCandidacy?.()`, a silent no-op on the port. Consequences on
main since #46 (f4f5b5a6e), on the liferaft backend production runs:

- an unfit leader (durability-fitness detector, C3 bounded fallback) is never
  demoted; the hook fires, the role stays leader;
- the replica handler's tracked leader handoff
  (`src/node/replica-handler-leader-handoff-methods.js:157`) goes through the
  same dead demotion.

Witness: `test/convergence/dt6-ledger-leader-durability-fitness.test.js` (six
subtests red on main). These call sites were already listed as
`liferaftOnlyCallSites` (change / deferCandidacy) in
`solve/quests/raft-rs-experimental-partition-backend/evidence/interface-reduction-table.json`;
the operation-port quest removed the object without giving the port the
semantic operations. Owner: a quest that adds the two semantic operations to
the port with rs-raft semantics (step down / transfer leadership; hold
candidacy while unfit) and re-certifies the fitness contract on the real
partition path. Do not add a `change` compatibility method.

## F2. `test/bootstrap/production-scheduling-defaults.test.js` asserts liferaft timer internals

Its subject is `partition.raft.timers` (the VirtualTick manager and the
commit-apply yield primitives). The port's `startScheduling()` carries the
scheduling-substrate fact (a supplied clock arms the clock, production arms
the host timer; measured), but the commit-apply yield witness is
liferaft-internal. Owner decision: re-home the scheduling fact on
`startScheduling()` and give the yield witness a subject that survives the
cutover, or delete it with the legacy scheduler. One of its tests is already
hollow-green (timers undefined).

## F3. An unrecognised committed command is a silent no-op

`PartitionService.applyCommittedEntry` (src/partition/partition-service-entry-apply-base.js:963)
returns silently for a command whose type it does not know; under rs-raft it
received raw bytes and applied nothing while commitIndex advanced. R07: the
typed outcome belongs where the committed entry is decoded (quest
raft-rs-single-path-partition-cutover fixes the contract; the typed refusal of
an unknown command type is part of that fix).

## F4. `packaging/sea-bundle-smoke` is red on plain main

"bundle dry-run exits cleanly" fails on `e3ac0514b` on the lab node; the
bundler warns `import.meta` is empty in the cjs output. Main debt; and the
rs-raft runtime owner resolves the vendored WASM through `import.meta.url`, so
SEA packaging of the binding needs its own witness before R8.

## F5. Snapshot/catch-up is unowned on rs-raft (see census-snapshot-catchup-ownership-2026-09-23.md)

Creation, cadence, compaction, HLC warm-up and the install decision are inert or
fail-closed on rs-raft; the applied watermark is dual-written; a restart writes
a sticky `appliedGapMarker`; the checkpoint scrub would ship the sender's
`_raft_rs_*` rows to a follower. Owner: the epic gap "Snapshot/catch-up
ownership" becomes at least two quests (creation/install re-owned on the rs-raft
store; a follower-needs-snapshot signal, which needs a binding primitive or a
Lagrange-side decision from `status.progress`).

## F6. Consensus persistence can run inside an open user session transaction (pre-existing, both backends)

The rs-raft durable store shares the partition's single SQLite connection
(`partition-service-raft-init-base.js:434` -> `raft-rs-runtime-owner.js:705`), and
interactive session transactions run `BEGIN IMMEDIATE` on that connection
(`partition-service-transaction-base.js:576`, `partition-transaction-handler.js:81`).
A marker proposal inside such a session (`transaction-base.js:919,955,989`) persists
Ready state as a savepoint of the session on a lone leader; a later session ROLLBACK
erases log, hard-state and applied rows the core believes are durable. Liferaft had
the same shape (the commit slice ran as a savepoint inside the session). Owner: a
quest before certification item "acknowledged-write correctness across leader
change": consensus persistence must never run inside a user session transaction
(reorder marker proposals outside the session, or refuse proposals while the
connection is in a user transaction). Also recorded there: TRANSACTION_COMMIT apply
records only the outcome so followers never replay `operations`
(`entry-apply-base.js:1096-1113`), and commit CDC fires before consensus
(`transaction-base.js:712-714`); `raftLogIndex` on the marker record has no source
once the legacy append is gone.

## F7. The public API still exports the legacy storage classes

`src/partition/index.js` re-exports PartitionRaftStorage/PartitionRaftLogEntry
(now pointed at `partition-raft-storage.js` directly to keep `src/public-api.js`
unchanged). Owner decision at R6: delete them from the public API with the legacy
substrate.

## F8. A restarted lone voter elects itself even with `deferElection: true`

After a restart, commit and applied advance by one (the new leader's empty entry)
with no proposal, on a group constructed with election deferred (A2 measurement).
Init therefore elects a lone voter when election is deferred; owner: the runtime
owner / convergence readiness (the same class as "the deferred joiner campaigns"
in `partition-service-transactions-query-routing`).

## F9. Runtime reconstruction after a host failure leaves the partition's leadership diverged

After RECOVERY_REQUIRED and reconstruction on a single-replica group, the group
comes back as follower and never campaigns again while `PartitionService.isLeader`
stays true; every later write reports "No leader available" (A1 probe). Owner: the
runtime owner's recovery path must re-announce role (or the partition must re-sync
from `readStatus()` after recovery). Ordinary SQL statement failures no longer
reach this path (design A7.2); genuine host failures still do.

## F10. A refused `initialize()` must release the database it opened

Init now fails closed on legacy consensus state (detector) and on an undecodable
committed entry (warm-up); the detector closes the connection, the warm-up path
does not (A2 measurement). R13: one init-failure path that releases every
acquired resource, decided at integration.

## F11. `step()` only enqueues; a scheduling-stopped joiner processes inbound only on the next tick or read

The rs-raft port's `step()` enqueues the envelope; delivered inbound is driven
through the core by the next tick, operation or `readStatus()` (which still
drains inbound first). A deferred-election joiner with scheduling stopped
therefore processes delivered messages only when something reads its status.
Owner: the runtime owner should drain on delivery. (A1 measurement; removing
the read-driven drain made the deferred joiner never promote.)

## F12. Other writers on the shared partition connection have no persistence admission

Layer 1 admits only the rs-raft store's writes. Peer-identity reservation
inserts (`raft-rs-peer-identity.js:121`), lifecycle retirement updates and the
store constructor's DDL still run without checking `db.inTransaction`, so a
session ROLLBACK can erase any of them. Owner: extend the admission to every
consensus-adjacent writer on that connection (layer 2 or its own quest).

## F13. Under layer 1 a leader holding an open session sends no heartbeats

Every core entry except read-status is deferred while a user transaction is
open on the partition connection, so a session longer than the election
timeout demotes the leader (explicit unavailability instead of silent
corruption). Layer 2 (design c', replay-per-request without a transaction
spanning a client round trip) removes the stall. Inbound envelopes and ticks
queue behind the waiting Ready, bounded by the 120 s admission wait.

## F14. The tail-of-queue bug in the runtime owner (fixed in this quest, recorded for the census)

`enqueue` stored `token.finally(...)` as the group tail but compared the
un-finalized token against it, so the tail was never cleared once a group's
work went asynchronous; every later operation and status read returned a
Promise (36-56 of 135 seed replicas at any instant). Fixed in attempt A1;
recorded because the same class (a memo keyed on the wrong identity) has
appeared before in this repository.

## F15. A failed delivery to one peer retires the whole shared runtime (rs-raft)

`raft-rs-runtime-owner.js` `sendMessages` -> `finishReady` catch marks the group
RECOVERY_REQUIRED on a rejected or handler-less delivery, and `replaceRuntime`
rebuilds the shared core for EVERY group in the process, bringing them back as
followers (the F9 class). In production a timeout to one partitioned follower
would unseat the leader. Owner: runtime failure isolation (epic gap): a peer
send failure is a per-peer transport outcome, never a group or runtime fatal.
(dt6 live-voter redesign, experiment exp1.)

## F16. The partition's own ADD_PEER proposal is always refused

`partition-service-raft-init-base.js:547` passes `peerId` where the port's
`proposeConfChange` expects `replicaIdentity`, so the proposal is refused as
`unknown-membership-change`; the follower/learner reconcile then forwards
redundant ADD_PEER proposals to the leader, adding nondeterministic log entries
(commit index 9 instead of 6 in the fixture). Owner: the membership
administration boundary (R2 quest); one caller, one shape.

## F17. A follower's `readStatus()` throws for a configured peer its registry never reserved

`unknown raft-rs peer identity` is thrown when a follower's ConfState names a
peer whose identity was reserved only on the leader (reservation happens
through the services-cache reconcile). Owner: peer-identity administration
must reserve from the committed ConfState, not from cache rows.

## F18. `probePeerProgress` is inert on rs-raft

The rs-raft port's probe returns `progress-observed` whenever
`followerProgress[peer]` is finite, and rs-raft reports matched 0 for every
configured peer, so it never ticks and never sends. The learner-promotion
liveness for an idle caught-up learner (progress-proof "snapshot-installed
shape") therefore has no rs-raft owner; the case is stopped with F5.

## F19. Layer-1 admission does not cover the store constructor's DDL or the peer-identity/lifecycle writers (see F12)

Recorded again here from the dt6 redesign: every consensus-adjacent writer on
the partition connection needs the same admission.
