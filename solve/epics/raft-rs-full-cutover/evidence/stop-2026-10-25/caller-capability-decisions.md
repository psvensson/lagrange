## Affinity query-loop demo

Reachable: package.json demo:movielens -> examples/service-data-affinity/run-comparison.js -> run-affinity-demo.js:deployQueryLoopService. It writes config(runtime.access.service.<SERVICE_ID>) with synthetic binding_version_id=demo-scaffold-movielens-topn, then service_definitions with sql_engine/sql-query-loop-runtime, replica_count=2, periodic query/reduce config. README explicitly describes a five-node observed-access placement experiment, two disjoint movie-id service shards, local top10 and at most20 candidates; ratings primary key is(user_id,movie_id), so ordinary partition-local top10 is not equivalent to complete per-movie aggregation.

Current authorities: external-service-manifest.js accepts OCI-container/WASM-component media, not SQL_ENGINE. RuntimeAccessPolicyOwner.configureBindingAccess requires an actual Binding and derives its service ID; the fake policy cannot be migrated to CONFIGURE unchanged. ServiceDefinitionsOwner has Binding reconciliation and the narrow PG built-in scale operation, not an internal query-loop deployment contract. sql-query-loop-runtime-module.js and parallel-reduce remain active internal runtime implementation, so npm reachability plus a legacy label does not justify deleting them.

Supported successor: call-binding-account-summary demonstrates genuine WASI Artifact installation, Binding-derived service definitions, declared runtime policy, per-partition leader-local run, numeric emit and coordinated reduce. It can express the ranking formula by exchanging finite sum/count values, but that changes the current exact two-service-replica placement experiment and twenty-candidate traffic bound. Because ratings for a movie span user-key partitions, naively taking local top10 is wrong. A faithful new public demonstration needs an explicitly sealed workload/data-layout/partial-bound decision, not a mechanical install substitution or fixed demo-only owner bypass.

Recommended decision: preserve historical internal runtime/evidence; replace this externally runnable raw-writer demo with a separately sealed public call-Binding ranking/placement experiment only after agreeing the changed placement and bounded-partial claim. Alternatively, if the exact internal two-replica experiment remains supported, its deployment/runtime-policy semantic contract is genuinely missing and needs an explicit owner decision. No generic internal exemption is available.

## MovieLens invocation-journal reset

Reachable implementation: movielens-public-request-workload-adapter.js:resetRunState drains operations, deletes two user result tables, globally DELETEs wasm_operations, then requires global journal COUNT=0. movielens-capacity-runtime-adapters.js:createMovielensLagrangeCapacityAdapter delegates this reset and captures one session's prepared Binding/runtime/artifact evidence. Repository search finds its direct factory callers in test/examples/movielens-capacity-runtime-adapters.test.js; scripts/checks/run-comparative-efficiency-movielens-paired-runtime-adapters-guard.js selects those assertions. That caller census alone does not retire the exported prepared-session capability.

Current owner: request invocation custody writes wasm_operations and owns replay; no supported journal-clear operation exists. A per-window operation ID already includes adapter ID, block index/order, side, offered load, phase and operation index, but preserving old journals while claiming globally empty fresh state would change the reset proof and retained-memory cost.

Existing isolation mechanism: run-movielens-public-request-workload.js:openMovielensPublicRequestWorkloadLive creates a unique temporary root, boots its own node, deploys genuine WASI request Binding and exposes close(). closeWorkloadSession stops the prepared Cell, shuts down the node, then removes its owned temporary root. A new isolated session per measured block can avoid any shared/durable journal mutation and preserve genuinely empty initial custody, provided startup/preparation is outside the measured window and actual new owner evidence is retained. The capacity adapter currently closes over immutable session/evidence; reset must be owned by a session factory/lifecycle, not mutate its captured prepared object or hide changed runtime identity.

Required causal correction before using close as this reset owner: current closeWorkloadSession attempts temporary-root rm even if Cell stop/node.shutdown failed (cleanupAttempt aggregates failures afterward). Any isolated reset must preserve custody and stop on failed shutdown before filesystem removal/replacement. This is a bounded lifecycle prerequisite, not permission to delete shared state. Recommended decision: replace the raw reset contract with isolated-session reset under the existing live session owner, verify shutdown/drain and exact fresh-session evidence, keep PostgreSQL reset accounting comparable, and preserve failed-session artifacts. No journal delete API.

## Legacy callback uploader and two distributed consumers

Reachable: scripts/examples/build-upload-run.js -> run-examples-catalog.js -> example-execution.js:uploadExample writes code and module_manifests, then partitionCallback. Consumers are test/distributed/scenarios/examples-catalog.js and wasm-service-failover.js plus test/scripts/examples-build-upload-run.test.js. Default catalog is test/fixtures/legacy-distributed-sql, whose README explicitly calls it a retained historical pre-Binding mechanism; architecture/query-runtime.md still identifies an active internal legacy callback surface.

The wasm case is expressly artifactContract=js_callback_envelope_rehearsal and packageCodeBlob uses buildJsWasmComponentArtifact from query/callback/callback-module-artifact.js. It is not genuine WASI installation. The failover scenario bootstraps that case, queries services.service_type=wasm_service, kills a host and checks replicas. handlePublishModule in wasm-service/meta-command-handlers.js is a validator/SQL builder; its only consumers found are tests, and it neither uploads the code blob nor supplies a reachable admin mutation owner. It is not an existing usable deployment API.

Supported WASI/call successors preserve general partition-local computation and failure recovery, but do not preserve every legacy test contract: fixture04 performs nested bounded ctx.call into config; fixture05 asserts the legacy unbounded-nested-call guard; fixture03 emits structured records then reduceByKey, whereas the public call boundary carries finite numeric partials. Do not claim a transparent catalog rewrite.

Recommended decision: retire the raw-upload/live-distributed use of this explicitly historical catalog while retaining its internal regression fixtures/tests where they exercise the retained callback owner; migrate the two distributed scenario purposes to genuine WASI request/call Bindings with actual lifecycle and remote-result/failure assertions. Catalog-specific nested-callback guards remain internal tests, not public capabilities. This is a concrete retirement/migration decision, not already done. If live legacy callback deployment itself must remain supported, a complete code+manifest publication owner is missing; adding a generic SQL bypass or pretending PUBLISH_MODULE already provides it is invalid.
