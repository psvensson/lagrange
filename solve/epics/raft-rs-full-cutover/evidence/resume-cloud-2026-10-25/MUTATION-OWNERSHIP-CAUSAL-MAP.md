## 1. Established causal mechanism and history

The classifier currently accepts a valid plain result with no typed outcome and no affected-row count as applied whenever `success:false` is absent. `test/control-plane/control-plane-mutation-outcome-classifier.test.js:108-113` explicitly preserves `{success:true}` as a legacy successful envelope. The gateway's completion and outcome builders independently turn the same otherwise-unknown valid shape into `APPLIED`; requiring only the gateway's resulting typed string at the consumer would therefore preserve the ambiguity.

The original F-ADMIN-1 review proved that config/policy discarded returned refusals, deferrals and zero effects. Their reviewed helper now prevents this at those semantic owners by requiring one applied row and completed visibility before success side effects. This is a recurrent owner-effect problem.

Producer inspection also reaches two alternate execution paths. The gateway can use SQL directly when CDC is absent and phase-scope/cache-wait options permit it. Separately, bootstrap-mode CDC attempts a Raft write and then fans a write out through `executeLocalQuery` after the Raft lane fails. ## 3. Contract to settle before edits

1. **Receipt interpretation has one owner.** The existing classifier interprets an explicit, immutable producer receipt. The gateway maps lower-layer owned facts into that contract without interpreting missing fields as success. Invalid, absent, accessor-bearing and unrecognized evidence remains unconfirmed or refused according to an explicit typed rule.
2. **Application, row effect and visibility are separate facts.** A committed statement, one changed row, and authoritative visibility are different guarantees. The contract records each without aliases. An exact-row operation requires count one or its existing authoritative exact-identity reconciliation; named replay with unknown count does not prove a matching row.
3. **Uncertainty retains custody.** Lost answers, explicit unknown outcome and named pending instances retain the original logical write/entry identity, useful cause, retry state and owning progress mechanism. Unknown is never converted to definite noncommit or a fresh intent. Q6 transport delivery cannot supply application evidence.
4. **One supported mutation execution path per capability.** CDC/gateway absence does not select SQL. Bootstrap Raft refusal does not select local mutation. Original-seed, join publication and handoff capabilities use their existing semantic owner and one canonical durable write path, or return typed not-ready/refusal while that owner retains the work.
5. **Consumers publish only their required fact.** Progress markers, admission authority, destructive cleanup, counters, cache invalidation, events and HTTP results follow their documented predicate. Diagnostic-only consumers may preserve a disposition without granting authority.
6. **No legacy compatibility layer remains in the affected interaction.** Remove success-only receipt support, `changes` guessing, boolean-or-envelope ambiguity where it bridges this interaction, method-presence alternate mutation selection and obsolete producer branches. Legitimate physical result adaptation belongs at the producer and is not duplicated at downstream callers.

The current typed vocabulary has no separate general UNKNOWN member. Root must settle whether the existing unconfirmed/error representation suffices or whether the sole vocabulary needs one explicit uncertainty state; a new meaning must be added at that owner and migrated together, not smuggled into `REJECTED`, `NO_OP` or `OWNER_NOT_READY`. This is an implementation decision within the authorized task, not a request for user permission.

## Primary comparable-system checks

The official [etcd API guarantees](https://etcd.io/docs/v3.6/learning/api_guarantees/#operation-completed), inspected 2026-10-25, preserve client uncertainty after a timeout or network disruption even when durable completion may have occurred. This supports preserving original intent and uncertainty; it does not substitute for Lagrange's receipt evidence.

The official [PostgreSQL UPDATE outputs](https://www.postgresql.org/docs/current/sql-update.html#SQL-UPDATE-OUTPUTS), inspected 2026-10-25, distinguish successful command completion from the affected-row count, including zero-row success. That is relevant precedent for keeping statement completion separate from an exact conditional row effect. The specific Lagrange predicate, replay and visibility obligations remain owned by the repository contracts above.
