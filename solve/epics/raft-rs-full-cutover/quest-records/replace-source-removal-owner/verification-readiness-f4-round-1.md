## 2. Fact 2 classification (attack 2)

`collectDeferredReasonCodeSet(snapshot, decisionDimension)` (`readiness-planning-publication-contract.js:339-373`) copies reasons iff `isDeferredVerdictDenial` = `snapshot?.dimensions?.[dimension] !== true`, dimension defaulting to `SERVE_ELIGIBLE` - the same default the variant key uses (`resolveReadinessDecisionDimension`, `snapshot-store.js:229-234`), so the classification dimension equals the variant's dimension for every read; a snapshot lacking the dimension key, or a null snapshot, is treated as a denial (fail-closed; a null source yields `[rp]` only). The consumer side is dimension-agnostic by design (`isEvidenceAbsentReadinessDenialSnapshot` reads reason codes only, `readiness-denial-classification.js:44-48`), and its only callers are the floor and placement carve-outs (`priority-publication-safety-topology.js:162`, `unified-rebalancer-available-nodes.js:264`) plus routing's own copy (`query-executor-partition-routing-snapshot.js:82-99`) - all three name their dimension, so no consumer classifies a deferral built for another dimension.

The two-dimensions-disagree cell: probed on production (`memo-dimension-probe.mjs`): snapshot eligible on `controlPlaneRecoveryEligible`, denied on `serveEligible`, reason PCPRP, same snapshot/token/ownerKey: A read -> `[rp]` evidence-absent; B read -> `[PCPRP, rp]` not evidence-absent; A again -> `[rp]`. Correct. But mutation M7 (memo key without the dimension) is SILENT in both witnesses (F-2): under M7 the B read would be served A's `[rp]` cell and a substantive serve denial would be weakened. The memo also thrashes across alternating dimensions on one owner key (A, B, A rebuilds each time; the memo was introduced against a 9x per-build cost) - hygiene, noted under F-2.

The 252-case witness (`readiness-deferred-denial-evidence-absent.test.js`) ranges over `LIFECYCLE_REASON` (bootstrap enum, 9) x `CONTROL_PLANE_READINESS_REASON` x 12 dimensions from the production enumerations; the completed snapshot's `reasons` are composed from `CONTROL_PLANE_READINESS_REASON` (`control-plane-readiness-evidence-reasons.js:164-270`) and the lifecycle DEGRADED reasons (`node-joining-ready-signal-readiness.js:329-333`), so the universe is the right one. The range is decorative for the mechanism (the rule drops ALL reasons of an eligible verdict, code-agnostic), which is fine: the value of the range is the denial direction (test 3) and the floor anchor (test 4). Test 3's predicate `isEvidenceAbsent && !codes.includes(reasonCode)` is weak in the letter but mutation M4 (classify on serveEligible regardless of the read's dimension) turns it red (22 failures), so the dimension is witnessed.

## 3. The carve-outs and a dead node (attack 3)

With a deferral over an eligible verdict counted, a node that died after its last eligible verdict is countable by the floor, placeable, and routable-by-fail-open for the window [death detected -> variant rebuild landed]. Before detection the strict path counts it too (unchanged by F4: a stale-heartbeat verdict needs `clusterMemberStaleHeartbeatMaxAgeMs` to elapse and the liveness timer to reproject, `node-liveness-semantic-projection-owner.js:381-423`). At detection the liveness change rotates the identity (G2) and defers the node's reads over the still-eligible completed verdict (`[rp]` only after F4) until the queued rebuild (`enqueueAffectedOwnerKey` -> one build per macrotask drain) lands a denial. Pre-F4 the same window existed for reason-less eligible snapshots (the greens' shape); F4 extends it to snapshots carrying informational reasons (PCPRP, NODE_DRAINING, ...). Bound = rebuild latency, ms in steady state, 0.25-5 s under event-loop gaps (slice-1 measurement), and NOT bounded in a rotation storm where the rebuild never lands current (the P1 class). No test asserts the bound (`readiness-planning-deferral-bounded.test.js` bounds the deferral per read, not the carve-out's counting window). Known mechanism (the sealed evidence-absent carve-out over a stale eligible verdict), new shape; recorded as F-3.

### F-1. Forward-only by watermark still admits two writers at equal watermarks

Reproduction: `node scratchpad/verify-f4/equal-watermark-probe.mjs` (production code, unmutated): a recorded `active/ready` row and a caller-held `draining/ready` row at the same `last_heartbeat`/`ready_lease_expires_at` alternate 3 times -> 7 semantic changes published, `clusterMembershipSemantics.state` healthy/invalid/healthy..., generation 1 -> 7; the same with `ready` vs `disconnected` and with a `{node_id,status}` row lacking heartbeat fields. Production reachability: the async evaluation's authoritative row vs the planning build's cache row while the cache lags a status or connection_state write with no heartbeat bump; each flip is a G2 global rotation and defers every variant until rebuilt. Bounded by the cache's deferred listener; the 10/10 acceptance batch did not show it. Exact change list: (1) amend the F4 coverage model with the dimension "caller-held row vs projected row: newer / equal watermark same content / equal watermark different content / no watermark / older / absent"; (2) production, projection owner only: record caller-held evidence when the candidate is strictly newer by watermark, or equal by watermark AND equal in the semantic row fields the projection reads (status, connection_state, lease clear), and treat a candidate without a heartbeat watermark as not current when the projected row has one; (3) witness 2: add the equal-watermark-different-content and watermark-less cases to `NON_SOURCE_ROW_CASES` (they must be red on today's rule) and a projection-owner anchor for each.

### F-2. The dimension-keyed deferred memo has no witness

Mutation M7 (drop `entry.decisionDimension === decisionDimension`) leaves both witnesses green although under it a `serveEligible` read after a `controlPlaneRecoveryEligible` read of the same (snapshot, token, ownerKey) is served the `[rp]`-only cell and a substantive serve denial becomes "no verdict" (the probe shows production is correct today). Change: a witness through `readSync`/`buildMemoizedDeferredSnapshot` alternating two dimensions on one owner key whose completed verdict disagrees between them, asserting each read's reason set; and note the memo's one-entry-per-owner-key thrash across alternating read kinds (the floor's `controlPlaneRecoveryEligible`, routing's `serveEligible`, placement's dimension) as a hygiene item for the owner.

### F-3. The counting window over a dead node is not bounded by evidence

A node whose last completed verdict was eligible and which then died is counted by the floor, placement and routing fail-open from the liveness detection (which itself rotates the identity and defers the read) until the variant rebuild lands the denial; pre-F4 this held for reason-less snapshots, F4 extends it to informational-reason snapshots, as the ruling intends. The bound is the rebuild latency (unbounded in a rotation storm). Change: state the bound in the F4 record and add an anchor asserting that a rotation caused by a node's own liveness change lands that node's rebuilt denial before any other read of it is served a second deferral (or fold it into the `readiness-planning-deferral-bounded` witness).

### F-4. Two unavailability contracts, two availability predicates

`NodesOwner.getNode` throws on `success===false` (`nodes-owner.js:15-25`) while `listNodes` returns the failure object; F4's `readNodeRow` guard on `getNode` is therefore unreachable and the single-row unavailability propagates as an exception where the list unavailability reads the cache. `isAuthoritativeRowReadAvailable` is `success !== false` (a result without `success` is "available" -> `[]` rows) while the coordinator's read-source contract it cites requires `success === true` (`membership-publication-coordinator-reads.js:191`). Change (owner hygiene, no behaviour change in F4's path): one predicate exported by the coordinator's read-source owner and consumed by the readiness readers; one unavailability outcome per owner class.
