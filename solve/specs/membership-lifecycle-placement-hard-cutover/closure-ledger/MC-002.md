# MC-002 Removal by key after an await

### STATE (current truth — read only this header to act; history below)

- **status**: `open` — a mechanism class: match a new defect against it before designing.
- **kind**: mechanism-class
- **definition**: State is removed or released by key or address after an await, so a successor that took the same key during the await loses its entry, handler or resource.
- **detectionQuestion**: Between capturing the key and removing by it, is there an await, and could a new holder of the same key exist by then? Is the removal by exact identity (this instance, this handler) or by key?

## Instances

- WASM service replica (PR #73, 2026-10-03). `WasmServiceReplica.shutdown`
  removed its transport handler by address, so a late shutdown of an old
  instance could remove a successor's handler registered at the same address
  (62913d57e retires the exact handler; fcbd2694f makes the lifecycle a named
  state machine after the first repair awaited before clearing).
- `stopReplica` deletes `activeReplicas` by service id after awaiting
  `replica.shutdown()`, removing a successor started under the same id - on
  main since 7e0c039d7 (`src/wasm-service/wasm-service-lifecycle.js`), repaired
  on the PR #73 branch by fcbd2694f.
- `startReplica` released the port by service id when a start failed, while a
  live successor could hold it (c6e6eeb1e, 535172bcb).
