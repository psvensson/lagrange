## First Violated Invariant

After a REPLACE's replacement replica reaches voter-ready raft state (learner -> voter promotion
completes locally), the REPLACE remove-safety gate evaluating that operation must observe the
replica as voter-ready within bounded time and proceed to remove the superseded source replica.
It must NOT defer the remove indefinitely on a stale "replacement replica is not voter-ready"
view — even on the replacement replica's OWN node, where the promotion truth is locally known.

## Mechanism (pinned; one local-write gap, no cross-node propagation needed)

The node that owns r4 and logged its voter-ready activation (11601fe0) is the SAME node that
then defers the remove claiming r4 "is not voter-ready". So the gap is entirely local:
r4's raft promotion (learner -> voter) at 16:40:52 updated r4's LOCAL raft / activation state
but did not write through to the **replica row's `raft_role` field** that the safety gate reads.

- Gate locus: `operation-workflow-remove-safety-evaluator.js:319,397-398` calls
  `context.isVoterReadyReplicaTopology(replacementReplicaRow)` /
  `context.isVoterReadyRoutableReplica(...)`.
- Predicate: `priority-publication-safety-topology.js:112 isVoterReadyReplicaTopology(replicaRow)`
  returns false unless `replicaRow.status` in {ACTIVE, SYNCING} (r4 = active, PASSES),
  `replicaRow.address` present (PASSES), AND `replicaRow.raft_role` is a non-null string that is
  NOT `learner` (the FAILING condition: r4's row still carries raft_role=learner or null after
  the local promotion).
- So the binding sub-condition is the `raft_role` field of the replacement replica's row, exactly
  the column class as [CL-021] (raft_role row write) and the evidence-locality concern of
  [CL-016] (voter-ready activation must reflect local truth without a durable round-trip through
  the control plane being recovered).

## Falsification Result — CONFIRMED (2026-06-14, subagent code trace)

CONFIRMED, with a refinement: the gap is a DEFERRED durable-write with no bounded flush during
recovery, NOT a missing write.
- The learner->voter promotion `becomeFollower()`
  (src/partition/partition-service-learner-promotion-methods.js:421-426) sets the in-memory role
  = FOLLOWER and calls `queueRoleUpdate(FOLLOWER)` — a QUEUED/deferred durable raft_role UPDATE.
- The flush of that queued role update is deferred until **metadata publication is ready**
  (roleMutationHelper, src/partition/partition-service-core-base.js). During post-restart
  control-plane recovery, publication readiness is itself blocked — so the durable raft_role row
  stays `learner`/null and may never flush before the gate reads it (deferred-write-no-bounded-
  flush, the CL-028-SECONDARY(i) / CL-016 lineage).
- The voter-ready activation emitter `waitForVoterReadyActivation()`
  (src/node/replica-handler-voter-readiness-methods.js:156) decides voter-ready from LOCAL
  in-memory state (`getTrackedReplicaRole`) + the cached services-row ADDRESS — it does NOT write
  the row's raft_role.
- The remove-safety evaluator reads a FRESH authoritative row (not a stale cache):
  src/rebalancer/priority-publication-safety-rows.js:61-86 merges
  readAuthoritativeControlPlaneRows() + cache, preferring authoritative. So the "different row"
  alternative is RULED OUT — it reads the same durable row whose raft_role never advances.
- The defers are logged ON 11601fe0, which is BOTH r4's host AND (this op) the dispatcher — so the
  node deferring "r4 not voter-ready" is the node that locally KNOWS r4 is a voter
  (getTrackedReplicaRole(r4)=FOLLOWER). Local truth is available at the gate; the durable row lags.

## Fix Design — RUBBER-DUCKED 2026-06-14 (subagent ae556ee5) → HYBRID, primary = (a-local)

DECISION: seed `raft_role` into the LOCAL systemTableCache row at promotion time via the existing
CL-016 local-commit path (NOT the control-plane gateway). Rejected: naive (a) through the gateway
(AuthoritativeRowMutationHelper.flush → control-plane-system-table-gateway.submitMutation, src/raft/
authoritative-row-mutation-helper.js:202,289) — returns DEFERRED/OWNER_NOT_READY during recovery,
RELOCATES the wedge (the CL-016 round-trip hazard, CONFIRMED). Rejected: pure (b) "read in-memory
role at the gate" — the gate's row source is durable, and the rebalance owner is not pinned to the
replica host in general. Rejected (c): a bounded retry owner ALREADY exists (scheduleRetry 30s cap)
but targets the blocked gateway lane — doesn't break the cycle.

Mechanism that makes (a-local) work end-to-end:
- The learner→voter promotion `becomeFollower()` (partition-service-learner-promotion-methods.js:
  421-426) is the seam: it sets in-memory role=FOLLOWER + queueRoleUpdate(FOLLOWER). ADD a
  local-cache raft_role write there for priority-control-plane partitions, via the sanctioned
  `applySystemTableChange` UPSERT that `seedLocalPriorityServiceRow`
  (replica-handler-create-methods.js:428-457) already uses — that helper currently OMITS raft_role
  (lines 440-449); the omission is the gap. Mark the row local-only (markServiceRowLocalOnly) so
  lifecycle UPSERTs don't wipe it (CL-021 lesson); the durable CDC confirm supersedes later.
- The safety merge `mergeReplicaRowsForSafety` (priority-publication-safety-rows.js:20-33) SKIPS
  null incoming fields, so a cache row with raft_role='follower' survives merge with an
  authoritative row whose raft_role is still null → the local seed is visible to the gate.
- OWNER LOCALITY RESOLVED FAVORABLY (run3+run4 artifacts): the ACTIVE-step remove-safety defer is
  always logged ON THE TARGET node (= replacement replica's host) — run4 ops 50c41276/7a2ae65e/
  c255a9af each deferred on their own target. So the dispatch-time gate is co-located with the
  replica host whose local cache the seed lands in. (a-local) suffices for the observed wedge.

SOUNDNESS (Q3): no joint-consensus two-phase config commit in this raft model — `becomeFollower`
runs only after `checkLearnerPromotion`'s leader-discovery + voter-count/budget gate on a

address present, so a non-active/addressless/learner replica still cannot pass — a source is never
removed before a real voter exists.
