## Task 1: leader write path + swallow sites (ranked)

### The leader write path (traced)
sql-routed write → `handleRemoteQuery` (src/partition/partition-service-entry-apply-base.js:291) → `executeQuery` (src/partition/partition-service-write-metrics-base.js:36) → **fork**:
- session known locally → `executeTransactionWrite` (write-metrics-base.js:168): runs SQL on `this.db` inside the open sqlite tx, stages in `transactionState.operations`, NO raft propose (replication deferred to PREPARE/COMMIT);
- no session → `proposeWrite` (write-metrics-base.js:418) → leader branch → `applyWrite` (line 598): `storage.appendEntry` (src/partition/partition-raft-storage.js:140-151, sync sqlite INSERT into `_raft_log` on `this.db`) → `executePartitionWriteStatement(this.db, …)` (line 664, optimistic local apply BEFORE commit) → `raftProvider.propose` (line 715) → liferaft `command()` (node_modules/@markwylde/liferaft/index.js:919) → `log.saveCommand` (src/raft/sqlite-log-adapter.js:274, ANOTHER `this.db` write) → replicate; quorum acks → `commitEntries` (index.js:943) → `log.commit` + emit('commit') → `applyCommittedEntry` (entry-apply-base.js:578; leader deduped via `recentlyAppliedEntryKeys` line 608).

**Structural key**: the raft log tail, the committedIndex watermark (`_raft_state`), and the applied table rows all live on ONE better-sqlite3 connection (`this.db`). One open (never-committed) transaction on that connection freezes ALL durable state at once with zero errors, while same-connection reads (incl. `getLastInfo` index minting) keep seeing the uncommitted writes — so in-memory raft leadership, replication, and applies continue normally.

### Ranked freeze mechanisms
1. **BINDING — zombie participant BEGIN, no timeout, empty-set 2PC commit.**
   - `beginTransaction` executes `db.exec(BEGIN_IMMEDIATE)` (src/partition/partition-service-transaction-base.js:398). No role guard (a follower would also BEGIN), no deadline.
   - **The sweep only covers prepared transactions**: `enforcePreparedStateHoldTimeouts` iterates `this.preparedTransactions` only (transaction-base.js:272-313). An ACTIVE (begun-never-prepared) session has no timeout, no sweep, no log line. THE recovery gap.
   - Coordinator-side empty-stage commit: `executeParticipantStage` silently `continue`s participants missing from the in-memory map (src/workflow/durable-workflow-coordinator.js:409-413) and falls back to `workflow.participants.keys()` when `participantKeys` is empty (lines 402-405) — zero participants ⇒ zero failures ⇒ `runCommitProtocol` marks COMMITTED (src/query/distributed/distributed-transaction-protocol.js:187-298) without a single participant message.
   - Live-state clobber that empties the participant set: `recoverFromSystemTables` (src/query/distributed/distributed-transaction-recovery.js:431-496) → `workflowCoordinator.recover()` → `setWorkflowState(createWorkflowRecord(...))` (durable-workflow-coordinator.js:459-471) **unconditionally replaces a LIVE in-memory transaction** with a cache-derived copy whose `participants` is a NEW Map built only from cache-visible rows (createWorkflowRecord line ~544-546: `new Map(record.participants…)` / `new Map()`), and `loadWorkflow` sets `writeOperations: []` (recovery.js:468). Entry points: `recoverDistributedTransactionStateFromCache()` at the TOP of EVERY `executeQuery` (src/query/sql-query-engine-statement-execution.js:345; one-shot flag NOT set while the sql_transactions cache is empty — src/query/sql-query-engine-transaction-recovery-methods.js:31-60, so it arms exactly when tx rows first become cache-visible ≈ this window), the periodic recovery sweep (recovery.js:209), and `loadAuthoritativeTransitionExecutionSession` (src/rebalancer/operation-workflow-transition-orchestration.js:64-144). CDC lag ⇒ the just-persisted participant row (08:02:59.119) is not yet cache-visible ⇒ recovered copy has participants=∅.
   - Enlist/rollback asymmetry: `enlistParticipants` records the participant only AFTER `await this.beginParticipant(...)` returns (src/query/distributed/distributed-transaction-coordinator.js:254-270; result not checked) — a thrown/timed-out begin leaves a possibly-delivered participant BEGIN that `runRollbackProtocol` can never target (`getRollbackParticipantKeys` walks `tx.participants` only, distributed-transaction-protocol.js:71-78).
   - Participant rollback latent bug: `rollbackTransaction`'s catch deletes session bookkeeping but SKIPS `db.exec(ROLLBACK)` when `replicateTransactionRollback` throws (transaction-base.js:617-651: ROLLBACK exec at 621 is after the replicate await; catch at 638-651 has no exec) — a second way to strand the sqlite tx.
2. **Absorption black hole (kept the log UPDATE-free post-wedge; independently freeze-capable).** A sessionless write reaching a partition with exactly one active transaction is silently absorbed into it: `resolveActiveTransactionSessionId(null)` falls back to "the single active session" (src/partition/partition-service-transaction-session-methods.js:26-37) → `executeQuery` picks `executeTransactionWrite` (write-metrics-base.js:76-90) → runs inside the zombie tx, returns success, NEVER raft-proposed, never durable. This is why post-08:02:59 transition UPDATEs that did reach node-3 vanished without a raft trace.
3. **SQLiteLogAdapter isOpen() silent no-op family** (NOT run-23's mechanism — a closed db would make `getLastInfo` return index 0 and mint wrong indices, contradicting followers' clean 150-155 — but a latent silent-freeze seam): every method silently no-ops when closed (src/raft/sqlite-log-adapter.js:51-53, put 209-214, saveCommand 274-297 still RETURNS a fabricated entry, commit 377-404, setCommittedIndex 555-572).
4. **liferaft commitEntries unawaited async forEach** (node_modules/@markwylde/liferaft/index.js:943-948): a throw in `log.commit()` or the 'commit' handler (`applyCommittedEntry` re-throws at entry-apply-base.js:686) becomes an unhandledRejection; apply errors never reach any caller. Plus `commitPromise.catch(() => {})` (write-metrics-base.js:656) and `raftProvider.propose` failure logged at DEBUG (line 716-719).

## Task 2: 'Query timeout after 1ms' — VERDICT: symptom of a broken budget derivation, NOT the freeze cause; but a real, independent killer of priority-op transitions

- Message minted at src/query/distributed/parallel-query-coordinator.js:349-356 with `effectiveTimeoutMs = options.timeoutMs` (resolveTimeoutMs line 670-672). The timeout only rejects the `Promise.race` — the participant execution promise keeps running detached; no abort/rollback at this layer.
- **The 1 comes from `resolveOperationMutationQueryTimeoutMs`** (src/rebalancer/replica-operation-repository-mutation-gateway-methods.js:469-487): `if (budgetRemainingMs <= 0) return 1;` — an EXHAUSTED budget still dispatches the mutation with a doomed 1ms timeout instead of failing fast.
- **The budget is anchored at `operation.createdAt`**, not the attempt start: `buildPriorityDispatchTransitionMutationBudget(operation, operation.createdAt ?? now)` (operation-workflow-transition-orchestration.js:530-533, 780-789); for sql_write_operations-p1 ops the budget is `REPLICA_OPERATION_DISPATCH_TIMEOUT_MS` = **5s** (orchestration.js:799-805; operation-workflow-owner-shared.js:371). 941c4acd was created 08:02:48 ⇒ from 08:02:53 onward every transition attempt computes remaining ≤ 0 ⇒ 1ms ⇒ guaranteed failure ⇒ **permanent doom-loop** (every retry re-anchors at the same createdAt). Its observed failure at 08:03:02 is exactly this.
- Cause-vs-symptom for the FREEZE: the wedge-opening transaction (303af027, module_manifests-p1 = non-priority) did NOT use this budget (`shouldUsePriorityDispatchTransitionMutationBudget` false; and priority ops bypass the 2PC entirely via `shouldBypassTransitionExecutionTransaction`, operation-workflow-owner-execution-lane.js:696-720 → `disableSystemWriteSession`). So the 1ms budget did not open the zombie BEGIN. It IS however the reason priority-op transitions (941c4acd etc.) could never persist again even where the participant was healthy, and post-wedge it hid the participant's true responses (TRANSACTION_ALREADY_ACTIVE / absorption success) behind client-side timeouts.
- The attack hypothesis "1ms abort wedges sqlite mid-write" is REFUTED mechanically: better-sqlite3 statements are synchronous and uninterruptible; the 1ms timeout is client-side only. The wedge needs an explicit un-closed BEGIN, which is mechanism #1.

## Task 3: INSERT vs UPDATE asymmetry — explained

- Creates (INSERT OR IGNORE) travel the **sessionless** lane: `executeQuery` → `proposeWrite` → `applyWrite` → local append+apply on the leader (into the zombie tx: succeeds in-memory, non-durable) **and `raftProvider.propose`** → followers (r2@node-0, r5@node-4, r6@node-2; membership was 4 replicas — leftover r2 never removed) append + commit durably. Quorum=3 is satisfied by the leader's in-memory ack + followers' acks; the leader's DISK is not part of the raft contract anywhere. Index minting stayed correct because `saveCommand`/`getLastInfo` read through the leader's own connection, which SEES the uncommitted `_raft_log` rows (entries 150-155 exist inside the zombie tx). Follower `_raft_log.timestamp` for 150-155 (08:03:11.34 → 08:05:23.728) match node-3's in-memory apply read-backs — the leader genuinely replicated post-freeze.
- Transition UPDATEs after 08:02:58 had three fates, none reaching the raft log: (a) non-priority 2PC UPDATEs (303af027 REMOVED, 4cb4188a REMOVED, 52303232 STOPPING/REMOVED — tx rows COMMITTED 08:03:04/09/15 with zero raft markers) were staged **in-session** into the zombie transaction or empty-set-committed coordinator-side; (b) priority-op sessionless UPDATEs that reached node-3 were **absorbed** into the zombie session (mechanism #2) — success in-memory, no propose; (c) priority-op UPDATEs killed client-side by the 1ms doom-loop before/regardless of delivery. Hence: entries 150-155 all INSERT OR IGNORE, zero UPDATEs cluster-wide.
- Note the leader was NOT "frozen at 149 in memory" — it applied 150-155 and continued serving raft; only durability froze. "Committed via followers" is precise: the durable copies live only on followers.
