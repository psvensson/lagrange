2. Narrow proposed contract (NOT yet implementation-approved)

Proposed identity direction for review: payload.requestId, scoped by serviceDefinitionId, generated and retained by the logical write caller before first delivery. K=(serviceDefinitionId,requestId); exact semantic contents C=(commandVersion,KV_SET,sessionId,key,canonical value bytes). Transport route, current leader and delivery attempt are not C. This would be a NEW caller/command contract, not an unchanged optional field. No source edit can claim its producers already retain it.

Proposed application record direction: a WASM-owned typed outcome relation in the same existing replica database, keyed by K and binding C, with original outcome and actual term/index. This is a NEW persistent schema/version/recovery obligation under the existing WASM application owner, not a new global service. Success and deterministic refusal are distinct; environmental rollback creates no terminal result. No outcome format, production limit or retirement rule is adopted by this gate.

Required transition rules:
- Invalid input or proven pre-proposal admission refusal: no consensus effect; return a typed refusal. A generic error after proposal entry is not proof of absence.
- Enroll bounded local completion interest before proposal; exact pending duplicate joins that intent only after content match. Physical repeated proposals still belong to runtime custody; deduplication of waiters does not make physical occurrences free.
- At actual apply prefix, retained matching K/C: answer its original result without repeating KV effects. Same K/different C: conflict refusal, no overwrite of original outcome or user value. Original identity cannot be reassigned.
- First admissible K/C: effect and exact result in the same transaction as applied position. afterCommit delivers that result; afterRollback can report uncertainty/environment failure but cannot announce successful application.
- Timeout/demotion/shutdown/lost response after possible proposal: keep original K/C in the caller; UNKNOWN unless a retained authoritative result is available. A later authoritative outcome may settle a later query/retry; no automatic new ID.
- Historical detail unavailable: explicit unavailable-history/UNKNOWN classification with non-reexecution protection. It is not NOT_COMMITTED and cannot authorize re-execution.

3. Exact decisions required before implementation

D1 — Caller identity and compatibility. Select the actual producer/API that owns payload.requestId through first delivery, redirect, lost response and retry, including restart if promised. Decide the behavior of existing identity-less calls: refuse before proposal, migrate via an explicit caller-side enrollment, or explicitly scoped one-shot support with its weaker replay semantics. The last option does not by itself satisfy this complete repair. Server-generated IDs returned only after success cannot recover a lost response. The frozen witness file has no request-ID assertion, but its current fixture sends no ID and proposalEntries filters by the exact old encoded command bytes (fixture165-170). Adding request identity/version would make that unchanged observation match zero proposals. Preserve original file/fixture/results. A new identity/encoding profile therefore needs an explicit reviewed companion or fixture-supersession decision, with the frozen .test.js unchanged where feasible and a separately frozen fixture. It cannot be called an identical-original-input GREEN. The same semantic premature-success assertion must remain reachable on the source-negative treatment; missing-field/zero-match rejection is not its RED. Do not weaken the witness or silently choose compatibility.

D2 — Persistent result/version and old commands. Approve the WASM-owned canonical command/result schema and migration behavior for existing KV data and already-committed identity-less commands. Original exact outcomes cannot be fabricated from today's KV row or guessed from arbitrary retained logs. Identify the meaning of recovery with an old database: live KV recovery can be valid while historical exact requests are unavailable. Preserve application/refusal result and actual position, not requested disposition. The existing operation-port committedEntryApplication adapter converts native index/term to Number (raft-rs-operation-port.js:116-122); a new outcome schema must address that supplied-position precision seam rather than stringify an already-rounded number or silently promise arbitrary exact64-bit positions. No generic runtime edit is authorized by this observation. Any deterministic size policy used at apply must have common authoritative inputs; local follower pressure cannot change the result of accepted history.

D3 — Finite retention and pending-resource contract. Select a bounded replay policy and its durable non-reexecution protection. A TTL/LRU deletion of arbitrary request-ID outcomes is unsafe: A applies, B applies, A's row expires, A retries and overwrites B. Keeping every UUID forever is unbounded. The owner must choose a finite caller/history-generation or acknowledgement/frontier contract with explicit old-request responses, or another proved bounded equivalent. No such WASM protocol exists today. Specify count and byte bounds, pinned uncertain obligations, the event enabling retirement, local waiter count/deadline, and restart reconstruction. At capacity, refusing new work may be necessary, but permanent saturation with no owned release is not a complete progress contract. New finite numbers alone do not decide this. Physical WAL/log/page/snapshot costs remain with storage/runtime owners; a waiter limit is not their bound.

These decisions are coupled: how K carries admissible history is what permits safe finite outcome retirement. They must be reviewed as one small WASM request/application/lifecycle contract, not separate partial source patches.

4. Minimal counterexamples at this gate (reasoned traces, not new native executions)

Registration race: propose -> synchronous apply/commit -> publish callback -> register waiter. Completion is lost; enroll first.
Rollback race: KV apply callback -> resolve success -> applied-state write/transaction commit throws. Caller sees false success; publish only afterCommit.
Lost response: server chooses K -> applies A -> reply containing K lost -> caller retries without K. Existing inputs cannot distinguish retry from new intent; caller must own K before delivery.
A/B/A: commit K_A/valueA -> lose response -> commit K_B/valueB -> retry K_A. Blind applySet overwritesB. Retained exact result must bypass the effect.
Eviction: same trace after K_A outcome deletion. Absence cannot be freshness; a bounded durable retirement fence is required.
Restart: commit outcome -> process loss before afterCommit notification. Volatile Map cannot answer; recover the durable result or explicitly unavailable history, never current-value inference.
