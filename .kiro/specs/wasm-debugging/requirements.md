# Requirements Document

## Introduction

This feature adds debugging capabilities for WASM functions executing in the distributed database system. WASM functions run in two contexts: on service replicas (via WasmExecutor) and on partition replicas during ctx.call callback stages (via CallbackExecutionHost). A ctx.call chain can span multiple partition replicas across different nodes.

The feature is delivered in three phases:
1. **Structured Tracing** — host-imported `debug.trace()` with lineage-correlated event forwarding to a VS Code extension
2. **DWARF-based Source-Level Debugging via DAP** — breakpoints, variable inspection, and distributed debug coordination
3. **Snapshot + Replay Debugging** — deterministic execution capture and local replay with full interactive debugging

## Glossary

- **Debug_Trace_Host**: The host-side component that implements the `debug.trace(level, message, context)` import function available to WASM modules
- **Trace_Event**: A structured record produced by Debug_Trace_Host containing the trace message, level, timestamp, lineage_id, stage_id, partition_id, node_id, and service_definition_id
- **Trace_Collector**: The per-node component that receives Trace_Events from all local replicas and forwards them to connected debug clients
- **Debug_Session**: A stateful object attached to a WasmExecutor or CallbackExecutionHost instance that gates debug functionality and tracks active debug state
- **Debug_Capability**: A capability string (`debug.trace`, `debug.breakpoint`, `debug.snapshot`) declared in module manifests and enforced by CapabilityPolicy
- **DAP_Server**: A Debug Adapter Protocol server instance running per-replica when a debug session is active, exposing breakpoint, step, and variable inspection operations
- **Debug_Coordinator**: A component that tracks which node/replica is executing the current stage of a ctx.call chain and routes debug client connections to the correct DAP_Server
- **Execution_Snapshot**: A deterministic capture of WASM function inputs, host call results, and memory state at stage boundaries, serialized for replay
- **Replay_Runtime**: An embedded WASM runtime in the VS Code extension that replays Execution_Snapshots with DWARF-based source-level debugging
- **Lineage_ID**: An existing deterministic identifier generated by LineageTracker that correlates operations across stages and retries
- **Stage_ID**: An existing identifier within a ctx.call chain that identifies a specific callback stage execution
- **DWARF_Info**: Debug information in DWARF format, either embedded in the WASM binary or provided as a separate sidecar via the `external_debug_info` custom section
- **Fuel_Metering**: A WASM runtime mechanism that limits execution by counting instructions, used to implement breakpoint suspension
- **Debug_Channel**: A WebSocket connection between the Trace_Collector (or DAP_Server) and the VS Code extension

## Requirements

### Requirement 1: Debug Capability Declaration

**User Story:** As a module developer, I want to declare debug capabilities in my module manifest, so that the system can gate debug features per module and enforce policy.

#### Acceptance Criteria

1. WHEN a module manifest declares `debug.trace` in its capabilities array, THE Capability_Policy SHALL allow the Debug_Trace_Host import to be injected into the WASM runtime
2. WHEN a module manifest does not declare `debug.trace` in its capabilities array, THE Capability_Policy SHALL reject any attempt to use the debug.trace host import
3. WHEN a module manifest declares `debug.breakpoint` in its capabilities array, THE Capability_Policy SHALL allow DAP_Server attachment to that module's execution
4. WHEN a module manifest declares `debug.snapshot` in its capabilities array, THE Capability_Policy SHALL allow Execution_Snapshot capture during that module's execution
5. THE Debug_Capability strings SHALL be defined as named constants in a dedicated debug constants file

### Requirement 2: Structured Trace Emission (Phase 1)

**User Story:** As a WASM module developer, I want to call `debug.trace(level, message, context)` from my module code, so that I can emit structured diagnostic information during execution.

#### Acceptance Criteria

1. WHEN a WASM module calls `debug.trace(level, message, context)`, THE Debug_Trace_Host SHALL create a Trace_Event containing the level, message, context, current timestamp, lineage_id, stage_id, partition_id, node_id, and service_definition_id
2. WHEN no debug session is active for the executing replica, THE Debug_Trace_Host SHALL discard the trace call with zero additional overhead beyond the host function call itself
3. WHEN a debug session is active, THE Debug_Trace_Host SHALL forward the Trace_Event to the Trace_Collector on the same node
4. THE Debug_Trace_Host SHALL validate that the level parameter is one of the defined trace levels (error, warn, info, debug, trace)
5. IF the level parameter is not a valid trace level, THEN THE Debug_Trace_Host SHALL reject the call with a descriptive error
6. THE Debug_Trace_Host SHALL attach lineage_id and stage_id from the existing LineageTracker and CallbackContext without creating duplicate tracking state

### Requirement 3: Trace Collection and Forwarding (Phase 1)

**User Story:** As a developer using the VS Code extension, I want to receive trace events from all nodes in real time, so that I can observe the execution of a distributed ctx.call chain.

#### Acceptance Criteria

1. THE Trace_Collector SHALL accept Trace_Events from all local replicas (both WasmServiceReplica and partition callback replicas) on the same node
2. WHEN a Debug_Channel is connected, THE Trace_Collector SHALL forward Trace_Events to the connected VS Code extension with ordering preserved per-replica
3. WHEN no Debug_Channel is connected, THE Trace_Collector SHALL discard Trace_Events without buffering
4. THE Trace_Collector SHALL expose a WebSocket endpoint for Debug_Channel connections
5. WHEN a Debug_Channel connects with a lineage_id filter, THE Trace_Collector SHALL forward only Trace_Events matching that lineage_id prefix
6. THE Trace_Collector SHALL serialize Trace_Events to JSON for transmission over the Debug_Channel

### Requirement 4: Debug Session Lifecycle

**User Story:** As a developer, I want to attach and detach debug sessions to running WASM services, so that I can enable debugging without restarting the service.

#### Acceptance Criteria

1. WHEN a debug session is started for a service_definition_id, THE Debug_Session SHALL be attached to the WasmExecutor on the replica currently executing that service
2. WHEN a debug session is started for a ctx.call chain identified by lineage_id, THE Debug_Session SHALL be attached to the CallbackExecutionHost processing the current stage
3. WHEN a debug session is detached, THE Debug_Session SHALL remove all debug state from the executor and restore normal execution with zero overhead
4. THE Debug_Session SHALL be gated by the module's declared Debug_Capability — a session requesting breakpoint functionality SHALL require `debug.breakpoint` capability
5. IF a debug session is requested for a module that lacks the required Debug_Capability, THEN THE system SHALL reject the session with a descriptive error

### Requirement 5: DAP Server for Source-Level Debugging (Phase 2)

**User Story:** As a developer, I want to set breakpoints and inspect variables in my WASM source code, so that I can debug my functions interactively.

#### Acceptance Criteria

1. WHEN a debug session with breakpoint capability is active, THE DAP_Server SHALL start on the replica hosting the active execution
2. THE DAP_Server SHALL implement the Debug Adapter Protocol for setBreakpoints, continue, next, stepIn, stepOut, threads, stackTrace, scopes, and variables requests
3. WHEN a breakpoint is set at a source location, THE DAP_Server SHALL translate the source location to a WASM instruction offset using DWARF_Info
4. WHEN execution reaches a breakpoint instruction offset, THE DAP_Server SHALL suspend WASM execution using Fuel_Metering or epoch interruption
5. WHEN a variables request is received, THE DAP_Server SHALL read WASM linear memory and local variables via the runtime introspection API and map them to source-level names using DWARF_Info
6. IF DWARF_Info is not available for the executing module, THEN THE DAP_Server SHALL report an error indicating that source-level debugging requires debug info

### Requirement 6: Distributed Debug Coordination (Phase 2)

**User Story:** As a developer debugging a ctx.call chain, I want the debugger to automatically follow execution across nodes and replicas, so that I can debug distributed callbacks without manually reconnecting.

#### Acceptance Criteria

1. THE Debug_Coordinator SHALL track which node and replica is executing the current stage of a ctx.call chain using lineage_id and stage_id
2. WHEN a callback stage completes and the next stage begins on a different replica, THE Debug_Coordinator SHALL notify the VS Code extension of the new DAP_Server endpoint
3. WHEN the VS Code extension receives a stage transition notification, THE Debug_Coordinator SHALL provide the new node address, replica_id, and DAP_Server port
4. THE Debug_Coordinator SHALL use existing CDC events and the services system table to discover replica locations without creating a parallel discovery mechanism

### Requirement 7: Execution Snapshot Capture (Phase 3)

**User Story:** As a developer, I want the system to capture a deterministic execution trace when debug mode is enabled, so that I can replay and debug executions after the fact.

#### Acceptance Criteria

1. WHEN debug snapshot mode is enabled for an execution, THE system SHALL capture WASM function inputs for each stage invocation
2. WHEN debug snapshot mode is enabled, THE system SHALL capture the return values of all host calls made by the WASM module during execution
3. WHEN debug snapshot mode is enabled, THE system SHALL capture WASM linear memory snapshots at stage boundaries (before and after each callback invocation)
4. THE Execution_Snapshot SHALL include lineage_id, stage_id, partition_id, node_id, and timestamps for each captured frame
5. THE Execution_Snapshot SHALL be serializable to a binary format suitable for transmission to the VS Code extension

### Requirement 8: Snapshot Replay Debugging (Phase 3)

**User Story:** As a developer, I want to replay a captured execution snapshot locally with full interactive debugging, so that I can debug complex distributed issues without affecting the live system.

#### Acceptance Criteria

1. WHEN the VS Code extension receives an Execution_Snapshot, THE Replay_Runtime SHALL load the WASM module with DWARF_Info in an embedded local runtime
2. THE Replay_Runtime SHALL replay execution deterministically by providing captured host call results instead of making live calls
3. THE Replay_Runtime SHALL support all DAP operations (breakpoints, stepping, variable inspection) against the replayed execution
4. FOR ALL valid Execution_Snapshots, replaying with the same inputs and captured host call results SHALL produce identical execution traces (determinism property)

### Requirement 9: Zero-Overhead Debug Gating

**User Story:** As a system operator, I want debug features to have zero runtime overhead when not in use, so that production performance is unaffected.

#### Acceptance Criteria

1. WHEN no debug session is active for a replica, THE WasmExecutor SHALL execute WASM functions with zero additional overhead from debug instrumentation
2. WHEN no debug session is active for a callback stage, THE CallbackExecutionHost SHALL execute callbacks with zero additional overhead from debug instrumentation
3. THE debug host import (`debug.trace`) SHALL be injected only when the module declares the `debug.trace` capability AND a debug session is active
4. WHEN debug capability is declared but no session is active, THE Debug_Trace_Host SHALL execute the trace call as a no-op without allocating Trace_Event objects

### Requirement 10: Debug Metadata Persistence

**User Story:** As a system architect, I want all debug metadata to flow through the existing SQL/CDC write path, so that the debug system respects the single-owner-per-concern principle.

#### Acceptance Criteria

1. THE system SHALL store active debug session records in a system table accessible via the SQL engine
2. WHEN a debug session is created or destroyed, THE system SHALL write the change through the SQL/CDC path so all nodes receive the update via CDC events
3. THE system SHALL NOT create direct inter-node communication channels for debug session state outside the existing MessageRouter and CDC infrastructure
