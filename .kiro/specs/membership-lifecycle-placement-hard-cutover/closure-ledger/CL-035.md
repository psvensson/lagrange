# CL-035 A Replica's Voter-Ready Raft Promotion Must Be Visible To The REPLACE Remove-Safety Gate On Its Own Node

- Status: OPEN (recorded 2026-06-14 from stat-gate 20260614T162505Z runs 3+4; first-violated
  invariant pinned with single-node local evidence; NO code yet — closure-grammar = record
  before fix). Next step = falsify the raft_role-write hypothesis, then rubber-duck + fix +
  guard + gate.
- Concern: placement-priority-spread (post-restart priority control-plane spread recovery) /
  replica-activation-evidence — the CL-016 voter-ready-evidence + CL-021 raft_role-row lineage,
  resurfacing in the post-restart settle phase as the surplus-drain/settle class the handoff named.
- Failure Class: liveness (a materialized replacement replica never satisfies the remove-safety
  voter-ready gate, so the REPLACE wedges at workflowStep=ACTIVE and priority control-plane
  spread never recovers within the scenario budget — publication membership CONVERGES, but the
  scenario probe reports PRIORITY_CONTROL_PLANE_RECOVERY_PENDING). Never corruption: the
  safety policy is CORRECTLY conservative (never remove the old replica before its replacement
  is voter-ready); the defect is that the replacement's voter-readiness is not observable to
  the gate, not that the gate is wrong.

## First Violated Invariant

After a REPLACE's replacement replica reaches voter-ready raft state (learner -> voter promotion
completes locally), the REPLACE remove-safety gate evaluating that operation must observe the
replica as voter-ready within bounded time and proceed to remove the superseded source replica.
It must NOT defer the remove indefinitely on a stale "replacement replica is not voter-ready"
view — even on the replacement replica's OWN node, where the promotion truth is locally known.

## Mechanism (pinned; one local-write gap, no cross-node propagation needed)

The node that owns r4 and logged its voter-ready activation (11601fe0) is the SAME node that
then defers the remove claiming r4 "is not voter-ready". So the gap is entirely local:
r4's raft promotion (learner -> voter) at 16:40:52 updated r4's LOCAL raft / activation state
but did not write through to the **replica row's `raft_role` field** that the safety gate reads.

- Gate locus: `operation-workflow-remove-safety-evaluator.js:319,397-398` calls
  `context.isVoterReadyReplicaTopology(replacementReplicaRow)` /
  `context.isVoterReadyRoutableReplica(...)`.
- Predicate: `priority-publication-safety-topology.js:112 isVoterReadyReplicaTopology(replicaRow)`
  returns false unless `replicaRow.status` in {ACTIVE, SYNCING} (r4 = active, PASSES),
  `replicaRow.address` present (PASSES), AND `replicaRow.raft_role` is a non-null string that is
  NOT `learner` (the FAILING condition: r4's row still carries raft_role=learner or null after
  the local promotion).
- So the binding sub-condition is the `raft_role` field of the replacement replica's row, exactly
  the column class as [CL-021] (raft_role row write) and the evidence-locality concern of
  [CL-016] (voter-ready activation must reflect local truth without a durable round-trip through
  the control plane being recovered).

## Next Falsification Step (do FIRST, before fixing)

Confirm that r4's replica row (as read by the safety evaluator on 11601fe0) carries
raft_role=learner/null at the defer time, i.e. the learner->voter promotion event does not write
the row's raft_role. Read the voter-ready activation path ("Replica reached voter-ready activation
state" emitter) and find whether/where it updates the replica/services row raft_role; confirm the
remove-safety evaluator reads from that same row vs. a stale snapshot. Rule out the alternative
that the gate reads a DIFFERENT (e.g. cached/CDC) row than the one the promotion updates.

## Fix Direction (candidate, rubber-duck before coding)

Either (a) the voter-ready activation must write the replica row's raft_role to the post-promotion
role (the CL-021-class row-write fix, scoped to the activation path), or (b) the remove-safety
voter-ready predicate must accept the replica's LOCAL authoritative voter-ready activation evidence
when the row's raft_role lags (the CL-016-class "accept local truth" fix). Prefer the one that does
NOT weaken the safety gate for genuinely-not-ready replacements. MANDATORY: the gate must still
block removal when the replacement is truly a learner / not caught up (never-break-only-slow:
removing the source before a real voter exists risks losing the priority control-plane quorum).
