# CL-036 Control-Plane Publications Spread Recovery Must Not Be Gated On A Node-Readiness That Is Itself Gated On Publications Recovery

- Status: OPEN (recorded 2026-06-14 from stat-gate 20260614T172031Z run4; first-violated
  invariant + circular mechanism pinned with single-node evidence; NO code yet — closure-grammar =
  record before fix). This is an instance of the [[circular-dependency-class-formation-vs-steady-state]]
  meta-pattern; the project memory warns this class has attracted parallel/wrong fixes — rubber-duck
  + careful design before coding. Non-deterministic: surfaced in 1/4 runs (the SLOW run) under a
  heavy 4/5-node rolling restart; confirm frequency before promoting a fix.
- Concern: placement-priority-spread (control_plane_publications-p1 post-restart spread recovery)
  under heavy rolling restart; the circular formation/recovery readiness dependency.
- Failure Class: liveness (circular dependency → spread move never planned → spread stuck <3 →
  the recovery-pending nodes never get the spread → they REGRESS from ready back to recovery-
  pending → spiral). Run4 was SLOW (not stalled) — the system degrades safely; this is the
  binding latency wedge in that run, distinct from CL-035 (which is GUARDED: 0 not-voter-ready
  defers in this same gate).

## First Violated Invariant

Priority control-plane publications spread recovery must make progress whenever a sufficient
quorum of nodes can host a control-plane replica. It must NOT be gated on a per-node readiness
dimension that is itself satisfied only AFTER priority control-plane recovery completes — under
rolling restart that is circular (spread move requires all active nodes "ready" → node "ready"
requires priority-recovery complete → priority-recovery requires the spread), and unlike every
OTHER priority partition, control_plane_publications has NO quorum escape, so the spread wedges
whenever any ACTIVE node is still recovery-pending.

  3), never reaching the required >=3 distinct; last critical log 17:45:39, run end ~17:46:02.
- The spread MOVE is never planned: the planner emits "Waiting for transitional cluster membership
  to settle before planning critical system rebalancing" x39 for control_plane_publications-p1.
  Early blockerReason=topology_operations_in_flight; LATE (17:45:15-30, near end)
  blockerReason=`node_ready_lease_incomplete`, unreadyNodeIds=[11601fe0, 8be8d30f].
- BUT those 2 nodes were READY: 11601fe0 reached `join_ready ready=true` at 17:43:22, 8be8d30f at

  counted them unready:2. Then at 17:45:34 BOTH regressed to `degraded ready=false
  PRIORITY_CONTROL_PLANE_RECOVERY_PENDING` (the spiral: spread never came, so recovery-pending
  re-asserted and readiness was lost).
- The unready classification is NOT the nodes-table status path: the seed saw both nodes
  status="active" (96x each), state ready/steady. So it is the readiness-DIMENSION path
  (unified-rebalancer-critical-topology-methods.js:120 `!nodeMembershipReady` from
  controlPlaneReadinessService.getNodeReadinessSync), and the dimension is unsatisfied because the
  node is PRIORITY_CONTROL_PLANE_RECOVERY_PENDING. That is the closed loop.

## Mechanism + Locus (pinned)

`buildCriticalSystemTopologySettlingDecision` (unified-rebalancer-critical-topology-methods.js:60-153):
- For each ACTIVE node it computes `nodeMembershipReady = isReadinessDimensionSatisfied(
  getNodeReadinessSync(nodeId), readinessDecisionDimension)` (:98-109). A node that is
  ACTIVE-status but recovery-pending is pushed to `unreadyNodeIds` (:120-123).
- If any node is transitional/unready, it normally returns
  NODE_READY_LEASE_INCOMPLETE / TRANSITIONAL_NODE_MEMBERSHIP and blocks the spread (:142-152).
- There IS a quorum escape (:135-139): `priorityRecoveryMayProceedOnQuorum =
  isControlPlanePriorityPartition() && !isControlPlanePublicationPriorityPartition() &&
  hasRequiredHealthyNodes` — i.e. other priority partitions (e.g. sql_write_operations-p1, observed
  proceeding in this run) may spread once a healthy QUORUM is ready, tolerating still-converging
  nodes. control_plane_publications is EXPLICITLY EXCLUDED (`!isControlPlanePublicationPriorityPartition()`,
  :137), so it requires ALL active nodes ready — the binding difference.

## Open Questions to resolve BEFORE coding (rubber-duck)

1. WHY is control_plane_publications excluded from the quorum escape? Likely deliberate: publications
  is the membership-authority partition (spreading/REPLACING it while membership is unsettled could
  perturb the very membership truth). So "just add publications to the escape" may be UNSAFE — verify
  the intent (git blame :137, the membership-lifecycle cutover design) before relaxing it.
2. Is the binding sub-condition the node-readiness dimension being too STRONG for spread-targeting?
  A node that is ACTIVE + can host a control-plane replica should be a valid spread TARGET even
  before its OWN priority recovery fully completes. Candidate de-circularizing fix: use a weaker
  "control-plane-replica-hostable" readiness for spread TARGET eligibility than the full
  recovered-dimension, so the spread that COMPLETES recovery is not gated on recovery being complete
  (the [[circular-dependency-class-formation-vs-steady-state]] "leader-authoritative local
  establishment for recovery" direction).
3. Confirm reproducibility/frequency (1/4 here, non-deterministic; 4/5 restart is an extreme corner
  near the 3-node hard floor the handoff flags as not-realistic). Gate a few more runs to see how
  often control_plane_publications is the binding SLOW cause before investing in the fix.

## Candidate Witness (for whatever fix)

A heavy rolling-restart run where control_plane_publications-p1 reaches >=3 distinct spread within
budget without waiting for every restarted node's full priority-recovery; no
node_ready_lease_incomplete deferral persisting while the named unready nodes are at join_ready
ready=true; the ready→degraded readiness regression at the spread-pending window disappears.
