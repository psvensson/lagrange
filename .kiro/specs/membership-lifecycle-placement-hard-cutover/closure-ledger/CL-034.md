- Status: OPENED (locus pinned from CL-033 profiled gate 161104Z + CL-001 variant-B
  owner trace; fix designed + rubber-ducked; no code yet — record-before-code)
- Concern: control-plane-seed event-loop liveness under post-restart recovery
  (the RESIDUAL of CL-033, and the binding root of CL-001 variant B)
- Failure Class: liveness (synchronous hot-path cost -> event-loop freeze -> raft
  election-timeout breach -> publication leadership loss -> published-epoch freeze)
- First Violated Invariant: during post-restart recovery the per-routing-call
  readiness build must not run synchronously long enough (cumulatively, per event-loop
  turn) to exceed the raft election timeout. CL-033 eliminated the 55s projection

  ~14s gap still exceeds the raft election timeout, so the seed loses
  control_plane_publications-p1 leadership mid-recovery and the published epoch freezes
  (= CL-001 variant B, see closure-ledger/CL-001.md "VARIANT B — REFINED + PINNED
  2026-06-14").

### Fix Design (rubber-ducked; corrected after the design subagent mis-located the call sites)

LOCUS (verified by grep — `resolveMembershipPublicationPlanningSnapshot` has exactly
two callers, both in stage-3: :471 async [not hot] and :503 sync [hot]): memoize the
merge OUTPUT inside `resolveNodeMembershipPublicationPlanningAnswerSync` (stage-3:503),
the sole hot caller via getNodeReadinessSync. The design subagent's claim of additional
call sites in segment-4-stage-4 / runtime-authority-methods was WRONG
(buildEvaluatedNodeReadinessSnapshot consumes the already-resolved
context.membershipPublicationPlanningSnapshot; it does not re-call the merge).

FIX (mirror CL-033 exactly):
- New `resolveMemoizedMembershipPublicationPlanningSnapshotSync(nodeId, observedAt,
  membershipPublication, planningSnapshot)` wrapping the stage-3 merge
  `resolveMembershipPublicationPlanningSnapshot({nodeId, observedAt, membershipPublication,
  membershipPublicationPlanningSnapshot: planningSnapshot})`, keyed per publisher node
  (nodeId || this.nodeId), reused when `!isReadinessSnapshotInvalidated(memoKey,
  capturedAtMs)` AND within `membershipPublicationPlanningActiveStaleGraceMs` AND the
  latest publication epoch/status still match the cached projection (the identical
  validity predicate `resolveMemoizedPriorityRecoveryPlanningProjectionSync` uses).
- The side-effectful per-node layer `resolvePriorityRecoveryPlanningAnswer` (storeActive/
  clearActive) stays OUTSIDE the memo and runs every call on the cached frozen merge,
  exactly as CL-033 keeps it outside its projection memo.
- New field `membershipPublicationPlanningSnapshotMemoByNodeId` (segment-1.js init,
  alongside priorityRecoveryPlanningProjectionMemoByNodeId), cleared on
  membership-service swap (segment-1.js:325) and cache swap (segment-1.js:360).

SAFETY (why no new staleness class — same argument CL-033's verifier accepted):
- The merge output is ALREADY `Object.freeze(...)` today (buildPriorityRecoveryPlanning
  Projection, stage-1:464 ends `return Object.freeze({...})`), so reusing the same
  instance across calls introduces ZERO new mutation hazard; resolvePriorityRecovery
  PlanningAnswer already receives it frozen.
- Invalidation covers every decision-relevant input: ack/epoch/status changes are
  CONTROL_PLANE_PUBLICATIONS row writes -> handleCacheChange advances the cluster marker
  (snapshot-store.js:625-632) -> memo invalid; NODES/SERVICES changes advance the
  per-node marker (:634-641) -> memo invalid. The ONLY un-invalidated window is
  PARTITIONS / NODE_ENDPOINTS, which CL-033 already tolerates for the identical reason
  (advancing the marker on PARTITIONS — the highest-churn table in recovery — would
  collapse all reuse and re-open the freeze). The CL-034 merge consumes the same cluster
  state as the CL-033 projection it sits next to, so it reproduces exactly the existing
  PARTITIONS-stale window, not a wider one.

GUARD (red-on-revert): test/control-plane/cl-034-planning-snapshot-merge-memo.test.js —
(a) build-once-per-stable-epoch (N routing calls -> 1 merge build); (b) exactly-one-
rebuild-per-invalidation (invalidate via NODES/PUBLICATIONS marker -> exactly one
rebuild); (c) per-publisher-node keying (invalidating node A does not rebuild node B);
(d) nodeId||this.nodeId fallback. Neutralizing the memo must fail (a)-(c).
