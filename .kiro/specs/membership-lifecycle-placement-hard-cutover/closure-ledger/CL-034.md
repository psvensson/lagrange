## CL-034 The Residual Readiness-Build Merge Must Not Run Per-Routing-Call Long Enough To Lose Raft Leadership During Recovery

- Status: OPENED (locus pinned from CL-033 profiled gate 161104Z + CL-001 variant-B
  owner trace; fix designed + rubber-ducked; no code yet — record-before-code)
- Concern: control-plane-seed event-loop liveness under post-restart recovery
  (the RESIDUAL of CL-033, and the binding root of CL-001 variant B)
- Failure Class: liveness (synchronous hot-path cost -> event-loop freeze -> raft
  election-timeout breach -> publication leadership loss -> published-epoch freeze)
- First Violated Invariant: during post-restart recovery the per-routing-call
  readiness build must not run synchronously long enough (cumulatively, per event-loop
  turn) to exceed the raft election timeout. CL-033 eliminated the 55s projection
  freeze but a ~14s residual REMAINS, dominated by the stage-3 membership-publication
  planning-snapshot MERGE (`resolveMembershipPublicationPlanningSnapshot`,
  control-plane-readiness-service-segment-4-stage-3.js:19) which is NOT covered by the
  CL-033 projection memo and rebuilds on every routing call during recovery churn. The
  ~14s gap still exceeds the raft election timeout, so the seed loses
  control_plane_publications-p1 leadership mid-recovery and the published epoch freezes
  (= CL-001 variant B, see closure-ledger/CL-001.md "VARIANT B — REFINED + PINNED
  2026-06-14").
- Authoritative Owner: ControlPlaneReadinessService sync readiness path —
  `getNodeReadinessSync` (control-plane-readiness-service-node-methods.js:333) ->
  `resolveNodeMembershipPublicationPlanningAnswerSync`
  (control-plane-readiness-service-segment-4-stage-3.js:480) ->
  `resolveMembershipPublicationPlanningSnapshot` (stage-3:19, the merge).
- Authoritative State: the per-publisher-node merged membership-publication planning
  projection (publicationRecoveryGate + priority-recovery projection), a pure function
  of publication + node/service/partition cluster state for the publisher node.
- Stable Witness: (latency) seed event-loop gap-watchdog max single gap during recovery
  drops below the raft election timeout, with the
  `resolveMembershipPublicationPlanningSnapshot` / `buildMembershipPublicationPlanning
  Snapshot` / `buildPriorityRecoveryPlanningProjection` frames no longer dominating
  the profiler windows; (convergence) the seed HOLDS control_plane_publications-p1
  leadership through recovery (no mass "Lost leadership" downstream of a >election-
  timeout gap) and the published epoch reaches the full active-node set.
- Allowed Evidence: gap-watchdog series (taggedExclusiveMs/unexplainedMs/openSections),
  V8 sampling-profiler topInclusiveFrames, owner decision-trace leadershipTier +
  reconcile outcome, authoritative publication rows.
- Forbidden Promotion Inputs: none new — this is a pure-latency/liveness memo; routing
  and admission DECISIONS must be byte-identical with the memo on vs off within a tick

  state).
- Convergence Trigger: query-routing readiness evaluation during the post-restart
  recovery window (per service row, per query, per ingress/mutation-readiness check).
- Entry Gate: same as CL-001 — `Cluster._waitForAllActive()` load-mode gate (the
  published-set disagreement is the downstream symptom).
- Current Symptom: gate 054348Z (UNPROFILED, N=8) run4 STALLED missing=2 / run6 SLOW

- Next Falsification Step (before relying on the fix): confirm the stage-3

### Fix Design (rubber-ducked; corrected after the design subagent mis-located the call sites)

LOCUS — CORRECTED 2026-06-14 after adversarial verification (my first grep used
`grep -v '...(context'` which HID the call sites that pass a variable named `context`;
the design subagent was RIGHT that there are more). `resolveMembershipPublicationPlanning
Snapshot` has SIX callers; FIVE are on the sync getNodeReadinessSync hot path:
- stage-3:503 `resolveNodeMembershipPublicationPlanningAnswerSync` — the MAIN path;
  providedPlanningSnapshot = getMembershipPublicationPlanningAnswerSync output (P1).
  THIS is what the landed memo covers.
- stage-4:318 `buildPriorityControlPlaneRecoveryProjection`, segment-2:41
  getPriorityControlPlaneRecoveryState wrapper, segment-2:442
  `isControlPlaneRecoveryEligible`, runtime-authority-methods:257
  `buildRuntimeAuthoritySnapshot` — all reached via buildEvaluatedNodeReadinessSnapshot
  (segment-3:301); each re-runs the RAW merge with providedPlanningSnapshot =
  context.membershipPublicationPlanningSnapshot = the RESOLVED answer (P2), a DIFFERENT
  provided snapshot than P1. So these 4 CANNOT share the P1-keyed merge memo without a
  collision (different providedPlanningSnapshot → different merge output for the same
  nodeId). (stage-3:550 async is not hot.)
- The directPlanningSnapshot build (buildMembershipPublicationPlanningSnapshot,
  stage-2:466) is CHEAP — it only assembles from the already-computed membershipPublication
  (buildPublicationRecoveryProtocolSnapshot + normalize), no deep cluster read and no
  buildPriorityRecoveryPlanningProjection — so memoizing IT would not capture the dominant
  cost. The dominant residual cost is the merge's FINAL buildPriorityRecoveryPlanning
  Projection (stage-3:299/:42; the fastJsonClone/parseStepsHistory self-frames), which is
  providedPlanningSnapshot-dependent.

FIX (mirror CL-033 exactly):
- New `resolveMemoizedMembershipPublicationPlanningSnapshotSync(nodeId, observedAt,
  membershipPublication, planningSnapshot)` wrapping the stage-3 merge
  `resolveMembershipPublicationPlanningSnapshot({nodeId, observedAt, membershipPublication,
  membershipPublicationPlanningSnapshot: planningSnapshot})`, keyed per publisher node
  (nodeId || this.nodeId), reused when `!isReadinessSnapshotInvalidated(memoKey,
  capturedAtMs)` AND within `membershipPublicationPlanningActiveStaleGraceMs` AND the
  latest publication epoch/status still match the cached projection (the identical
  validity predicate `resolveMemoizedPriorityRecoveryPlanningProjectionSync` uses).
- The side-effectful per-node layer `resolvePriorityRecoveryPlanningAnswer` (storeActive/
  clearActive) stays OUTSIDE the memo and runs every call on the cached frozen merge,
  exactly as CL-033 keeps it outside its projection memo.
- New field `membershipPublicationPlanningSnapshotMemoByNodeId` (segment-1.js init,
  alongside priorityRecoveryPlanningProjectionMemoByNodeId), cleared on
  membership-service swap (segment-1.js:325) and cache swap (segment-1.js:360).

SAFETY (why no new staleness class — same argument CL-033's verifier accepted):
- The merge output is ALREADY `Object.freeze(...)` today (buildPriorityRecoveryPlanning
  Projection, stage-1:464 ends `return Object.freeze({...})`), so reusing the same
  instance across calls introduces ZERO new mutation hazard; resolvePriorityRecovery
  PlanningAnswer already receives it frozen.
- Invalidation covers every decision-relevant input: ack/epoch/status changes are
  CONTROL_PLANE_PUBLICATIONS row writes -> handleCacheChange advances the cluster marker
  (snapshot-store.js:625-632) -> memo invalid; NODES/SERVICES changes advance the
  per-node marker (:634-641) -> memo invalid. The ONLY un-invalidated window is
  PARTITIONS / NODE_ENDPOINTS, which CL-033 already tolerates for the identical reason
  (advancing the marker on PARTITIONS — the highest-churn table in recovery — would
  collapse all reuse and re-open the freeze). The CL-034 merge consumes the same cluster
  state as the CL-033 projection it sits next to, so it reproduces exactly the existing
  PARTITIONS-stale window, not a wider one.

GUARD (red-on-revert): test/control-plane/cl-034-planning-snapshot-merge-memo.test.js —
(a) build-once-per-stable-epoch (N routing calls -> 1 merge build); (b) exactly-one-
rebuild-per-invalidation (invalidate via NODES/PUBLICATIONS marker -> exactly one
rebuild); (c) per-publisher-node keying (invalidating node A does not rebuild node B);
(d) nodeId||this.nodeId fallback. Neutralizing the memo must fail (a)-(c).

### LANDED 2026-06-14 (commits e542b02d + 7cfba95d) + adversarial verification (TRUSTED-WITH-NOTES)
