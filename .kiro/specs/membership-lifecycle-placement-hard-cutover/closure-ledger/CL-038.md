# CL-038 A Surplus-Drain REPLACE's Source-Leader Handoff Must Terminalize When Its Source Replica Is Already Locally Removed

## First Violated Invariant

A surplus-drain REPLACE whose source-removal step is gated on a source-leader handoff
(`STEP_DOWN_REPLICA`) must reach a settling decision once the source replica is no longer
locally tracked on the source node. When the named source replica has already been locally
REMOVED, the handoff is moot (there is no local leader left to step down), but the handler
returns `NOT_APPLICABLE`/`NOT_FOUND` and the workflow re-dispatches the same dead handoff
indefinitely, so the REPLACE `source_removal` step never terminalizes, the priority-recovery
operation drain never settles, and cluster topology never quiesces within the run budget —
even though membership publication has already CONVERGED (missing=0).

## Open Nuance To Resolve Before Coding (rubber-duck + falsify first)

The handler returns `NOT_FOUND`, and `recordPriorityPublicationLeaderHandoffEvidence` DOES accept
NOT_FOUND and records evidence (sourceReplicaId=r2, 1-minute TTL). Yet the STEP_DOWN re-dispatches
every ~30s (well inside the 1-min TTL), so the recorded evidence is NOT unblocking the
safe-removal. Candidates to pin (one falsification each) BEFORE choosing the fix locus:
1. **operationId churn**: the gate keys evidence by `operationId`; if the drain re-derives a new
   op instance per reconcile, the recorded evidence's operationId never matches the gate's lookup.
   Falsify: compare `operationId` on the dispatch/record path vs the gate-read path across two
   reconciles in the seed ndjson.
2. **durable-row lag (CL-029 class)**: the local removal completed (cache REMOVED) but the durable
   workflow row never advanced from `source_removal/dispatched`, so the reconcile re-derives "need
   handoff" regardless of recorded evidence. Falsify: read the durable `currentStepId` transitions
   for the op vs the cache `latestOperationWorkflowStep`.
3. **target-readiness is the real gate**: the safe-removal also requires the REPLACE target
   (8be8d30f / 11601fe0) voter-ready, and the handoff is a red herring. Falsify: check target
   replica voter-ready state at the wedge window.

## Candidate Fix Directions (do NOT implement until the nuance above is pinned + rubber-ducked)

- (a) **Source side**: when the source replica is already locally removed (no local leader to step
  down), the remove-safety gate must treat the handoff as SATISFIED/UNNECESSARY (the removal
  already relinquished leadership) and terminalize source_removal — never re-dispatch a STEP_DOWN
  for an absent replica. Must NOT weaken safety for a source replica that is still present and
  leader.
- (b) **Handler side**: `requestTrackedPartitionLeaderHandoff` should resolve the handoff by
  `partitionId` + leader role (or recognize "source absent → already handed off → COMPLETED")
  rather than requiring an exact `replicaId` key match; a persistent NOT_FOUND for a removed source
  should terminalize, not silently re-defer.
- Prefer the locus the falsification implicates (likely (a) if durable-row lag, or the gate's
  evidence-consumption if operationId churn). Guard red-on-revert + re-gate N>=4 expecting the
  STEP_DOWN re-dispatch loop to stop, the readiness oscillation to flatten, the rebalancer churn
  batches to disappear, and SLOW/long-wall topology-quiesce runs to compress.
