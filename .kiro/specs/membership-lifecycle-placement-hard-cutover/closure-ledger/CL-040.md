### 2026-06-16 — FIX LANDED → `guarded`

Fix: `src/raft/liferaft.js` `truncateConflictingSameIndexTail(raft, packet)`, called at the top of the `APPEND` branch of the patched data listener (guarded synchronously by `if (raft.log && typeof raft.log.get === 'function')`). Raft §5.3 conflicting-entry deletion: when an inbound append's `packet.last` references index `i` (the leader's last entry on a heartbeat, or prevLog on an entry-append) and the follower holds its OWN, UNCOMMITTED entry at `i` with a DIFFERENT term, delete it and everything after (`removeEntriesAfter(i-1)`), so the base append-fail/catch-up rebuilds the suffix from the leader instead of the commit-index catch-up stale-committing the follower's own entry. Inert on the normal path (fires only on a real same-index/different-term conflict); never touches a committed entry (a committed entry cannot legitimately conflict). No new writer / no leadership change → does not affect the B4 single-writer invariant.

The synchronous `if (raft.log ...)` guard is load-bearing for test fidelity, not just perf: an unconditional `await` of the (async) helper added one microtask hop per append even on logless nodes, which shifted the virtual-clock async interleaving of the logless DT6 step-6 scenario (deterministic-but-microtask-sensitive) and broke seed 8. Guarding so logless nodes never await restores byte-identical timing; logful nodes (step 7, the production message-group raft) take the necessary await (production-safe — one extra microtask on an already-async path).

Evidence: `test/closure/CL-040.repro.test.js` flipped `todo` → green (asserts committed-entry agreement across nodes; red-on-revert confirmed). DT6 step-7 guard tightened to additionally assert committed-row equality (`test/convergence/dt6-publication-quorum-failback-network.test.js`, +1 assertion, green). `test/raft/` 689/689, `test/message-group/` all pass + 3 pre-existing skips. control-plane+distributed pre-existing failures = 68 with AND without the fix (zero new). ### 2026-06-16 — opened at `reproduced` (DT6 step-7 verification finding)

Surfaced by the independent verification of DT6 step 7 (`test/convergence/dt6-publication-quorum-failback-network.test.js`), which drives a REAL quorum-gated publication commit through a real liferaft log over the deterministic VirtualNetwork. The step-7 guard deliberately asserts published-VERSION convergence (which holds) and NOT committed-COMMAND equality (which would expose this gap) — so step 7 stays green; this record tracks the separate raft-layer violation.

Concrete evidence (deterministic, seed 0 and seed 3, captured at log index 2 after a Phase-A commit, a partition+migration, a stale old-leader append, a new-leader quorum commit, and heal):

```
seed 0: leaderA=N1 leaderB=N2
  idx2 per node:
    N1 (old leader): {committed:true, term:1, command:{tag:'OLD', by:'N1'}}
    N2 (new leader): {committed:true, term:2, command:{tag:'NEW', by:'N2'}}
    N3 (follower):   {committed:true, term:2, command:{tag:'NEW', by:'N2'}}
```

So index 2 is committed cluster-wide but the committed COMMAND differs (old leader keeps its own stale term-1 entry; the rest hold the new leader's term-2 entry) — an agreement-safety violation. In the DT6 step-7 publication scenario the divergent commands are membership publication rows with different `publisher_node_id`/`term` at the same index; the published-VERSION field happens to collide (both required-version 2), which is why step-7's coarser assertion stays green.

Mechanism (from the step-7 verifier's instrumentation): base liferaft's `append` handler skips truncation when `packet.last.index === localLastIndex` (both `i`), then the commit catch-up (`committedIndex < packet.last.committedIndex`) commits the follower's OWN local entry at `i` without verifying its term/command matches the leader's. `src/raft/in-memory-log-adapter.js commit(index)` marks `this.entries.get(index)` committed unconditionally (no match check). The `src/raft/liferaft.js` `patchIncomingDataListener` adds a committed-prefix guard for the multi-entry BATCH path (`handleFollowerAppendBatch`: `packet.last.index < getCommittedIndex(raft)` → no-op) but the single-entry same-index path is unguarded.

Scope of impact: PRE-EXISTING in `@markwylde/liferaft` + `InMemoryLogAdapter`; NOT introduced by DT6. Whether it bites production depends on whether a partitioned old leader ever appends an uncommitted entry at the same index a new leader commits, and whether anything downstream reads the committed COMMAND (not just an index/epoch) across nodes. The message-group raft (the production `InMemoryLogAdapter` consumer) and the control-plane publication path are the exposure surfaces to assess.
