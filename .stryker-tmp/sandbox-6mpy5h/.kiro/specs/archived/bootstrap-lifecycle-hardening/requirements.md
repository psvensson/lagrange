# Requirements Document

## Introduction

The distributed database system's bootstrap, join, CDC propagation, and rebalance lifecycle suffers from brittleness caused by implicit timing dependencies, fire-and-forget CDC propagation, absence of readiness signals, and premature rebalancer activation. This feature hardens the lifecycle by introducing awaitable CDC confirmation, explicit readiness gates, CDC event buffering, cluster-readiness-gated rebalancing, seed bootstrap optimization, and improved CDC pipeline observability. The goal is to eliminate silent event loss, race conditions between write and cache visibility, and premature rebalancer decisions during cluster formation.

## Glossary

- **CDC_Pipeline**: The end-to-end path from a partition leader generating a CDC event through message group propagation to SystemTableCache update on every node
- **CDC_Confirmation**: A trackable promise returned by the CDC generation path that resolves when the event has been applied to the local SystemTableCache
- **CDC_Pipeline_Readiness_Gate**: A component that determines whether the CDC pipeline is fully wired and capable of propagating events from partition leaders to the SystemTableCache
- **CDC_Event_Buffer**: A bounded in-memory buffer that captures CDC events generated by partition leaders before CDC subscriptions are active, for replay once subscriptions are established
- **Cluster_Readiness_Signal**: A composite readiness check that evaluates whether the cluster has reached a stable state suitable for rebalancer planning (all expected nodes registered, CDC pipeline ready, cache hydrated)
- **Rebalancer**: The UnifiedRebalancer component that manages replica placement for partitions, message groups, and replicated service groups
- **SystemTableCache**: The in-memory cache of CDC-propagated system tables, updated only by CDC events (plus bootstrap hydration exception)
- **PartitionService**: A SQLite-backed Raft group that stores data and generates CDC events on writes
- **BootstrapService**: The seed node bootstrap orchestrator that sequences infrastructure, message group, partition, registration, and cache hydration phases
- **NodeJoiningService**: The joining node bootstrap orchestrator that contacts the seed, hydrates cache from snapshots, subscribes to CDC, and registers the node
- **CDCGroupPropagationService**: The topology-aware service that routes CDC events through message group leaders to all nodes

## Requirements

### Requirement 1: Awaitable CDC Confirmation

**User Story:** As a system component, I want to optionally await CDC delivery confirmation after a write, so that I can safely read from the SystemTableCache without racing against the asynchronous CDC pipeline.

#### Acceptance Criteria

1. WHEN a write is committed through PartitionService and the caller requests CDC confirmation, THE PartitionService SHALL return a promise that resolves when the corresponding CDC event has been applied to the local SystemTableCache
2. WHEN a write is committed without requesting CDC confirmation, THE PartitionService SHALL maintain the existing fire-and-forget CDC generation behavior with no additional overhead
3. WHEN a CDC confirmation promise does not resolve within a configurable timeout, THE PartitionService SHALL reject the promise with a descriptive timeout error
4. IF a CDC event fails to propagate through the pipeline, THEN THE CDC_Confirmation SHALL reject with an error describing the failure stage (generation, propagation, or cache application)
5. THE CDC_Confirmation timeout SHALL be configurable through ConfigurationManager with a default value defined as a named constant

### Requirement 2: CDC Pipeline Readiness Gate

**User Story:** As a bootstrap orchestrator, I want to verify that the CDC pipeline is fully operational before declaring a node ready, so that no writes are lost due to incomplete pipeline wiring.

#### Acceptance Criteria

1. THE CDC_Pipeline_Readiness_Gate SHALL evaluate three conditions: CDC subscriptions are active on all CDC-propagated system tables, the propagation message group has an elected leader, and the pipeline has successfully delivered at least one event to the SystemTableCache
2. WHEN all three readiness conditions are satisfied, THE CDC_Pipeline_Readiness_Gate SHALL report the pipeline as ready
3. WHEN any readiness condition is not satisfied, THE CDC_Pipeline_Readiness_Gate SHALL report which specific conditions are unmet
4. WHEN the CDC_Pipeline_Readiness_Gate does not reach ready state within a configurable timeout, THE BootstrapService SHALL fail the bootstrap with a descriptive error identifying the unmet conditions
5. WHILE the CDC_Pipeline_Readiness_Gate reports the pipeline as not ready, THE BootstrapService SHALL not transition the node to READY state
6. WHILE the CDC_Pipeline_Readiness_Gate reports the pipeline as not ready, THE NodeJoiningService SHALL not transition the node to READY state

### Requirement 3: CDC Event Buffering During Subscription Setup

**User Story:** As a bootstrap orchestrator, I want CDC events generated between partition leader election and CDC subscription setup to be buffered and replayed, so that no events are silently lost during bootstrap.

#### Acceptance Criteria

1. WHEN a partition leader generates a CDC event and no CDC subscribers are registered, THE CDC_Event_Buffer SHALL capture the event in a bounded in-memory buffer
2. WHEN CDC subscriptions become active, THE CDC_Event_Buffer SHALL replay all buffered events to the subscribers in the order they were generated
3. WHEN the CDC_Event_Buffer reaches its capacity limit, THE CDC_Event_Buffer SHALL drop the oldest events and emit a warning-level log with the count of dropped events
4. WHEN buffered events are replayed, THE CDC_Event_Buffer SHALL deduplicate events that were already delivered through the normal subscription path
5. THE CDC_Event_Buffer capacity limit SHALL be defined as a named constant

### Requirement 4: Rebalancer Cluster-Readiness Gate

**User Story:** As a cluster operator, I want the rebalancer to wait for a cluster-level readiness signal before its first planning cycle, so that it does not make premature placement decisions based on incomplete cluster state.

#### Acceptance Criteria

1. WHEN the Rebalancer is activated on a partition leader, THE Rebalancer SHALL evaluate the Cluster_Readiness_Signal before executing its first planning cycle
2. THE Cluster_Readiness_Signal SHALL evaluate three conditions: all nodes registered during the current bootstrap or join sequence are present in the SystemTableCache with ACTIVE status, the CDC_Pipeline_Readiness_Gate reports ready, and the SystemTableCache contains at least one complete hydration of all CDC-propagated system tables
3. WHILE the Cluster_Readiness_Signal is not satisfied, THE Rebalancer SHALL defer its first planning cycle and re-evaluate at the next periodic check interval
4. WHEN the Cluster_Readiness_Signal is satisfied, THE Rebalancer SHALL proceed with normal stabilization-period-based planning
5. WHEN the Cluster_Readiness_Signal does not become satisfied within a configurable timeout, THE Rebalancer SHALL log a warning with the unmet conditions and proceed with planning using available state

### Requirement 5: Seed Bootstrap Single-Replica Optimization

**User Story:** As a cluster operator, I want the seed node to create single-replica groups during bootstrap and scale up as nodes join, so that the second node joining does not trigger a redistribution storm.

#### Acceptance Criteria

1. WHEN the seed node bootstraps, THE BootstrapService SHALL create partition and message group Raft groups with a single replica on the seed node
2. WHEN a second node joins the cluster, THE Rebalancer SHALL scale partition and message group replica counts from one to the policy target count by adding replicas on the new node
3. WHEN the seed node operates with single-replica groups, THE PartitionService SHALL establish leadership immediately without running a Raft election
4. WHEN scaling from single-replica to multi-replica groups, THE Rebalancer SHALL add replicas as learners before promoting them to voters
5. IF the seed node fails before a second node joins, THEN THE single-replica groups SHALL contain all committed data with no data loss

### Requirement 6: CDC Pipeline Observability and Error Reporting

**User Story:** As a cluster operator, I want observable CDC pipeline behavior with no silent event drops, so that I can diagnose propagation failures and trust that all writes reach the SystemTableCache.

#### Acceptance Criteria

1. WHEN a CDC event is generated by a partition leader but not delivered to any subscriber, THE PartitionService SHALL emit a warning-level log containing the table name, operation type, and partition identifier
2. WHEN CDCGroupPropagationService cannot resolve a propagation message group, THE CDCGroupPropagationService SHALL emit a warning-level log with the table name and reason for resolution failure instead of silently returning null
3. WHEN a CDC event delivery fails at any stage of the pipeline, THE owning component at that stage SHALL emit a warning-level log with the event details and failure reason
4. THE CDC pipeline SHALL expose a metrics snapshot containing: total events generated, total events delivered to cache, total events dropped, and total delivery failures
5. WHEN the BootstrapService resolves a CDC propagation message group and the result is null, THE BootstrapService SHALL emit a warning-level log identifying the CDC event that will not be propagated

### Requirement 7: Integration Test Stabilization

**User Story:** As a developer, I want the failing integration tests to pass reliably by leveraging the new readiness gates and awaitable CDC, so that the test suite is trustworthy without relying on hardcoded timeouts.

#### Acceptance Criteria

1. WHEN the CDC propagation integration test verifies cache visibility after a write, THE test SHALL use awaitable CDC confirmation instead of polling with hardcoded timeouts
2. WHEN the control plane rebalance integration test verifies dispatch behavior, THE test SHALL wait for the Cluster_Readiness_Signal before asserting rebalancer outcomes
3. WHEN the leader metadata validation integration test verifies leader information in cache, THE test SHALL use the CDC_Pipeline_Readiness_Gate to confirm pipeline readiness before assertions
4. WHEN the multi-node Raft replication integration test verifies cross-node replication, THE test SHALL use awaitable CDC confirmation to verify write visibility across nodes
