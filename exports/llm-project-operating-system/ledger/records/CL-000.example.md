## CL-000 Concurrent signup returns 500 (uniqueness check races the insert)

- Status: narrowed
- Concern: request-correctness
- Failure Class: data-race
- First Violated Invariant: At most one account row exists per normalized email, and a signup either creates that row or returns a clean 409 — never a 500.
- Authoritative Owner: `SignupService.register` (the write path that owns account creation).
- Authoritative State: The `accounts` table row keyed by `lower(email)`, plus the unique constraint `accounts_email_key`.
- Allowed Evidence: the unique-constraint violation surfaced by the database insert; the committed row returned by the insert.
- Forbidden Promotion Inputs: a prior `SELECT ... WHERE email = ?` returning zero rows used as proof the email is free (read-then-write is not a uniqueness guarantee under concurrency); an application-level in-memory "seen emails" cache used as completion proof.
- Progress Trigger: the account-creation insert reaching the database and either committing or raising the unique-violation error that the service maps to 409.
- Stable Witness: HTTP status distribution for `POST /signup` under the concurrency probe — count of {201 created, 409 conflict, 500 error}; the invariant holds when the 500 count is 0 and exactly one 201 wins per duplicate burst.
- Entry Gate: `concurrent-signup` load probe (N parallel requests for the same new email).
- Current Symptom: Under two or more simultaneous signups for the same email, one request returns 201 and the loser intermittently returns 500 (an unhandled unique-violation) instead of 409.
- Scope: A targeted test that fires K concurrent `register()` calls with one identical email against a real database connection.
- Next Falsification Step: Run the concurrency probe with the pre-insert `SELECT` removed and the insert wrapped to catch the unique-violation and map it to 409; confirm the 500 count drops to 0 while exactly one 201 remains.
- Required Guard: A regression test under the concurrent-signup gate asserting {exactly one 201, the rest 409, zero 500} for a duplicate-email burst.

### Evidence

1. Load probe `concurrent-signup` at concurrency 8 produced status mix `{201: 1, 409: 5, 500: 2}` — two losers raised 500.
2. The 500 responses carry the database error `duplicate key value violates unique constraint "accounts_email_key"`, raised by the insert, not by application validation.
3. The handler performs `SELECT` for the email and, on zero rows, proceeds to `INSERT`; concurrent callers all observe zero rows in their own snapshot before any of them commits (read-then-write race).
4. The unique constraint `accounts_email_key` exists and is doing its job at the storage layer — the bug is that the service does not translate its violation into the 409 path.

### Exit Criteria

1. The concurrent-signup gate reports zero 500 responses across the duplicate-email burst.
2. Exactly one request wins with 201 and every other duplicate request returns 409.
3. The regression guard exists and passes, and asserts the full status distribution (not just "no exception thrown").
4. No forbidden promotion input (read-then-write existence check, in-memory seen-email cache) is used to obtain the green result; correctness rests on the database constraint plus the violation-to-409 mapping.

### Notes

1. The pre-insert `SELECT` may stay as a fast-path for the common non-conflicting case, but it must not be treated as a uniqueness guarantee — the constraint plus the caught violation is the only authoritative truth.
2. Cross-cutting effect (kept here, not promoted to a second concern): the 500s also pollute the error-rate alarm; that is a downstream symptom of this one invariant, so it does not get its own record.
